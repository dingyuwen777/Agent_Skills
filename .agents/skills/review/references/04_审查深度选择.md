# 审查深度选择

Review 采用**最小充分**深度：只审到足以覆盖当前真实风险、协作交接和合并结论的程度，不把每个小 PR 都机械提升为完整 L3 审查；一旦发现更高风险事实则立即升级。

## Quick Review

适用：L1、边界明确的小 diff、行为不变的机械修改或低风险局部修复。

至少检查：

- 实际 diff 与直接邻近调用链；
- 明显边界条件、错误处理和回归风险；
- 与修改目标直接对应的测试/验证；
- 是否意外改变 public Contract、数据、权限、配置或运行时边界。

Quick Review 不能用“改动很小”跳过已经出现的高风险事实；一旦发现 public Contract、Schema/Migration、安全/权限、数据或跨组件语义变化，升级 Standard/Deep。

## Standard Review

适用：普通 L2 Feature、Bug、重构、前端/后端正常行为变化，以及需要独立审查但没有 L3 风险的 PR。

在 Quick 基础上至少检查：

- 当前可验证的目标、范围/非目标、验收标准和关键不变项；
- 实现是否符合真实模块/Contract Owner；
- 错误处理、状态转换、兼容和相邻回归；
- 测试层是否覆盖当前真实失败边界；
- 文档/配置/构建影响是否按事实处理。

若没有持久 Requirement Source，但当前任务事实足够支持本 PR 的有限范围审查，可以明确审查边界；不得把有限范围结论冒充“已验证完整产品需求”。

## Deep Review

适用：L3，或 public API/ABI/CLI/数据格式、Schema/Migration、认证授权、安全、重要数据语义、破坏性兼容、重大部署/依赖、重要跨 Owner/多 PR 交付。

必须结合 Review Skill 既有流程完整执行：

- 独立重建上游 Requirement Source；
- A1：上游要求 → 施工/实现范围，检查 requirement omission；
- A2：已确认要求 → 实现/测试/文档，检查真实覆盖；
- Contract/兼容/Migration/回滚/安全边界；
- `reviewed_base_sha`、`reviewed_head_sha`、`current_base_sha` 与 current-base fresh validation；
- Findings、测试充分性和必要 re-review。

## 升级与降级

- Review 深度由**当前事实**决定，不由仓库是否 protected、历史 contributor 数量或 PR 是否存在单独决定。
- Quick/Standard 中发现更高风险后立即升级，不因为已经开始轻量审查而保持原级别。
- 已证实风险消失时可以缩小后续检查范围，但不能删除已经发现的 Finding、未验证项或项目强制门禁。
- 无论哪个深度，没有实际证据都不得声称完成、需求符合、可合并或可发布。
