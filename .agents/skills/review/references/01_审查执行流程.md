# 审查执行流程

这份规则只定义 Review 怎样独立执行，不重新定义 Coding 的研发规范，也不重新定义 Testing 的测试工程方法。

同仓存在 [`.agents/skills/coding/SKILL.md`](../../coding/SKILL.md) 时，先读取 Coding，并按当前任务触发其 references；Review 只负责把这些规范当作审查基线。

同仓存在 [`.agents/skills/testing/SKILL.md`](../../testing/SKILL.md) 时，Testing 是测试策略、黑盒/User Journey、探索式、Integration/Golden Path/Probe、Regression 和测试资产方法的专业 Owner；Review 负责审查测试充分性并在需要新增/系统性测试时 Handoff Testing。

## 1. 建立 Review Target

开始前明确：

```text
Review Target：PR / branch diff / commit range / working tree / module / feature
Base / Head：适用时记录真实 SHA/ref
模式：review-only / review-and-test / review-and-fix
授权：允许读、跑已有测试、修改测试资产、改生产代码、提交、PR、合并到什么程度
上游事实：用户决定 / Spec / Roadmap / Change / Contract / Schema
项目事实：AGENTS / Manifest / locks / build / tests / CI / runtime
```

没有明确 Target 时先从仓库和当前任务自行恢复；能从 PR、branch、diff 或代码确认的事实不要反问用户。

## 2. 先恢复规则，再看 diff

顺序：

```text
上位指令
→ 仓库 AGENTS/CONTRIBUTING
→ Coding（同仓存在时）
→ 当前任务触发的 Coding references
→ Testing（存在测试设计/执行需求且同仓存在时）
→ Review Target 相关需求/Contract/代码/测试
→ diff
```

不要先看 diff 后再凭个人习惯挑问题，否则容易把项目明确允许的实现误报成问题，也容易漏掉上游要求。

## 3. 独立重建上游要求

复杂 Review 不接受“作者已经写好了 checklist”作为需求全集。

重新建立：

```text
用户/业务已确认目标
→ 正式 Spec/Roadmap/Change 上游来源
→ public Contract / Schema / compatibility
→ 用户或 consumer 可观察结果
→ 必须保持不变
→ 非目标
```

然后分别检查：

```text
A1：上游要求 → Change / 实现，有没有漏项？
A2：Change / 实现 → 测试 / 文档 / 运行证据，有没有空证据？
```

如果 Coding 已定义 Requirement Traceability / Completion Audit，直接使用它的当前规则，不另造第二份格式。

## 4. 从影响面而不是文件数量判断风险

对每个变更问：

- 谁调用它？
- 它调用谁？
- 输入/输出/错误/状态有没有变化？
- public API/ABI/CLI/Schema/文件格式是否变化？
- 是否涉及事务、并发、重试、幂等、缓存或资源生命周期？
- 用户能看到什么变化？
- 部署/配置/依赖/运行时是否受影响？
- 现有测试最可能漏掉哪个失败模式？

“只改 5 行”不能自动判成低风险。

## 5. 先设计风险，再审测试

在读现有测试结果之前，先独立写出本次高价值风险：

```text
正常路径
边界输入
非法输入
错误/异常传播
状态转换
重试/取消/恢复
并发/幂等/事务
兼容性
安全/权限/Secret
用户可见状态
构建/启动/打包
外部依赖变化
```

不适用的项有事实依据地跳过。

这样可以避免看到“测试全绿”后产生确认偏差。

## 6. 审查测试证据

读取 [03_测试专家审查方法.md](03_测试专家审查方法.md)。

对每个重要要求建立最小映射：

```text
Requirement / Risk
→ 哪个测试或检查在证明？
→ 它实际运行了哪些真实边界？
→ 它断言了什么可观察结果？
→ 哪些边界仍是 Mock/Fake/未运行？
→ 是否存在需要 Testing 补证据的 Test Gap？
```

测试名称、覆盖率数字或 CI 绿色本身不是充分证据。

## 7. 主动验证与 Testing Handoff

`review-only` 可以运行已有、非破坏性的验证；需要新增测试或专业测试设计时，在授权范围 Handoff Testing。

优先顺序是证据价值，而不是“Review 自己多跑几层”：

```text
能快速证伪 Finding 的已有 targeted validation
→ 识别 Test Gap
→ Testing 选择/新增最小充分验证
→ Testing 返回 Evidence / Defect
→ Review 复核证据边界
```

不要为了显得“全面”默认跑最贵、最慢、最脆的测试层。

## 8. 形成 Findings

每个 Finding 按 [02_Findings与严重度.md](02_Findings与严重度.md) 输出。

形成 Finding 前至少做一次反证检查：

```text
有没有项目规则允许这种行为？
有没有上游决定说明它是刻意设计？
有没有调用链证据证明我理解错了？
有没有测试已经覆盖，只是我还没读到？
```

无法排除时降低确定性，写成待验证风险，而不是确定缺陷。

## 9. 修复回路

### review-only

只报告，不修改。

### review-and-test

```text
Review 识别 Test Gap
→ Testing 设计/新增/执行最小充分测试（存在 Testing 时）
→ Testing 返回 Evidence
→ Review 复核
```

测试证明生产缺陷后，不把 Review/Testing 当生产修复 Owner，进入 Coding。

### review-and-fix

```text
Finding 已确认
→ 失败证据已建立（需要专业测试时由 Testing）
→ 返回 Coding
→ 重新读取 `.agents/skills/coding/SKILL.md`
→ Coding 实施最小修复并完成新鲜验证
→ Testing Regression（存在独立测试风险时）
→ 返回 Review
→ 对原问题、相邻风险和新 diff 做 re-review
```

Review 不直接维护自己的生产修复规则。

### Finding Admission Gate 与 Repair Loop Owner

Main/Parent Agent 是当前 **Repair Loop Owner**。Reviewer 负责独立发现、证据和 disposition；Reviewer 不直接重新派发 Worker。每轮返修前由 Main/Parent 执行 **Finding Admission Gate**：

1. 重新核对 Finding 的证据、触发条件和当前 revision；
2. 确认 disposition 仍是 `IN_SCOPE_BLOCKING`；
3. 确认修复不突破当前 Requirement / Contract / Schema / Scope / 授权；
4. 只有满足以上条件才交给 Coding/Worker；
5. `IN_SCOPE_NON_BLOCKING` / `OUT_OF_SCOPE` 记录但不进入自动返修；`REQUIREMENT_CHANGE` 返回上游决策。

## 10. re-review 范围与 Review Convergence Guard

re-review 不是新一轮无限范围 Full Review。默认只覆盖：

- **原 blocking findings**；
- **本轮新 diff**；
- 新 diff 的**直接相邻**回归风险；
- 当前 **Acceptance Criteria**。

不要因为进入 re-review 就重新扫描与当前 Requirement / 新 diff 无关的历史问题；新发现的真实历史问题按 disposition 处理。

在上述范围内至少复核：

- 原 Finding 是否真正消失；
- 新增修复是否改变了其他合法行为；
- 回归测试是否能证明原问题与修复结果（适用时）；
- 修复是否引入新的兼容、安全、并发或测试真实性问题；
- 文档/Contract/generated 是否同步（受影响时）。

如果修复导致范围明显扩大，停止滚雪球式修改，返回 Coding/上游重新界定。

### 单调收敛与自动返修安全阀

每个 automatic repair round 至少满足以下一项才算**单调收敛**：

- unresolved blocking finding 集合减少；
- 原 blocking Finding 被关闭；
- 问题被新证据收敛到更明确、可验证的根因和更窄修复边界。

如果**连续两轮**都没有任何一项成立，执行 `STOP_REPAIR_LOOP`：停止机械 Worker↔Reviewer 循环，进入 **root-cause reanalysis** / replan。

同一 `IN_SCOPE_BLOCKING` **连续两次修复**后仍存在，第三次修复前必须先做 root-cause reanalysis；禁止只换一种写法“再试一次”。

默认每个同一 Review Target / 同一修复方案最多 **3 个 automatic repair rounds**。达到上限必须 `STOP_REPAIR_LOOP` 并 replan，**不是自动 PASS**；仍有 unresolved `IN_SCOPE_BLOCKING` 时当前交付继续 blocked。

重新诊断后，如果仍可在原 Requirement / Contract / Scope / 授权内形成有新证据支持的方案，Main/Parent 可以继续；若需要扩大这些边界，则按 `REQUIREMENT_CHANGE` 返回上游决策。

## 11. 结束条件

Review 完成不以“没有更多想法”或“Reviewer 没有任何意见”为标准，而以：

```text
目标和上游要求已覆盖
高风险调用链已读取
测试充分性已评估
Test Gap 已报告或由 Testing 补足（适用时）
必要验证有新鲜证据
不存在 unresolved IN_SCOPE_BLOCKING
Findings 有触发条件、证据和 disposition
未验证项明确
权限边界没有越过
```

没有证据支持“可合并/可发布”时，不得给这种结论。
