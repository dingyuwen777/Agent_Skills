# 审查执行流程

本 Reference 只定义 Review 执行与收敛；研发规范归 Coding，测试方法归 Testing。

## 0. Review Phase State Machine

同一 frozen Review Target 单调推进：

```text
FIRST_ASSEMBLY → REPAIR_VERIFY → ESCAPE_CORRECTION → REVIEWER_RECOVERY → FINAL
```

- `FIRST_ASSEMBLY`：首轮闭包并发布一个稳定 Finding batch。
- `REPAIR_VERIFY`：验证已经通过 Coding **Re-review Admission Gate** 的 Repair Package，只看原 blocking findings、`reviewed_head → repair_head` 的 **repair diff**、直接相邻回归与 Acceptance Criteria。
- `ESCAPE_CORRECTION`：第二轮从**未改变的旧基线**发现首轮本可推导 blocker 时标记 `FIRST_REVIEW_ESCAPE`；**不得立即发布单条**，先做一次 **fresh blind Review Assembly**，关闭同根剩余 material projections，再形成一个 **consolidated review-correction batch**；`escape budget=1`。
- `REVIEWER_RECOVERY`：escape budget 用尽后仍出现旧基线漏审时记录内部 `REVIEW_PROCESS_FAILURE`。它是**内部恢复状态、非终态**：只重开受影响 Root Invariant，说明遗漏原因，关闭剩余 material projections，撤销/合并冲突 draft，完成 **single synthesis**。`review-only` 输出稳定 `CHANGES_REQUIRED/BLOCKED`；已有修复授权时只形成一个 final recovery correction batch，修复后再做一次最终 `REPAIR_VERIFY`。
- `FINAL`：正常 Review terminal 只使用 `NO_FINDINGS_WITHIN_SCOPE / NON_BLOCKING_FINDINGS / CHANGES_REQUIRED / BLOCKED / UPSTREAM_DECISION_REQUIRED / CAPABILITY_BLOCKER` 或项目等价状态。`REVIEW_PROCESS_FAILURE` **不得作为用户/作者终态**；真实 blocker 不能为了结束流程被强行忽略。

只有**新 Requirement / 新外部事实 / repair diff 新行为**可以建立新 Review baseline；Reviewer 自身漏审不能借机重开无界 Full Review。

## 1. 冻结 Review Target

恢复而不是猜测：

```text
Review Target / base / reviewed_head
review-only | review-and-test | review-and-fix
Requirement / Acceptance / Contract / Schema / 不变项 / 非目标
项目规则 / Coding required Context / tests / CI / authorization
```

先读规则与 Requirement，再读 diff/调用链；PR 描述、作者 checklist、CI Green 都不是需求全集。

## 2. Review Coverage Map 与首次发布闭包

按真实影响面覆盖 Requirement、Contract/compatibility、state/lifecycle/error/recovery、并发/幂等/事务、安全/权限、用户行为、test/evidence、build/runtime/docs；每域记 `covered / ruled_out / not_applicable / unknown`。高风险 unknown 先有界取证。

### Material Projection Matrix

复合机制先写 **Root Invariant**，再枚举会改变 Review terminal、修法、Acceptance 或 compatibility 的 sibling projections；状态为 `confirmed / ruled_out / covered_by_evidence / not_applicable / unknown`。这组叫 **Material Projection Matrix**。

`material unknown` 若答案不同会改变当前结论或 Finding batch，发布前必须继续调查；非 material unknown 可作为剩余风险。达到 Systemic 条件先 route refresh 到 `执行模式=诊断`，复用 Coding [`22_根因调试.md`](../../coding/references/22_根因调试.md)，按 Invariant → Lifecycle/state/ownership → Failure Boundary → Projection 闭环，保持**机制内完整、任务外有界**；**新代码/Requirement/外部事实引入的不记** First-pass Coverage Miss。

### First Review Assembly Gate / No-Findings-Drip Gate

按 [04_审查深度选择.md](04_审查深度选择.md) 做固定、非递归 Assembly；blind 视角互不看 Finding，只返回**内部 draft**，Parent **一次 synthesis / single synthesis**。

对外发布前必须满足：

```text
Root Invariant
+ Material Projection Matrix 无会改变结论的 material unknown
+ Coverage / Omission Audit
+ Counterevidence Check
+ single synthesis
```

这就是 **No-Findings-Drip Gate**。通过前一律**禁止发布** Finding、禁止触发 Repair Batch、禁止逐条 request-review；也**不得向作者发布部分 Findings**或在 synthesis 后**递归开启 Full Review**。首轮漏掉旧基线可推导 blocker = First-pass Coverage Miss。

## 3. Evidence 与 Testing

先独立列 Requirement/Risk，再看现有测试：

```text
Requirement/Risk → Evidence → 实际边界 → 断言结果 → Gap
```

测试名、覆盖率或 CI Green 不是充分证据。review-only 可跑已有非破坏性 targeted validation；需要新增/系统测试时 Handoff Testing；Testing 证明生产缺陷后返回 Coding。

## 4. 模式与 Finding Owner

- `review-only`：只报告。
- `review-and-test`：Review 定 Test Gap → Testing 验证 → Review 复核。
- `review-and-fix`：Finding → Coding 修复/Green → Testing Regression（适用）→ Repair Package Closure → `REPAIR_VERIFY`。

Reviewer owns Finding classification；Parent owns repair scheduling。Parent 不得单方降级 blocker、改 Scope 或关闭 Finding；Reviewer 不直接派 Worker。

## 5. Second-pass Repair Verification

作者完成统一 Repair Batch 后，必须先通过 Coding 的 **Repair Package Closure / Re-review Admission Gate**；外部第二轮 Review 默认只做 `REPAIR_VERIFY`，不是第二次 Full Review。

正常第二轮新 Finding 只允许来自：**repair diff 新行为/回归、新 Requirement、新外部事实**。若发现：
- 旧基线本可推导问题 → `FIRST_REVIEW_ESCAPE`，进入 `ESCAPE_CORRECTION`；
- 本可由 Repair Package Closure 捕获的 repair-diff blocker → `REPAIR_PACKAGE_ESCAPE`；先对当前 repair diff 做一次 bounded sibling closure / single synthesis，再发布一个 consolidated repair-correction batch，不按问题逐条滴漏。

第二轮的目标是验证已收敛 Repair Package；不是把“继续替作者找 repair 问题”当正常职责。

## 6. Review Convergence Guard

### Net Delivery Convergence

无本轮引入的**同级或更高级** BLOCKING，且 blocker/影响下降或 Acceptance Evidence 增强才是 `Delivery Convergence`；只把根因说得更清楚是 `Diagnostic Progress`。

正常路径是一批 Finding → 一个 Repair Package → 一次 delta re-review。**连续两轮**无净收敛 → `STOP_REPAIR_LOOP / root-cause reanalysis`；同一 blocker **连续两次修复**仍在先 repair-plan reset。`3 个 automatic repair rounds` 是 hard ceiling，**不是自动 PASS**。

## 7. 结束条件

Requirement/Acceptance、Coverage/Material Projection、关键调用链、测试充分性、Findings Evidence、新鲜验证和未验证边界都处理后才能结束。缺事实/测试先由 Agent 有界恢复；只有真实 `OWNER_DECISION / AUTHORIZATION_REQUIRED / REQUIRED_USER_INPUT / CAPABILITY_BLOCKER` 才向上游请求，不把 Reviewer 自己没审完当 blocker。
