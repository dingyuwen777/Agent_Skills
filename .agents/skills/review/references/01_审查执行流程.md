# 审查执行流程

本 Reference 只定义 Review 执行与收敛；研发规范归 Coding，专业测试方法归 Testing。

## 1. 冻结 Review Target 与事实

开始前恢复而不是猜测：

```text
Review Target / base / reviewed_head
review-only | review-and-test | review-and-fix
Requirement / Acceptance / Contract / Schema / 必须保持不变 / 非目标
AGENTS / Coding required Context / 测试与 CI / 当前授权
```

能从 PR、仓库和正式事实恢复的内容不问用户。先读规则和 Requirement，再读 diff/调用链；PR 描述、作者 checklist、CI Green 都不是需求全集。

## 2. Review Coverage Map

按真实影响面只纳入适用风险域：Requirement、Contract/compatibility、state/lifecycle/error/recovery、concurrency/idempotency/transaction、security/permission、user-visible behavior、test/evidence、build/runtime/docs。每个域最终为 `covered / ruled_out / not_applicable / unknown`；高风险 unknown 先有界恢复事实或验证，不把猜测发布成 Bug。

### First Review Assembly Gate

按 [04_审查深度选择.md](04_审查深度选择.md) 使用固定、非递归 Review Assembly。各视角基于同一冻结 base/head 独立工作，**互相不看 Finding**，只返回内部 draft findings；Parent 只做一次 synthesis：去重同根问题、按 current revision / source owner / Contract / 可复现 test/probe / 更直接 Evidence 裁决冲突，并关闭 Coverage Map。**synthesis 后不得递归开启新的 Full Review，也不得先把部分问题发给作者**。

达到 Systemic 条件先 route refresh 到 `执行模式=诊断`，复用 Coding [`22_根因调试.md`](../../coding/references/22_根因调试.md)。按 **Invariant → Lifecycle/state/ownership → Failure Boundary → Projection** 审查；Projection 状态为 `confirmed / ruled_out / covered_by_evidence / not_applicable / unknown`；Findings 前完成 **Omission / Coverage Audit**，保持**机制内完整、任务外有界**。冻结旧基线本可推导却未进入首轮 batch 的 blocker 是 **First-pass Coverage Miss**。

Assembly 完成后才按 [02_Findings与严重度.md](02_Findings与严重度.md) 建立稳定 Finding ID；若交给另一作者返修，追加 `治理=多人协作`，进入 Coding Repair Batch。默认一个 blocking Finding batch 对应一次 repair handoff，不逐条 request-review。

## 3. Evidence 与 Testing

先独立判断风险，再看现有测试。对重要项只问：

```text
Requirement/Risk → 哪个 Evidence → 实际运行什么边界 → 断言什么结果 → 仍缺什么
```

测试名、覆盖率或 CI Green 不是充分证据。review-only 可运行已有非破坏性 targeted validation；需要新增/系统测试时 Handoff Testing。Testing 证明生产缺陷后返回 Coding，不让 Review/Testing 变成生产修复 Owner。

## 4. 三种模式

- **review-only**：只报告，不修改。
- **review-and-test**：Review 定 Test Gap → Testing 最小充分验证 → Review 复核 Evidence。
- **review-and-fix**：Finding 确认 → Coding 按当前规则修复并取得新鲜 Green → Testing Regression（适用）→ Second-pass Repair Verification。

### Finding Classification 与 Repair Scheduling Owner

**Reviewer owns Finding classification；Parent owns repair scheduling。** Reviewer 判 Evidence/severity/Scope/Delivery Effect/Action；Parent 只调度已确认的 repair。Parent **不得单方**降级 blocker、改 Scope 或关闭 Finding；Reviewer 不直接派 Worker。

## 5. Second-pass Repair Verification

作者完成统一 Repair Batch 后冻结 `repair_head`，以 `reviewed_head → repair_head` 的 **repair diff（本轮新 diff）**为主，只审**原 blocking findings / repair diff / 直接相邻回归 / Acceptance Criteria**；未改变旧基线不得重开为**无限范围** Full Review。逐 Finding ID 核验 closure 与 Evidence。

只有 repair diff 新引入行为/回归、**新 Requirement**、**新外部事实**属于**正常第二轮新 Finding**。若仍从未改变旧基线发现首轮本可推导 blocker，标记 `FIRST_REVIEW_ESCAPE / First-pass Coverage Miss`；**新代码/Requirement/外部事实引入的不记** First-pass Coverage Miss。Escape 不能逐条退给作者，只允许一次 **fresh blind Review Assembly**，Parent 单次 synthesis 为 **consolidated review-correction batch**，**不得递归**多轮 correction。

## 6. Review Convergence Guard

### Net Delivery Convergence

无本轮引入的**同级或更高级** BLOCKING，且 blocker/影响下降或 Acceptance Evidence 增强，才是 `Delivery Convergence`；根因更清楚只算 `Diagnostic Progress`，**不等价**。正常目标是一批 Repair Batch + 一次 delta re-review；安全阀不授权机械跑满。

**连续两轮**无净收敛 → `STOP_REPAIR_LOOP` / **root-cause reanalysis**；同一 blocker **连续两次修复**仍在也先重诊断/repair-plan reset。最多 **3 个 automatic repair rounds** 是 hard ceiling，**不是自动 PASS**，也不是默认流程。

## 7. 结束条件

Review 只有在 Requirement/Acceptance、适用 Coverage Map、高风险调用链、测试充分性、Findings Evidence、新鲜验证和未验证项都已按真实边界处理时完成。没有证据支持“可合并/可发布”就不给该结论；缺事实/测试先由 Agent 有界恢复，只有真实 `OWNER_DECISION / AUTHORIZATION_REQUIRED / REQUIRED_USER_INPUT / CAPABILITY_BLOCKER` 才向上游请求，不把“Reviewer 没审完”本身抛给用户。
