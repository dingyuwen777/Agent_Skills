# 审查执行流程

本 Reference 只定义 Review 执行与收敛；研发规范归 Coding，专业测试方法归 Testing。

## 0. Review Phase State Machine

同一冻结 Review Target 使用以下有界 phase；phase **单调前进**，不能因为 Reviewer 自己漏审就退回无界 Full Review：

```text
FIRST_ASSEMBLY
→ REPAIR_VERIFY
→ ESCAPE_CORRECTION（escape budget=1）
→ REVIEWER_RECOVERY（仅内部、必要时）
→ FINAL
```

- **FIRST_ASSEMBLY**：独立建立 Requirement/Risk、Root Invariant、Coverage Map 与适用的 Material Projection Matrix，完成 single synthesis 后才允许首次发布 Findings。
- **REPAIR_VERIFY**：只核验原 blocking findings、reviewed_head→repair_head diff、直接相邻回归与 Acceptance；不重新扫描未变旧基线。
- **ESCAPE_CORRECTION**：发现 `FIRST_REVIEW_ESCAPE` 时使用，**不得立即发布单条**旧基线新 Finding；先做一次 fresh blind correction assembly，把同根未变旧基线的剩余 material sibling projections 一次关闭，再形成一个 consolidated review-correction batch。每个 frozen target 的 **escape budget=1**。
- **REVIEWER_RECOVERY**：escape budget 用尽后又从未变旧基线出现本可推导 blocker、或 Reviewer 发现自己此前错误宣称 projection closure 时，记内部信号 `REVIEW_PROCESS_FAILURE` 并进入本 phase。它是**内部恢复状态、非终态**：Reviewer 必须说明遗漏原因，重新打开**受影响根机制**而不是全仓，关闭剩余 material projections，撤销/合并冲突内部 draft，并在同一有界 Material Projection Matrix 内完成 single synthesis。若 recovery 证明没有真实 blocker，直接继续 FINAL；若确认仍有 blocker，则只形成**一个 final recovery correction batch**。`review-and-fix` / 已有修复授权下，该 batch 统一交 Coding 修复并只做一次最终 REPAIR_VERIFY 后进入 FINAL；`review-only` 则把同一稳定 batch 作为 FINAL `CHANGES_REQUIRED` / `BLOCKED` 结果交付。**REVIEW_PROCESS_FAILURE 不得作为用户/作者终态**，也不得把“Reviewer 没审完/审漏了”包装成外部 blocker。
- **FINAL**：只输出正常 Review terminal：`NO_FINDINGS_WITHIN_SCOPE`、`NON_BLOCKING_FINDINGS`、`CHANGES_REQUIRED`、`BLOCKED`、`UPSTREAM_DECISION_REQUIRED`、`CAPABILITY_BLOCKED`（项目既有 Router 可使用等价 `CAPABILITY_BLOCKER`）或项目等价状态。真实 blocker 仍存在就给稳定的 CHANGES_REQUIRED，不为“成功 Review”强行制造无阻塞结论；只有真实外部事实、Owner 决策、授权或必要能力缺失才允许相应 blocked terminal。

只有**新 Requirement / 新外部事实 / repair diff 新行为**可以合法建立新 Review baseline。Reviewer recovery 本身不授权第三、第四轮普通 Full Review，也不改变 review-only / review-and-fix 的生产代码修改权限。

## 1. 冻结 Review Target 与事实

开始前恢复而不是猜测：

```text
Review Target / base / reviewed_head
review-only | review-and-test | review-and-fix
Requirement / Acceptance / Contract / Schema / 必须保持不变 / 非目标
AGENTS / Coding required Context / 测试与 CI / 当前授权
```

能从 PR、仓库和正式事实恢复的内容不问用户。先读规则和 Requirement，再读 diff/调用链；PR 描述、作者 checklist、CI Green 都不是需求全集。

## 2. Review Coverage Map

按真实影响面只纳入适用风险域：Requirement、Contract/compatibility、state/lifecycle/error/recovery、concurrency/idempotency/transaction、security/permission、user-visible behavior、test/evidence、build/runtime/docs。docs diff 做 targeted Reverse Documentation Audit：查 `Existing/Machine Owner / Growth / Reverse impact/exit`；需要修文档时 Handoff Docs。每个域最终为 `covered / ruled_out / not_applicable / unknown`；高风险 unknown 先有界恢复事实或验证，不把猜测发布成 Bug。

### Material Projection Matrix

对复合机制先写一个 **Root Invariant**，再只枚举会实质改变当前 **Review terminal / 修复方案 / Acceptance / compatibility** 的 sibling projections；这组投影称为 material projections。状态仍使用 `confirmed / ruled_out / covered_by_evidence / not_applicable / unknown`。

- **material unknown**：若答案不同会改变当前结论、Finding batch 或修法，则必须在发布前继续有界取证、反证或标记真实外部 blocker；不能先把已知一条发给作者。
- 非 material unknown 可以作为剩余风险记录，不为了“理论完备”无界扩审。
- 同一 Root Invariant 的 lifecycle/state、failure/recovery、compatibility/history 与主要 consumer projections 应在同一矩阵中一次关闭，避免只修首个表面投影。

### No-Findings-Drip Gate

首次或 correction batch 对外发布前必须同时具备：

```text
Root Invariant
+ Material Projection Matrix 无会改变结论的 material unknown
+ Coverage / Omission Audit
+ Counterevidence Check
+ blind perspectives（按深度适用）
+ single synthesis
```

在上述条件完成前，任何 Finding 都是**内部 draft**，**禁止发布**给作者、禁止触发 Coding Repair Batch、禁止逐条 request-review。Finding 数量不是目标；目标是当前 Root Invariant 的 material failure surface 在一次 handoff 前闭合。

### First Review Assembly Gate

按 [04_审查深度选择.md](04_审查深度选择.md) 使用固定、非递归 Review Assembly。各视角基于同一冻结 base/head 独立工作，**互相不看 Finding**，只返回内部 draft findings；Parent 只做一次 single synthesis：去重同根问题、按 current revision / source owner / Contract / 可复现 test/probe / 更直接 Evidence 裁决冲突，并关闭 Coverage Map / Material Projection Matrix。**synthesis 后不得递归开启新的 Full Review，也不得先把部分问题发给作者**。

达到 Systemic 条件先 route refresh 到 `执行模式=诊断`，复用 Coding [`22_根因调试.md`](../../coding/references/22_根因调试.md)。按 **Invariant → Lifecycle/state/ownership → Failure Boundary → Projection** 审查；Projection 状态为 `confirmed / ruled_out / covered_by_evidence / not_applicable / unknown`；Findings 前完成 **Omission / Coverage Audit**，保持**机制内完整、任务外有界**。冻结旧基线本可推导却未进入首轮 batch 的 blocker 是 **First-pass Coverage Miss**。

Assembly 通过 No-Findings-Drip Gate 后才按 [02_Findings与严重度.md](02_Findings与严重度.md) 建立稳定 Finding ID；若交给另一作者返修，追加 `治理=多人协作`，进入 Coding Repair Batch。默认一个 blocking Finding batch 对应一次 repair handoff，不逐条 request-review。

## 3. Evidence 与 Testing

先独立判断风险，再看现有测试。对重要项只问：

```text
Requirement/Risk → 哪个 Evidence → 实际运行什么边界 → 断言什么结果 → 仍缺什么
```

测试名、覆盖率或 CI Green 不是充分证据。review-only 可运行已有非破坏性 targeted validation；需要新增/系统测试时 Handoff Testing。Testing 证明生产缺陷后返回 Coding，不让 Review/Testing 变成生产修复 Owner。

## 4. 三种模式

- **review-only**：只报告，不修改。
- **review-and-test**：Review 定 Test Gap → Testing 最小充分验证 → Review 复核 Evidence。
- **review-and-fix**：Finding 确认 → Coding 按当前规则修复并取得新鲜 Green → Testing Regression（适用）→ Second-pass Repair Verification。

### Finding Classification 与 Repair Scheduling Owner

**Reviewer owns Finding classification；Parent owns repair scheduling。** Reviewer 判 Evidence/severity/Scope/Delivery Effect/Action；Parent 只调度已确认的 repair。Parent **不得单方**降级 blocker、改 Scope 或关闭 Finding；Reviewer 不直接派 Worker。

## 5. Second-pass Repair Verification

作者完成统一 Repair Batch 后冻结 `repair_head`，以 `reviewed_head → repair_head` 的 **repair diff（本轮新 diff）**为主，只审**原 blocking findings / repair diff / 直接相邻回归 / Acceptance Criteria**；未改变旧基线不得重开为**无限范围** Full Review。逐 Finding ID 核验 closure 与 Evidence。

只有 repair diff 新引入行为/回归、**新 Requirement**、**新外部事实**属于**正常第二轮新 Finding**。若仍从**未改变的旧基线**发现首轮本可推导 blocker，标记 `FIRST_REVIEW_ESCAPE / First-pass Coverage Miss` 并进入 **ESCAPE_CORRECTION**；**新代码/Requirement/外部事实引入的不记** First-pass Coverage Miss。

ESCAPE_CORRECTION **不得立即发布单条** Finding：先以同一 Root Invariant 做一次 **fresh blind Review Assembly**，重建 Material Projection Matrix，把未变旧基线的剩余 material sibling projections 统一关闭，再由 Parent single synthesis 形成一个 **consolidated review-correction batch**。该 frozen target 的 **escape budget=1**，不得递归多轮 correction。

如果 escape budget 已用尽后又出现未变旧基线本可推导 blocker，不再创建第二个 escape batch，也不把它直接退给作者；标记内部 `REVIEW_PROCESS_FAILURE`，进入 **REVIEWER_RECOVERY**，按第 0 节完成遗漏原因分析、剩余 material projections closure 与 single synthesis，再输出普通 FINAL terminal。

## 6. Review Convergence Guard

### Net Delivery Convergence

无本轮引入的**同级或更高级** BLOCKING，且 blocker/影响下降或 Acceptance Evidence 增强，才是 `Delivery Convergence`；根因更清楚只算 `Diagnostic Progress`，**不等价**。正常目标是一批 Repair Batch + 一次 delta re-review；安全阀不授权机械跑满。

**连续两轮**无净收敛 → `STOP_REPAIR_LOOP` / **root-cause reanalysis**；同一 blocker **连续两次修复**仍在也先重诊断/repair-plan reset。最多 **3 个 automatic repair rounds** 是 hard ceiling，**不是自动 PASS**，也不是默认流程。

## 7. 结束条件

Review 只有在 Requirement/Acceptance、适用 Coverage Map、高风险调用链、测试充分性、Findings Evidence、新鲜验证和未验证项都已按真实边界处理时完成。没有证据支持“可合并/可发布”就不给该结论；缺事实/测试先由 Agent 有界恢复，只有真实 `OWNER_DECISION / AUTHORIZATION_REQUIRED / REQUIRED_USER_INPUT / CAPABILITY_BLOCKER` 才向上游请求，不把“Reviewer 没审完”本身抛给用户。
