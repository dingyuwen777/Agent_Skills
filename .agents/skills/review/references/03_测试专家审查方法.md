# 测试充分性与 Evidence 审查

Review 的测试职责是**独立判断测试是否足以支持当前结论**，不是再维护一套 Test Strategy / Black-box / Integration / Exploratory 方法。

同仓存在 [`.agents/skills/testing/SKILL.md`](../../testing/SKILL.md) 时：

- Testing 是测试工程方法、测试设计与系统性测试执行的唯一专业 Owner；
- Review 负责从 Requirement/Risk 反查已有测试实际证明了什么、缺什么；
- 需要新增测试、User Journey、黑盒/探索式测试、复杂 Integration/Golden Path/Probe 或 Regression 设计时，Handoff 到 Testing；
- Testing 返回 Evidence 后，Review 再独立判断该证据是否足以支持 merge/release/交付结论。

同仓没有 Testing Skill 时，Review 可以基于项目已有测试体系做测试充分性审计并运行已有非破坏性验证，但不得凭空发明不存在的测试制度。

## 1. 先从 Requirement / Risk 审证据

Review 不先问“有几个测试”，而是问：

```text
Requirement / Risk
→ Expected observable behavior
→ Existing evidence
→ Evidence actually exercised
→ Evidence boundary
→ Gap
→ 是否阻塞当前结论
```

先独立列出当前功能真实适用的风险，再读作者测试结果，避免“CI 全绿”造成确认偏差。

常见审查维度仍包括：

```text
正常路径
输入边界 / 空值
非法输入
错误与异常传播
状态转换
重试 / 取消 / 恢复
并发 / 幂等 / 事务
缓存 / 刷新 / 顺序
兼容性
用户可见反馈
权限 / 安全
构建 / 启动 / 打包
外部依赖事实
```

只保留当前项目真实适用的项。

## 2. 测试绿色不等于覆盖充分

`测试绿色` 只能证明实际运行与断言的范围没有失败。它不能自动证明：

- 没写测试的行为正确；
- Mock 与真实依赖一致；
- 数据库事务真的工作；
- UI 与真实 API 已接通；
- 一条成功链覆盖所有错误状态；
- 外部 Provider 当前在线；
- public Contract 没有漂移；
- package/build/runtime 可用。

Review 必须把“测试结果”和“测试充分性”分开判断。

## 3. 证据层审查

当项目真实存在对应边界时，Review 检查各层是否只声明自己真正证明的事实：

```text
Behavior / Unit / Component
Contract / Consumer
Integration / Persistence / Runtime Dependency
User / Workflow Acceptance
Real Cross-component Golden Path
External Dependency Probe
Build / Package / Runtime
```

具体如何设计和执行这些测试，以 Testing Skill 当前 canonical rules 为准；Review 不复制第二套方法。

固定反例：

- Browser Mock 不能证明真实 Backend/DB/Worker/Provider；
- Fake/SQLite 不能冒充任务真正依赖的 Runtime/Persistence；
- 一条 Golden Path 不能证明全部状态空间；
- External Probe 不能替代稳定回归测试；
- Unit 不能自动证明 public consumer/package/install；
- CI 绿色不能替代 Requirement Completeness。

## 4. 用户/调用者场景充分性

对用户可见 L2/L3 Feature/Bug，如果存在公开入口，Review 必须检查是否有与风险匹配的用户/调用者 Workflow Evidence；没有明确不适用依据时，只有内部 Unit 往往不足以证明用户真的能完成目标。

Review 应从结果反向问：

```text
真实用户/调用者入口是什么？
关键 Journey 是否可完成？
成功、失败、空状态、重试/恢复中的哪些是当前 Requirement？
现有测试是否真的运行了该入口？
是否只测了内部 helper 或手写 Mock？
```

需要新增 Scenario-based Black-box Acceptance 或 Exploratory Testing 时，Handoff Testing，不在 Review Reference 内重复其场景设计规则。

## 5. 项目形态保持条件化

Review 不把 Web/PostgreSQL 术语强加到其他项目：

- Web/Full-stack：检查 Browser/UI、Backend/API/Persistence、Contract、Golden Path 的证据边界；
- Backend/API：没有 UI 时不机械要求 Browser；
- Library/SDK：关注 public API/ABI、consumer、serialization/compatibility、package/install；
- CLI：关注真实 command/flag/stdin、stdout/stderr、exit code、filesystem/process/environment；
- Data/ETL/ML：关注输入 Schema、transform、data quality、checkpoint/idempotency、batch rerun、artifact reproducibility；
- Mobile/Desktop：关注 View/State、simulator/device、permission/storage/network、build/package；
- Infra/IaC/Release：区分 lint/validate、plan/diff/dry-run、artifact/build、真实 apply/deploy。

项目实际不使用 PostgreSQL 时，不机械要求 PostgreSQL；项目没有外部 Provider 时，不机械要求 Real Provider Probe。

## 6. Review-and-test 的 Handoff

`review-and-test` 不再表示 Review 自己拥有完整测试工程方法，而表示：

```text
Review 识别 Test Gap
→ Handoff Testing
→ Testing 在授权范围设计/新增/执行最小充分测试
→ Testing 返回 Evidence / Defect
→ Review 复核 Evidence
```

如果 Testing 证明生产实现有缺陷：

```text
Testing failure evidence
→ Coding 修复
→ Testing Regression
→ Review re-review
```

Review 不越权直接维护生产修复流程。

## 7. 输出测试充分性结论

推荐精确表述：

```text
现有 Workflow Acceptance 覆盖了 X/Y 用户状态；真实 Persistence 未运行，因此仍未验证。
Contract drift check 在当前 HEAD 通过。
一条真实跨组件 Golden Path 通过；错误状态广度仍只由可控层覆盖。
缺少用户入口黑盒证据，该缺口会阻塞当前 L2 功能的完成结论。
```

不要笼统写：

```text
E2E 全通过
测试很充分
系统已完整验证
```

除非当前证据确实支持这些更强结论。
