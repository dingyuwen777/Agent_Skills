# 测试专家审查方法

Review 的测试职责不是把已有测试再跑一遍，而是从需求和失败风险判断**当前证据是否足以支持当前结论**。同仓存在 Coding 时，Validation Matrix 与分层定义以 Coding 当前 references 为准。

## 1. 从行为和风险推导测试

先独立列可观察行为：正常路径、输入边界、非法输入、错误传播、状态转换、重试/取消/恢复、并发/幂等/事务、缓存/顺序、兼容、安全、用户反馈、资源生命周期/性能、build/package/startup、外部依赖事实。只保留真实适用项。

然后问：错误先被谁观察、发生在哪层、什么最小测试能稳定制造失败、现有测试是否真的运行那层。

## 2. 测试绿色不等于覆盖充分

绿色不能自动证明未测试行为、Mock 与真实依赖、真实 persistence 事务、UI 与真实 API 接线、一条成功链覆盖所有错误、外部 Provider 在线或 public Contract 无漂移。

## 3. Test Gap Matrix

```text
Requirement / Risk
→ Expected observable behavior
→ Existing evidence
→ Evidence boundary
→ Gap
→ Smallest useful next test
```

这是审查思路，不要求项目创建固定文档。

## 4. Web/UI/API/Persistence 等专项边界

### UI / Client Mock Acceptance

广覆盖用户可见行为、状态、请求语义。检查关键 action、loading/empty/success/failure/retry/cancel、资格、请求字段、错误、刷新/轮询、Mock 是否来自正式 Contract。不能冒充真实 Backend/Persistence/Worker/Provider。

### Backend / API / Persistence Integration

检查真实服务规则和真实 persistence/runtime：status/error Contract、事务/约束、幂等/锁/并发、异步状态机、查询/分页和持久化结果。项目实际使用什么 persistence 就验证什么，不机械要求某个数据库。

### Contract / Generated Consumer

检查生产者和 consumer 是否共享同一机器 Contract，防止 Mock 字段与真实接口分叉。Contract 测试不代替业务行为测试。

### Real Cross-component Golden Path

只要求足够证明关键真实接线的少量路径：真实入口 → 真实关键组件 → 真实 persistence/runtime → 最终 user/consumer 结果。不要复制全部 Mock 状态。

### External Dependency / Provider Probe

只有当前变更依赖外部现时字段、协议、费用、权限、硬件行为时考虑；检查授权、有界、Secret、外部失败分类和稳定 Fixture/Fake 回归。

## 5. 其他项目形态

Library/SDK：public API/ABI、consumer compile/invoke、serialization compatibility、package/install smoke。

CLI：command/flag/stdin、stdout/stderr、exit code、filesystem/process/environment、副作用、安装后真实命令。

Data/ETL/ML：input schema、deterministic transform、data quality、checkpoint/idempotency、重跑、artifact/version reproducibility。

Mobile/Desktop：View/State、simulator/device、permission/storage/network、build/package/signing。

Embedded：host unit、simulator、target/HIL 分别证明不同边界。

IaC/Release：lint/validate、plan/diff/dry-run、artifact/build、真实 apply/deploy 是不同证据等级。

## 6. 最小新增测试

有 `review-and-test` 授权时：选择能稳定复现 Finding 的最低成本层；断言可观察行为；只 Mock 当前层不负责证明的外部边界；命名描述业务行为/失败条件；Bug 测试能证明修复前失败/修复后通过；不引入与现有体系重复的新框架。

## 7. Fixture 与测试数据

检查 perfect-only data、null/empty/large/boundary、Fixture 是否符合当前 Contract、时间/排序/分页/ID/枚举边界、并发是否真的并发、Mock 是否过度宽松。

## 8. 测试可维护性

测试应稳定复现业务行为、少依赖实现细节、失败可定位、不依赖未控制网络/随机时间、不要求关闭真实安全/数据约束、不用 sleep 隐藏竞态、不把 Snapshot 更新作为默认修复。

## 9. 输出措辞

精确说明哪层通过、哪层未运行、哪些事实因此仍未验证。不要笼统写“E2E 全通过”“测试很充分”“系统已完整验证”，除非实际证据确实支持。
