# 方案比较与阶段化决策

## 先闭环再最小化

方案设计的顺序是：

```text
当前真实问题与约束
→ 判断现有因果 / 根因深度是否足以决定方案
→ 确定稳定解决问题的必要解决条件
→ 在这些条件内最小化复杂度、副作用和交付成本
→ 验证真实问题被解决
```

如果根因或关键机制尚未确认，而且不同原因会导向不同修法，就先回到因果/根因分析；可以同时给止血方案和验证路径，但不要先把某个永久方案当成既定答案。

## 必要解决条件

在比较“哪个方案更小”之前，先写清本次方案必须满足什么。只保留会改变决定的真实条件，例如：

- 真实目标和成功标准；
- 已确认根因或必须被切断的关键机制；
- correctness / 数据 / 安全 / 权限 / 兼容等硬约束；
- 会造成同一问题复发的主要已知边界；
- 能直接证明问题解决的验证方式。

这些条件不满足时，方案再小也不叫“最小充分”。

## 最小充分不是最小改动

**最小充分**是在全部必要解决条件满足后，选择机制最少、复杂度最低、副作用最小、维护成本合理且可验证的方案。

不要用下面这些代理指标定义“最小”：

- 修改**文件数**最少；
- 新增/删除**代码量**最少；
- 实施**步骤数**最少；
- diff 最短；
- 当下看起来最快。

一个一行补丁如果只隐藏症状，就不是充分方案；一个跨多个文件的修复如果这些边界共同组成真实根因链，也可能才是当前最小充分方案。

## 先确定必须优化什么

只比较会改变决定的真实维度：目标满足、正确性、根因/机制覆盖、实施成本/时间、团队实际能力、可靠性/安全/数据风险、可逆性、兼容/迁移、运维维护和可验证性。不要固定制造十几个维度或无数据打分。

## 默认阶段

- **止血 / 缓解**：只在当前风险需要立即控制时先做；必须明确它不等于永久解决。
- **当下方案**：现在需要做、能够稳定解决当前真实问题的最小充分改变。
- **后续演进**：只有负载、团队、产品阶段或约束达到明确条件时再增加。
- **理想方案**：只在帮助今天的边界设计或避免死路时展开。

后两项没有当前决策价值就省略；没有止血需要时也不机械增加一层。

## Trade-off 与推荐

写真实可验证取舍，不写“灵活性 8/10”这类伪精确评分。最终推荐明确：

- 为什么它满足当前必要解决条件；
- 现在做什么、什么不做；
- 它是止血、阶段修复还是永久修复；
- 什么条件出现后重评；
- 如何验证症状、关键机制和主要复发风险。

方向取决于尚未决定的业务/安全/数据硬条件时，再提请用户决定。
