# 后端服务实施与运行边界

本 Reference 是 Coding 内部的 **Service / Backend / API / Persistence 实施 profile**。它只在 Coding 已经因真实开发、诊断、方案、验证或交付意图命中后，根据后端项目形态/范围细化实现责任；不能凭“项目是后端”“范围有 API/持久化”单独把 Coding 拉入 Testing-only、Docs-only 等任务。

目标是让服务端改动沿真实生产边界实现，而不是把所有项目强行套成 Controller / Service / Repository 或某一种数据库架构。

## 1. 先恢复真实服务端入口

按当前仓库确认：

```text
公共入口：HTTP / RPC / message / command / job / library call
→ validation / auth / domain rule
→ side effect / persistence / external dependency
→ async worker / scheduler（存在时）
→ read model / response / event / artifact
```

同时确认：

- 路由/handler/consumer/command 的真实 Owner；
- request/response/event/file/schema 等正式 Contract；
- 数据写 Owner、transaction boundary、幂等/并发机制；
- timeout/retry/cancel/backpressure 等真实 Runtime 机制；
- process/container/runtime 的启动、关闭与资源生命周期；
- 当前日志、metric、trace/correlation、health/readiness 机制；
- 当前测试、CI、Migration、部署和回滚入口。

仓库没有某一层时不制造它；不能因为示例提到数据库、queue、worker 就假设项目拥有这些组件。

## 2. API 与服务端校验

存在 public API/RPC/command/event boundary 时：

- 生产者和消费者必须遵守当前正式 Contract；
- 前端或客户端校验不能替代服务端已有的安全、授权、完整性和业务校验；
- status/error code、错误结构、分页、排序、过滤、时间、时区、单位、空值、默认值、枚举和兼容语义保持一致；
- 破坏性变化先处理版本、兼容窗口、Migration/部署顺序和回滚；
- 不从测试、脚本或临时入口绕过正式业务边界直接改内部状态来“证明”功能可用。

公共 Contract/Schema/Migration 改动继续由 [06_仓库边界数据交换与条件式约束.md](06_仓库边界数据交换与条件式约束.md) 负责完整兼容与 Owner 治理；本文件不复制第二套 Contract 规则。

## 3. Transaction、原子性与数据 Owner

只有当前实现真实依赖 Persistence 时才应用：

- transaction boundary 以业务不变量和失败恢复为单位，不按函数/文件机械划分；
- 一个操作要求“要么全部成功、要么全部失败”时，不能把关键写入拆成无法恢复的半成功状态；
- 数据唯一性、外键、检查约束、版本/fencing、乐观/悲观锁等只在项目真实存在时遵守；
- current/history/cache/index/materialized view 等派生状态不能静默变成第二写 Owner；
- Migration、backfill、双写/双读、兼容窗口和 rollback 只在真实数据变化时启用，并与读写双方一起验证。

不要用“先 catch 再忽略”“失败后继续返回成功”等方式掩盖部分写入或破坏不变量。

## 4. 幂等、并发与重复请求

只在任务存在重复执行、并发竞争或 at-least-once 语义时处理：

- 先定义业务幂等键/资源身份和允许的重复结果；
- 并发保护应落在真正共享状态的边界，不能只依赖单进程内锁去保护跨进程/跨实例数据；
- race、lock、lease、fencing、compare-and-swap、unique constraint 等机制按当前存储/Runtime 事实选择；
- retry 必须知道哪些副作用已发生，避免重试把一次操作放大成多次扣费、写入、发送或创建；
- 并发正确性必须由实际并发或能直接证明对应原语的证据支持，不能把顺序测试命名成 concurrent 就当作已验证。

没有并发风险时不为形式增加锁、队列或分布式协调。

## 5. Async Job / Worker / Retry / Timeout

项目存在后台任务、queue、scheduler、worker 或长任务时：

- 明确提交入口、任务身份、状态机、终态、失败/取消/重试语义；
- timeout 属于调用方预算，不等于下游动作一定停止；需要取消时确认真实 cancellation contract；
- retry 只针对可重试失败并设置边界，区分业务永久失败、权限/参数错误、外部临时故障和本地资源不足；
- backoff/jitter/dead-letter/backpressure 只有在项目现有机制或风险确实需要时启用；
- 状态更新和副作用顺序必须让调用者能区分 queued/running/success/failure/cancelled 等项目真实存在的状态；
- 进程重启、worker 接管或重复投递可能发生时，恢复逻辑与幂等边界一起设计。

不要用任意 `sleep` 代替真实同步、polling 条件或状态机。

## 6. 资源生命周期与优雅关闭

真实持有连接、线程、进程、文件、socket、browser、client、pool、consumer 等资源时：

- owner 明确负责创建、复用、关闭和异常清理；
- 正常退出和异常退出都不能无界泄露资源；
- server shutdown 应停止接收新工作、处理或有界终止进行中工作，并按项目真实能力释放资源；
- signal、context/lifespan、dispose/close、defer/finally 等机制跟随语言/框架事实；
- 不因为测试进程会退出就忽略生产进程长期运行的资源泄露。

## 7. 可观测性与错误边界

复用项目现有 logger/metric/trace/health：

- 记录低频关键生命周期、外部 I/O、retry、partial failure、状态转换和 terminal result；
- 保留 request/job/correlation 等当前项目已有可定位标识；
- 错误既要保留排障上下文，也不能泄露 Secret、Token、敏感 Raw 或 PII；
- 业务错误、依赖错误、环境错误和代码缺陷尽量在边界上分类，不把所有异常压成一个“未知失败”；
- 对用户/消费者的错误 Contract 与内部诊断信息分层，不能把 stack trace 当公共响应。

通用日志格式、安全和宿主边界继续由 Coding Core 与对应现有 Reference 负责。

## 8. Testing / Review / Git Handoff

本 Reference **不拥有**：

- Test Strategy、Black-box/User Journey、Integration/Golden Path/Probe/Regression 的专业测试方法；
- 独立 Code Review、Findings、测试充分性判断；
- Git/PR/CI/Release 的通用交付规则。

这些分别由 Testing、Review 和 Coding 既有 Git/CI/Release Owner 负责。Backend Coding 只需要声明当前实现有哪些独立失败边界必须被证明；专业测试设计/执行通过 Testing 完成，独立合并判断通过 Review 完成。

## 9. 完成前反向检查

按真实边界反查：

```text
public request / event / command
→ validation / auth / domain rule
→ side effect / persistence
→ async runtime（存在时）
→ final state / response / event / artifact
```

确认：

- 调用者发出的真实输入能到达生产 Owner；
- 失败不会留下违反不变量的半成功状态；
- 重试/重复/并发不会制造重复副作用；
- 持久化/异步结果能被真实读路径观察；
- 运行资源可以释放，关键故障可定位；
- required Evidence 已由对应 Owner 实际运行；
- 未验证边界明确列出，不用局部 Unit/Mock 结果冒充真实 Runtime/Persistence/Workflow。
