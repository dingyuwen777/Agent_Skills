# 最小充分治理与升级门禁

这份规则只回答一个问题：**当前任务实际需要启用多少治理，而不是仓库里有哪些治理能力。** Issue、Change、PR、Review、Branch Protection/Ruleset 都是工具；能力存在不等于本次任务必须使用。

核心原则是 **Minimal Sufficient Governance / 最小充分治理**：选择足以控制当前真实风险、协作和审计需要的最小流程；后续发现新事实时再单调升级。不得为了流程完整性机械创建 Issue、Change、PR、Review 阶段、归档记录或额外文档。

每次任务只独立判断四个事实：

```text
技术风险
× Git 交付规则
× 当前协作交接
× 持久追溯价值
→ 本次最小充分治理
```

四个维度不得互相错误推导：

```text
main protected ≠ 多人协作
多人协作 ≠ 必须 Issue
L2 ≠ 必须 Issue
PR ≠ 必须 Issue
Issue ≠ 必须独立 Change
Protected Branch ≠ 必须独立 Change / Deep Review
```

## 1. 风险决定验证深度，不直接决定文档数量

### L1

行为不变的机械修改或影响隔离的小修复，默认只需要：恢复事实 → 最小修改 → 对应回归/验证 → 按真实 Git 规则交付。项目没有要求时，不为形式创建 Issue 或 Change，也不机械进入独立 Review。

### L2

L2 必须把目标、范围/非目标、可观察成功标准、关键不变项、风险和验证入口说清楚，形成**最小充分任务契约**；但这不等于固定创建独立 `CHANGE.md`。

任务契约可由当前已经确认且可供执行/审查的事实承载，例如：

- 本轮用户明确确认的任务事实；
- PR body；
- GitHub/GitLab Issue 或其他工单；
- Spec、OpenSpec、RFC/ADR；
- 项目已有 Change/Proposal/Task 载体。

只有出现跨 Owner、跨 PR、跨会话长期开发、复杂依赖/阶段、正式审计、明确 Completion Gate 或项目规则要求等**持久治理价值**时，才升级为独立持久施工契约。详细格式继续由轻量 Change Reference 负责。

### L3

L3 不因减负降级。public API/ABI/CLI/数据格式、Schema/Migration、跨模块 Contract、认证授权、安全、重大数据/部署/依赖或破坏性兼容变化必须保留稳定 Requirement Source、持久施工契约、兼容/迁移/回滚、深度验证和独立 Review。不能用“流程太重”作为降级理由。

## 2. 当前任务决定协作，不给仓库永久贴标签

“多人协作”表示**当前任务**存在真实跨 Owner / 开发者 / Agent / PR 的交接，例如：

- 用户明确把不同部分交给不同开发者/Agent；
- 当前任务是审查另一个 Owner 提交的 PR；
- 当前存在与本任务相关、由不同 Owner 承担的并行工作单元；
- 同一目标被拆成多个需要协调的 PR/分支。

以下只能作为仓库线索，**不能单独证明**当前任务是多人协作：

```text
Protected Branch
多个 contributors
CODEOWNERS
历史 PR
多个历史分支
```

内部判断可以是 `solo / shared / unknown`，但 **unknown != shared**。未发现明确跨 Owner 事实时按当前单 Owner 的最小流程继续；后续发现交接事实后，再追加 `治理=多人协作` 并进入多人协作 Reference。不能因为“不确定”预先启动全部冲突、Issue 和审查流程。

## 3. Issue Necessity Gate

Issue 是持久需求索引和协作入口，不是开发流程固定前置步骤。

**L2、PR、Protected Branch 均不能单独触发 Issue。** 创建新的 Issue 前先回答：如果不创建，会失去什么真实的协作、审核或长期审计价值？

通常只有以下事实才支持创建/复用持久 Issue：

- 当前存在跨 Owner 交接，后续 Reviewer 需要稳定需求入口；
- 一个需求会拆成多个 PR；
- 任务跨多个会话/周期长期推进；
- 需要独立审核、长期审计或之后恢复“为什么这么改”；
- 用户明确要求建立 Issue；
- 项目规则明确要求 Issue/工单；
- 没有其他稳定 Requirement Source，并且本任务确实需要持久化。

已有可访问的 Spec/OpenSpec/RFC/Figma/Contract/工单等稳定 Requirement Source 时优先复用，不为了制造 GitHub UI 关联再造重复 Issue。需要 Issue 时再使用现有 Issue/PR 追溯 Reference 的搜索、模板和关联规则。

## 4. Branch Protection / Ruleset 只影响 Git 交付

Git 交付前读取目标仓库当前真实 Branch Protection / Ruleset；不能从历史对话或“这是团队仓库”推断。

### 未保护

如果目标分支未保护，且项目规则与用户授权允许直接提交，直接交付可以是合法最小路径：

```text
修改 → 验证 → 必要 Review → commit/push
```

未保护不要求额外补 Issue、PR 或 Change。

### 受保护

如果目标分支受保护，按当前真实规则进入 PR、required checks、review、conversation resolution、up-to-date、merge queue 或其他平台门禁。**受保护也不反向触发 Issue、多人协作、独立 Change 或 Deep Review。**

GitHub 小团队可以从轻量 profile 起步：

```text
Require a pull request before merging
+ Required status checks
+ Block force pushes / deletion
+ require conversation resolution
```

`required approvals`、strict up-to-date 和 Merge Queue 根据实际并发与权限模型逐级启用，不为“更规范”一次性全开：

- 并发较低：可使用 loose required checks，并由 Agent 在 merge 前检查 current-base freshness；
- 并发提高：再启用 strict / require branches to be up to date；
- 高流量且平台/套餐支持：再考虑 Merge Queue。

需要 Owner/自动化仍通过 PR 自动合并时，只给**已确认的 actor** 配置最小 bypass，优先 GitHub 的 `For pull requests only` 语义；不得因为 GitHub App 名称相同就假设不同用户拥有独立 actor 身份。真实 merge 安全、`expected_head_sha` 和 main fresh CI 继续由 Git 交付 Reference 负责。

## 5. Review 深度按风险和交接选择

Review 不是固定全量扫描：

- **Quick Review**：L1、小而明确的 diff；检查实际 diff、邻近调用链、明显边界和目标回归。
- **Standard Review**：普通 L2；检查目标/验收、实现边界、错误处理、兼容和测试充分性。
- **Deep Review**：L3，或 public Contract、Schema/Migration、安全/权限/数据风险、重要跨 Owner/多 PR 交付；完整重建上游需求、A1/A2、兼容/迁移/回滚与 current-base/head 证据。

最终 Review 方法、Findings 和测试专家规则仍由 Review Skill 负责。本 Reference 只选择治理深度，不复制第二套 Review 方法。

## 6. 升级，不预付复杂度

任务开始时使用当前事实支持的最小流程。以下事实出现后再升级：

```text
发现 public Contract / Schema / 安全影响 → 升 L3
发现明确跨 Owner 交接 → 加多人协作
发现需要跨 PR/长期持久追踪 → 建立/复用 Requirement Source 或 Issue
发现目标分支受保护 → 进入实际 PR/Ruleset 流程
发现 Review 风险升高 → Standard → Deep
```

治理升级必须说明新增事实；不得用“以后可能用到”预付 Issue、Change、测试层、审批或文档成本。反过来，也不得为了追求轻量而忽略已经真实存在的高风险、项目规则或平台门禁。
