# 需求来源、Issue 与 PR 追溯治理

本规则只负责 Requirement Source / Issue / PR 追溯、Review revision 与漂移 fail-closed；Review、Git merge/CI、Change/Completion 的详细方法由各自 Owner 承担。

```text
上游正式需求
→ Requirement Source（Issue / Spec / RFC / OpenSpec / 项目正式载体）
→ Change / 施工契约
→ PR / MR
→ 独立 Review
→ 当前目标分支 fresh validation
→ merge
```

## 1. Requirement Source 是上游事实，不是作者自证

Requirement Source 必须让另一位协作者无需作者脑内信息即可恢复：为什么改、目标/范围、完成标准、不变项和继续读取的正式事实源。合法来源由项目治理决定，包括正式 Spec/Roadmap/RFC/ADR、Issue/工单、Figma/Design System、public Contract/Schema/Migration/标准；Greenfield 可暂用本轮已确认需求，但进入多人 PR 前应按项目允许方式持久化为团队可访问事实。

硬边界：

- Coding Change 是施工契约，**不能把自己当 Requirement Source**；PR title/body、作者 checklist、测试结果和 **CI 全绿**默认也不是需求全集；
- 历史聊天、个人笔记、本地缓存或其他协作者不可访问的私有上下文不能成为多人 PR 的唯一来源；
- Review **不能从代码反推需求**，也不能因实现看似合理补造目标；
- L2/L3 按 Completion Gate 向上追溯；项目允许无需独立需求载体的纯机械 L1 不为形式强制创建 Issue。

## 2. Issue 作为 Requirement Source

进入多人协作或 PR 交付时，先解析已有正式来源。GitHub 项目只有同时满足以下条件时，才把 Issue 作为新的最小需求索引：

1. 项目**没有更强且已被正式采用的等价需求载体**，或项目本来就规定 Issue 是需求入口；
2. 当前任务属于**需要可追溯协作的 L2/L3**，或项目规则明确要求 Issue；
3. 当前用户/宿主已经授予**创建 Issue 的 GitHub 写授权**。

创建前必须**先搜索**已有事项：唯一且范围/验收明确匹配则复用；**多个候选**且范围、Owner、验收或生命周期有实质歧义时不得静默挑选/合并，先按仓库事实消歧，必要时请求上游取舍；无匹配且有写授权才创建；无写授权则记录“缺少可持久 Requirement Source / 无创建权限”，不能声称已建立关联。Issue 是索引，不复制已有 Spec/OpenAPI/Schema/Figma/Contract 形成第二事实源。

### Issue Title Contract

项目已有更强 Issue 标题规范时优先；否则 GitHub 默认：

```text
[需求] <简洁目标>
[缺陷] <可观察问题>
[技术变更] <工程目标>
```

`[需求]` 写要获得的用户/调用方/系统可观察结果，不用实现文件名替代目标；`[缺陷]` 写当前可观察偏差而非未经验证的根因；`[技术变更]` 写治理、架构、CI、依赖、安全、性能、基础设施等工程目标。**标题不承载状态、优先级、Owner、分支名或重复 Issue 编号**。同一 Requirement 身份持续存在时不因实现方案、PR 拆分或状态变化随意改标题；身份实质变化按项目治理决定更新或新建 Owner。

Agent_Skills 自身 chooser 固定为 `需求` / `缺陷` / `技术变更`，title prefix 固定 `[需求] ` / `[缺陷] ` / `[技术变更] `；其他项目和非 GitHub 平台使用自己的等价格式。

### Issue Acceptance Contract：公共 Contract + 类型 Profile + 平台 Profile

**Acceptance Criteria 是 Requirement Source 的最终完成状态 Owner**。Change 只保存 Traceability / Evidence Ledger，PR/MR 只保存交付关系，任何下游载体都不能创建第二套成功标准。

- Acceptance Criteria 使用稳定 `AC1 / AC2 / ...`；同一 Requirement 保持 AC 标识和语义，不因实现文件、PR 拆分或测试变化重新编号；实质范围变化先更新正式 Owner，再同步下游；
- **Change 不创建第二套需求**：Change 的 R 行必须映射上游 AC 并记录 direct Evidence；
- AC 处置只有 `satisfied / not_applicable / deferred / unresolved`。N/A 要有当前范围事实；deferred 要有**新的正式 Owner**和稳定引用；`partial / unverified` 属于 unresolved；
- 每个 satisfied AC 的 Evidence 必须说明实际证明的对象、行为、条件和 revision/environment；
- 公共字段至少包括 Acceptance Criteria、验证要求、上游事实源；各类型继续保留自己的场景、复现、兼容迁移、风险回滚等专项字段。

#### Evidence Sufficiency Gate

AC 标为 satisfied / 勾选前，必须取得**充分、直接且与该 AC 匹配**的 Evidence：对应**同一对象、行为、条件**，绑定受验 `revision/commit` 和**必要环境**，并说明证据**实际证明了什么**。一条 AC 含多个独立可观察结果时必须覆盖全部结果，否则保持 unresolved。

`CI Green`、测试存在/数量、`PR merge`、Change `done`/archive、作者说明、Review 无 Finding 都只能是辅助生命周期证据；除非其内容直接证明该 AC，否则不能机械满足 Requirement。依赖 post-merge、迁移、部署、真实数据/Provider、视觉或特定环境的 AC 必须取得相应新鲜 Evidence。无法证明充分时**不得勾选**。

直接 Evidence **不等于必须自动化测试**；可按对象使用 Unit、Integration、Workflow/Acceptance、真实运行、Contract 验证、截图/视觉审查或**人工语义审计**。**测试名称**、**测试文件**本身不是 **Requirement Coverage**。

GitHub 用 task list；GitLab/Gitea/Azure DevOps/Jira 等使用项目真实的**等价 Acceptance/Closure 状态**。项目已有更强 Issue/工单模板或需求系统时优先，**不强制复制 Agent_Skills 的 GitHub Issue Form**。

#### UI Profile 与 Agent 行为解耦

**GitHub Form 只是可选 UI Profile**。项目有更强 Issue/Ticket/Title/Closure Owner 就遵守；**没有安装或复制 Agent_Skills GitHub Forms** 时，Agent 在**创建、规范、更新和关闭 Requirement Source**仍执行本节默认 Contract。**落地 Issue Form 不是 Agent 行为 Contract 生效的前置条件**；多仓任务共享 canonical Contract，但**每个仓库继续使用自己的 Requirement/Change/PR 生命周期**，不得把跨仓实现或 Evidence 合并进一个 Change。

#### Issue Creation / Update Live Validation Gate

**创建或实质更新 GitHub Requirement Source** 后必须**重新读取平台上的真实 live Requirement Source**；**未完成这次写后重读**时，**不得把该 Requirement Source 视为 `resolved`**。至少确认真实 Issue 标识/状态/标题、最少充分正文、上游事实源和 Acceptance 都按当前 Owner 写入，不能用表单草稿、API 请求体或写调用成功返回替代 live 事实。

GitHub 默认 Acceptance 状态必须使用可回写 task list，如 **`- [ ] AC1：...`**；普通 `1. 2. 3.` 编号列表、无稳定 AC、PR/Change checklist 或 **comment-only Evidence** 都**不能冒充 Acceptance 状态 Owner**。

发现不合规时，只有有写权限且能**保持原 Requirement 语义**，才可在同一 Owner 按**原有验收顺序**规范化并**再次重新读取**；不得从实现、测试或作者猜测补造新成功标准。**无写权限**、语义不能安全恢复、写失败或**并发漂移**时保持 **`blocked/unresolved`**，不得另造 Requirement。

对**仍 open 且继续作为当前 Requirement Source** 的旧 Issue 同样处理；**已关闭历史 Issue** 默认**不批量迁移**，除非用户或项目正式 Owner 明确发起独立历史审计。

### Issue 类型与最少充分内容契约

项目已有更强 Issue/工单模板、RFC 或需求系统时优先；以下仅作为无冲突默认 Contract。创建 Issue 按**主要变更原因**分类，而不是按前端/后端/数据库等实现层分类：

- **需求 Issue**：**新增或改变用户、调用方或系统可以观察到的能力、行为、流程或完成定义**。至少写问题背景、目标/可观察结果、用户/调用方场景、范围、非目标、验收标准、不变项、上游资料、风险依赖、验证要求；
- **缺陷 Issue**：**当前可观察行为偏离已经确认的期望行为、Contract、设计或稳定语义**。至少写实际行为、确认的期望及依据、影响范围/频率/严重性、环境/版本/关键配置、复现步骤或触发条件、原始证据、回归范围、验收标准、验证要求、上游资料；没有证据时不得为模板完整猜根因；
- **技术变更 Issue**：**主要目标是架构、重构、基础设施、CI、性能、安全、依赖、部署、维护性或工程质量**，而不是新增用户能力。至少写动机/工程约束、当前/目标状态、范围、非目标、兼容与迁移、风险与回滚、验收标准、验证要求、上游 RFC/ADR/Contract/Schema/指标等；涉及 public API、Schema、数据、配置、依赖、运行环境或部署时必须明确兼容/迁移，无影响也要基于检查范围写明。

同一事项含多种性质时，以决定验收标准和主要完成定义的类型为主，并引用关联事项；不能为模板方便揉成不可审查的大 Issue。

required 表示必须显式处理，不要求编造事实；真实为无/N/A/待确认时写明原因。**关键未知项会影响范围**、Contract、数据、兼容、用户行为或验收时，Issue **不能因为表单提交成功就自动被视为 `resolved`**。**模板完整不等于需求已经完整**；范围、验收或上游决定实质变化时更新正式 Owner 并重新检查 Change/PR/测试/Review，不能让旧 AC 静默继续。同一需求载体的分类标签可以修正，但只要 Requirement 身份未变，应保持稳定 Issue/工单标识。

### GitHub Issue Form 只是平台 Profile

GitHub 可用 `.github/ISSUE_TEMPLATE/*.yml` 落地上述字段，Acceptance 示例为：

```text
- [ ] AC1：第一个可独立验收结果
- [ ] AC2：第二个可独立验收结果
```

open Issue 缺稳定 AC 时按 Live Validation Gate 处理。项目已有 Form 则遵守；没有但明确要建立平台门禁时，只有写授权和项目治理允许才落地；blank issue 设置由项目决定。Agent 不得用 API/维护者权限规避内容 Contract。通用 Agent_Skills 自身 Forms 只是 profile/回归样例，不是其他平台必须复制的字面 Contract。**非 GitHub 平台**使用等价 ticket/work item 字段，不要求模仿 GitHub YAML。

## 3. PR 使用稳定 Requirement-Source 关系

项目没有更具体格式时：

```text
Requirement-Source: <项目正式稳定标识>
```

GitHub Issue 可写 `Requirement-Source: #218`；已有 OpenSpec/RFC/ADR/Spec/Roadmap 等更强正式来源时直接引用其稳定标识，**不为了建立追溯关系再创建重复 Issue**。如果现有载体没有团队可稳定引用的标识，应先按项目治理补足可引用入口，而不是由通用 Skill 自创 URI 或复制一份需求正文。一个 PR 确实实现多个独立来源时可重复多行；跨仓或非 GitHub 同样使用项目已有稳定标识，不自创 URI schema。

`Requirement-Source` 表示 PR 为什么存在；`Closes` / `Fixes` / `Resolves` 表示 merge 后整个 Issue 是否应自动关闭：

- **一个 Issue 拆成多个 PR**时，**每个 PR 都可以写同一个 `Requirement-Source`**；
- 需要 post-merge evidence（如目标分支 fresh CI、迁移/部署后验证、Change archive）时不得使用关闭关键字，只保留 Requirement-Source，由 Closure Audit 后关闭；
- 只有不依赖 post-merge evidence 且当前 PR merge 已足以满足整个 Issue 时才可用 closing keyword；
- 不得让多个局部 PR 抢先关闭同一 Issue，也不得用 closing keyword 替代一般需求追溯。

**创建或更新 PR**后先重新读取真实 PR body，确认引用实际写入、对应来源真实可访问、没有复制旧模板/错误编号导致错指、PR 范围与 Requirement Source 匹配，再进入下述 live validation。

### Delivery Live Requirement Source Validation

**创建或更新 PR**、**正式 Review**、**PR Ready / 可合并**判断和 **merge preflight** 都必须**重新读取当前 live Requirement Source**。GitHub Issue 除真实存在外，还必须满足当前 Title、最少充分内容、稳定 AC 与 task-list Acceptance Contract，并与 PR/Review 范围匹配；正文、AC、状态或身份漂移后**旧 `resolved` 结论失效**。仅可按 Live Validation Gate 安全规范化并重读，否则转为 `partial/unavailable` 或 `blocked/unresolved`，停止 Ready、可合并和 merge 强结论。

宿主不能修改 PR/Issue 时只报告缺口和建议内容，不得声称已自动关联。

## 4. 机器门禁与 Agent 语义审查分工

若项目要求“没有需求来源不能 merge”，优先把项目 traceability CI 设为 **Required Status Check** 并由 **Branch Protection / Ruleset** 执行。机器适合验证：PR 是否含 Requirement-Source、标识能否解析、来源是否真实可访问、项目明确要求的最小结构是否存在、检查是否真实执行。机器不能假装理解自然语言完整性、上游语义一致性、PR 是否实现全部 Requirement 或测试是否足以证明完成；这些仍由 Requirement Traceability、Completion Audit 和独立 Review 判断，关键检查不得用 skip 冒充通过。

## 5. PR Review 快照与 Requirement 状态

正式 Review 前记录：PR/MR、base/target、`reviewed_base_sha`、`reviewed_head_sha`、`current_base_sha`、Requirement Source、required checks、授权。随后读取 diff/commits、直接调用链、测试和文档，并沿 Requirement-Source 继续读取 Issue/Spec/Figma/Contract/Schema 等上游事实；不能把 PR description 当替代。

Requirement Source 状态：

- `resolved`：足够重建当前范围目标、成功标准、不变项和关键约束，可继续 A1/A2；
- `partial`：缺少影响范围/接口/数据/兼容/用户行为/验收的关键事实，可继续已知范围的代码质量 Review、风险检查和测试充分性分析，但**不得声明整体需求符合**，缺口必须进入阻塞/未验证项；
- `unavailable`：来源不存在/不可访问/无法确认，可审确定性安全/错误处理/资源泄漏/项目规范问题，但不得猜需求，**不得声明整体需求符合，也不得声明可合并**。

CI 全绿、作者说明或代码看似正确都不能把 partial/unavailable 升为 resolved。

## 6. base/head 漂移与 merge preflight

head 漂移后读取新增 diff/commits、重判受影响需求和风险、重跑 required validation、re-review 原 Findings/相邻风险；不能因“小 commit”沿用旧 Approval。base 漂移时旧结论只证明旧 base + reviewed head，merge 前必须对当前 base + 待合入 revision 取得项目要求的 fresh validation，可使用 strict checks、**merge queue** 或项目自己的 merge-result pipeline；**不强制 rebase**，也不默认某一种 Git 策略最好。

准备给出“可合并”或执行 merge 前重新确认：当前 Delivery Live Requirement Source Validation = resolved、`reviewed_head_sha` 等于当前 PR head、当前 base 已完成所需 fresh validation、required checks 满足、阻塞 Findings 清零、Requirement/Contract/Schema 无未审漂移。任一不成立时只报告缺失证据，不强行推进。GitHub merge 继续遵守 REST merge + expected head guard；base freshness 与 head guard 不能互替。

## 7. Requirement Source 关闭前 Closure Audit

关闭 Issue/工单为 completed/resolved 前，先取得 required post-merge evidence，**重新读取当前 Requirement Source**并**逐条核对**验收标准；**只有实际证据支持**的项才能完成。状态必须**先回写** Requirement Source 再重读。仍有适用的 partial/unverified/unresolved AC 且没有正式 N/A/deferred 处置时，**不得以 completed / resolved 关闭**。

GitHub 标准顺序：

```text
重新读取当前 Requirement Source
→ 逐条 Requirement → Evidence 审计
→ AC → satisfied / not_applicable / deferred / unresolved
→ `- [ ]` → `- [x]`（仅正式处置项，保留 N/A/deferred 依据）
→ 写回 Issue body
→ 重新读取 Issue，确认 AC/状态/Evidence 无漂移且没有仍适用的未勾选项
→ 执行 close
→ 再次读取 Issue，确认 closed/completed 且 Acceptance 状态仍存在
```

- `satisfied`：至少一项**直接 Evidence**证明对应**可观察结果**，核对**对象、行为、条件**、`revision/commit` 和必要环境；
- `not_applicable`：当前范围事实明确证明 N/A，并保留原因；不能把“没做”冒充不适用；
- `deferred`：已有新的正式 Owner 和稳定引用（如 `Deferred → #245`）；否则仍 unresolved；
- `unresolved`：含 partial/unverified/未满足/关键未知；GitHub 保持 `[ ]`，**仍适用的未勾选项不得关闭**。

Closure comment/work-item history 可保存详细 AC→Evidence Mapping，但 **comment-only Evidence 不能代替 Issue body Acceptance 状态**；GitHub body task list 必须真实写回。写后读取发现写失败、正文并发修改、AC 数量/文本漂移或未勾选项即停止；close 后读取不是 closed/completed 只能报告 blocked/incomplete；**无写权限**/写失败不得声称完成；**关闭关键字不得绕过** Closure Audit。

非 GitHub 平台按等价字段/状态执行同一“逐项 Evidence → 状态写回 → 重读 → close → 再读”语义；没有 close 生命周期时至少回写并重读可用 Acceptance 状态，不发明平台能力。

## 8. 多人协作与输出边界

开始时基于最新 main 只是起点，真正硬门禁是 merge 前针对当时最新目标分支验证。Agent 看不到其他 clone 未 push 工作；多人 Change/文件/Contract 冲突仍按协作 Owner 处理。Issue/PR 关联不能替代 Contract Owner；Agent_Skills 不能自行强制平台保护/required reviewers/谁能 merge，平台负责执行，Agent 负责检查并在不满足时停止。只读 Review 不自动获得创建/修改 Issue、修改 PR、closing keyword、提交、merge 或关闭权限。

PR/MR Review/交付至少报告：Requirement Source 状态、`reviewed_base_sha / reviewed_head_sha / current_base_sha`、关键上游事实、A1/A2、Findings、测试充分性、实际 current-head/current-base 验证、未验证项与原因、merge 阻塞依据。没有 Finding 也不能只写 `LGTM`，必须让后续维护者知道审的是哪个需求/base/head 与哪些事实仍未证明。
