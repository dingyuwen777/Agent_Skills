# 需求来源、Issue 与 PR 追溯治理

这份规则处理多人或多 Agent 研发中的一条完整追溯链：

```text
上游正式需求
→ Requirement Source
→ Issue / Spec / RFC / OpenSpec / 其他项目正式载体
→ Change / 施工契约
→ PR / MR
→ 独立 Review
→ 当前目标分支上的新鲜集成验证
→ merge
```

它不重新定义 Review 的 Findings 方法，也不复制 Git merge、CI、Change 或 Completion Audit 的完整规则。Review 方法继续由 Review Skill 负责；Git merge 与 `expected_head_sha`、main fresh CI 继续由 Git 交付 Reference 负责；本文件只负责**需求来源如何解析、Issue 怎样成为清晰可审计的协作入口、PR 如何追溯、Review 如何绑定 revision，以及需求/目标分支漂移时怎样 fail closed**。

## 1. Requirement Source 是上游事实，不是作者自证

Requirement Source 必须能让另一个协作者或 Reviewer 在不依赖作者脑内信息的情况下回答：

```text
为什么要改？
目标和范围是什么？
什么算完成？
哪些行为必须保持不变？
详细事实还要继续读哪里？
```

优先级由目标项目现有治理决定。常见合法来源包括：

- OpenSpec、RFC、ADR、正式 Spec、Roadmap/Stage/Feature 完成定义；
- GitHub/GitLab Issue、工单或项目已经正式采用的需求系统；
- 设计任务中的正式 Figma/Design System 事实入口；
- public Contract、Schema、Migration、标准或其他真正决定验收结果的事实源；
- Greenfield 或尚无长期载体时，本轮用户已确认需求与技术决定，但在进入多人 PR 协作前应按项目允许的方式持久化为团队可访问事实。

硬边界：

- 当前 Coding Change 是施工契约，**不能把自己当 Requirement Source**；
- PR title、PR description、作者 checklist、测试结果和 CI 绿色默认都不是完整需求全集；
- 历史聊天、个人笔记、本地缓存或另一个协作者无法访问的私有上下文不能作为多人 PR 的唯一持久需求来源；
- Review 不能从代码反推需求，也不能因为“实现看起来合理”就补造未确认目标。

L2/L3 仍按当前 Completion Gate 从上游正式事实建立 Requirement Traceability。L1 纯机械变更如果项目明确允许无需独立需求载体，不为了形式强制创建 Issue。

## 2. 开发阶段先解析已有来源，再决定是否建立 Issue

当任务会进入多人协作或 PR 交付时，先做 Requirement Source Resolution：

```text
读取项目 AGENTS / CONTRIBUTING / 现有治理
→ 查找用户请求已经引用的 Issue / Spec / RFC / Change 上游来源
→ 查找当前分支、活动 Change、相关代码或已有 PR 能确认的正式入口
→ 只在真实需要时搜索项目的现有 Issue / 工单
→ 仍无持久来源时，再按项目治理与当前写授权决定是否创建
```

### GitHub Issue 作为需求索引

GitHub 项目只有在以下条件同时满足时，才把 Issue 作为新的最小需求索引：

1. 项目没有更强且已被正式采用的等价需求载体，或项目本来就规定 Issue 是需求入口；
2. 当前任务属于需要可追溯协作的 L2/L3，或项目规则明确要求 Issue；
3. 当前用户/宿主已经授予创建 Issue 的 GitHub 写授权。

创建前必须**先搜索**已有 Issue，避免同一需求产生重复事实源：

- 发现唯一、范围和验收语义都明确匹配的现有 Issue：复用它；
- 发现多个候选且它们在范围、Owner、验收或生命周期上有实质歧义：不得静默挑一个，也不得把多个 Issue 随意合成一个需求；先依据仓库事实消歧，确实需要上游取舍时再请求决定；
- 没有匹配项且已有写授权：创建 Issue；
- 没有写授权：明确记录“缺少可持久 Requirement Source / 无创建权限”，不能声称已经建立关联。

Issue 是**需求索引和协作入口**，不是要求把几千行正式 Spec、OpenAPI、Schema 或 Figma 注释全文复制进去。已有正式事实应引用唯一 Owner，避免形成第二份会漂移的正文。

### Issue 类型与最少充分内容契约

项目已有更强 Issue/工单模板、工单系统、RFC 流程或正式需求表单时，优先遵守项目现有 Owner；Agent Skills 不自动覆盖，也不把下面字段机械追加成第二套模板。只有项目没有更具体约束，或需要补足不冲突的语义缺口时，才使用本节作为默认内容契约。

创建 Issue 时先按**主要变更原因**分类，而不是按前端/后端/数据库等实现层分类：

- **需求 Issue**：新增或改变用户、调用方或系统可以观察到的能力、行为、流程或完成定义；
- **缺陷 Issue**：当前可观察行为偏离已经确认的期望行为、Contract、设计或稳定语义；
- **技术变更 Issue**：主要目标是架构、重构、基础设施、CI、性能、安全、依赖、部署、维护性或工程质量，而不是新增用户能力。

如果同一事项同时包含多种性质，以决定验收标准和主要完成定义的类型为主，并在范围中引用关联事项；不能为了模板方便把多个独立需求、缺陷和技术变更随意揉成一个不可审查的大 Issue。

#### 需求 Issue

至少说明：

```text
问题背景 / 为什么现在需要处理
目标 / 期望的可观察结果
用户、调用方或系统使用场景
范围
非目标
验收标准
必须保持不变
上游事实源 / 相关正式资料
风险与依赖
验证要求
```

验收标准必须能转成 Review 与测试可以判断的观察点；“体验更好”“支持一下”“代码优化”等无法独立判断完成状态的表述不够充分。

#### 缺陷 Issue

至少说明：

```text
实际行为
已经确认的期望行为及其依据
影响范围、频率与严重性
环境 / 版本 / commit / 关键配置
复现步骤；无法稳定复现时说明触发条件、频率和原因
原始证据：日志、错误、截图、trace、请求响应、失败测试或最小样例
回归范围
修复验收标准
上游事实源 / 定义期望行为的资料
```

“已知 / 怀疑根因”是可选信息。没有代码、日志、trace、实验或其他证据时不得为了模板完整而猜根因；Review 和修复仍应通过根因调试独立确认。

#### 技术变更 Issue

至少说明：

```text
动机 / 已知根因或工程约束
当前状态
目标状态
范围
非目标
兼容与迁移
风险与回滚
验收标准
验证计划
上游事实源 / RFC / ADR / Contract / Schema / 指标或事故证据
```

技术变更不能只写“重构”“升级”“优化”。如果涉及 public API、Schema、数据、配置、依赖、运行环境或部署，兼容与迁移必须明确；如果确实无影响，也要基于已检查范围明确写“无”，而不是留给实现者猜测。

### 缺失字段、待确认项和 Issue 漂移

- required 字段要求“必须显式处理”，不要求编造事实；真实情况是无、不适用或暂未确认时，应写 `无`、`不适用` 或 `待确认` 并说明原因和影响；
- 关键未知项会影响范围、Contract、数据、兼容、用户行为或验收时，Issue 不能因为表单提交成功就自动被视为 `resolved`；
- **模板完整不等于需求已经完整**。Issue Form 只能提高结构完整性，不能替代 Requirement Traceability、上游事实重建、A1/A2、独立 Review 或测试证据；
- Issue 范围、验收标准或上游决定发生实质变化时，更新原 Issue / 正式 Owner，并重新检查下游 Change、PR、测试和 Review；不能让旧 acceptance criteria 静默继续充当当前需求；
- 同一需求载体的分类标签可以修正，但只要需求身份未变，应保持稳定 Issue/工单标识，避免仅因分类调整破坏追溯链。

### GitHub Issue Form 只是平台 Profile

采用 GitHub 的项目可以通过 `.github/ISSUE_TEMPLATE/*.yml` 把上述关键字段实现为 Issue Form，并把需要显式处理的字段设为 required。目标项目是否安装、修改或关闭 blank issue，由目标项目当前治理决定：

- 项目已经有自己的 Issue Form / Issue Template：读取并遵守，不自动覆盖；
- 项目没有模板，但明确要求建立 GitHub 协作门禁：在有写授权和 Change/项目治理允许时，才落地项目自己的表单；
- 通用 Agent Skills 源仓库可以维护自己的 GitHub Forms 作为真实 profile 和回归样例，但这些文件不是非 GitHub 平台必须复制的字面 Contract；
- chooser 关闭 blank issue 只是减少普通绕过入口；Agent 不得用 API、维护者权限或其他路径规避项目要求的 Issue 内容契约。

GitLab、Gitea、Azure DevOps、Jira 或其他系统使用等价 ticket/work item 字段即可，不要求模仿 GitHub YAML。

## 3. PR 使用稳定 Requirement-Source 关系

项目没有更具体 PR 追溯格式时，PR 使用人和机器都容易解析的统一关系：

```text
Requirement-Source: <项目正式稳定标识>
```

`<项目正式稳定标识>` 必须来自目标项目已经存在的需求治理事实。例如 GitHub Issue 可以使用：

```text
Requirement-Source: #218
```

如果项目已经采用 OpenSpec、RFC、ADR、正式 Spec、Roadmap 单元或其他比 GitHub Issue 更强的正式载体，就直接使用该项目已经建立的稳定 ID、仓库相对正式路径或项目规则明确的等价标识。**已有更强正式来源时，不为了建立追溯关系再创建重复 Issue。** 如果现有载体没有任何团队可稳定引用的标识，应先按项目治理补足可引用入口，而不是由通用 Skill 自创 URI 或偷偷复制一份需求正文。

一个 PR 确实同时实现多个独立来源时，可以重复同一关系，每行各指向一个真实来源：

```text
Requirement-Source: <项目正式稳定标识A>
Requirement-Source: <项目正式稳定标识B>
```

跨仓库、外部工单或非 GitHub 平台同样使用目标项目已经定义的等价稳定标识，不为了通用 Skill 自创一套与项目冲突的 URI schema。

### `Requirement-Source` 与关闭关键字必须分离

`Requirement-Source` 表达：

> 这个 PR 为什么存在、应按什么需求审查。

`Closes` / `Fixes` / `Resolves` 表达：

> 这个 PR 合并后，整个 Issue 是否已经完成并应自动关闭。

因此：

- 一个 Issue 拆成多个 PR 时，每个 PR 都可以写同一个 `Requirement-Source`；
- 只有当前 PR 的 merge 确实满足整个 Issue 的完成定义时才使用 `Closes #218`、`Fixes #218` 或 `Resolves #218`；
- 不得为了制造 GitHub UI 关联而让多个局部 PR 都提前关闭同一 Issue；
- 不得用关闭关键字替代一般需求追溯语义。

创建或更新 PR 后必须重新读取真实 PR body 和 Requirement Source，确认：

- 引用文本实际写入成功；
- 对应 Issue/Spec/工单真实存在且当前可访问；
- 引用没有因为复制旧模板、错误编号或重建 PR 指向错误需求；
- PR 当前范围与 Requirement Source 没有明显错配。

宿主没有修改 PR/Issue 的写能力时，只能报告缺口和建议内容，不得口头声称“已自动关联”。

## 4. 机器门禁与 Agent 语义审查分工

目标项目希望“没有需求来源就不能 merge”时，优先在其 Branch Protection / Ruleset 中把项目自己的 traceability CI 设为 **Required Status Check**。Agent Skills 只规定责任，不自动给所有项目安装 GitHub Workflow。

机器检查适合验证：

- PR 是否包含项目要求的 `Requirement-Source`；
- 标识是否能解析；
- 被引用 Issue/文件/工单是否真实存在且可访问；
- 项目明确要求的最小结构是否存在，例如目标和验收标准；
- 对同一 PR 的检查是否真实执行并给出确定结果。

机器检查**不应假装理解**：

- 自然语言需求是否完整；
- Issue 与更上游 Spec/Figma/Contract 是否语义一致；
- PR 是否真的实现全部 Requirement；
- 测试是否足以证明业务完成。

这些仍由 Requirement Traceability、Completion Audit 和独立 Agent Review 判断。项目把 traceability job 设为 Required Status Check 时，不能设计成“关键情况下直接 skip 就当通过”；必须遵守该项目对 required check 的真实平台语义并产生可审计结果。

## 5. PR Review 先冻结审查快照

Review Target 是 PR/MR 时，在看 diff 和作者结论之前记录真实快照：

```text
PR / MR 标识
base branch / target branch
reviewed_base_sha
reviewed_head_sha
current_base_sha
Requirement Source 列表
当前 CI / required checks
授权模式
```

语义：

- `reviewed_base_sha`：本轮需求/集成审查所针对的 base revision；
- `reviewed_head_sha`：本轮实际审过的 PR revision；
- `current_base_sha`：审查时目标分支当前最新 revision，用于发现 base 漂移。

随后读取 PR 的 diff/commits、直接调用链、测试和文档，再沿 `Requirement-Source` 继续读取 Issue、Spec、Figma、Contract、Schema 或其他上游事实。不能把 PR description 当作读取上游来源的替代品。

## 6. Requirement Source 状态必须显式

PR Review 对需求来源只使用以下结论语义：

### `resolved`

已经取得足够上游事实，可以独立重建本 PR 当前范围的目标、成功标准、不变项和关键约束。

### `partial`

找到了部分来源，但仍缺少会影响范围、接口、数据、兼容、用户行为或验收结论的关键事实。

### `unavailable`

没有可验证来源，来源已失效/无权限访问，或当前证据无法确认 PR 应实现什么。

处理规则：

- `resolved`：可以继续 A1/A2 需求符合性 Review；
- `partial`：可以继续已知范围的代码质量 Review、风险检查和测试充分性分析，但**不得声明整体需求符合**，缺失部分必须进入阻塞/未验证项；
- `unavailable`：仍可以做不依赖业务意图的代码质量 Review，例如确定性安全缺陷、明显错误处理、资源泄漏或项目明确规范违规，但不得自行猜需求，**不得声明整体需求符合，也不得声明可合并**；
- CI 全绿、作者说明完整或代码“看起来正确”都不能把 `partial/unavailable` 自动升级为 `resolved`。

## 7. base/head 漂移后旧 Review 不能无条件沿用

### head 漂移

如果当前 PR head 与 `reviewed_head_sha` 不同：

```text
新 head
→ 读取新增 diff / commits
→ 重新判断受影响需求和风险
→ 重跑对应 required 验证
→ 对原 Findings 和相邻风险执行 re-review
```

不得因为“只是补了一个小 commit”自动沿用旧 Approval。

### base 漂移

如果目标分支当前 HEAD 与 `reviewed_base_sha` 不同，即使 PR head 一行没改，旧结论证明的仍是：

```text
旧 base + reviewed head
```

而不是：

```text
当前 base + reviewed head
```

因此 merge 前必须针对当前目标分支状态重新取得项目要求的集成证据，并按变化风险决定 re-review 范围。可能的项目机制包括：

- Branch Protection / Ruleset 的 branch up-to-date / strict status checks；
- merge queue 对候选 merge result 的验证；
- 项目自己的 merge-result pipeline 或等价 revision validation。

**不强制 rebase**，也不默认 merge commit、rebase 或 merge queue 中任一种策略一定最好；使用目标项目真实配置。要求的是“当前 base + 待合入 revision”得到新鲜证据，而不是某条固定 Git 命令。

GitHub 真正 merge 时继续遵守 Git 交付规则中的 REST merge + `expected_head_sha`；head guard 不能替代 base freshness，base freshness 也不能替代 head guard。

## 8. Merge 前重新确认追溯链

准备给出“可合并”结论或执行 merge 前，再次确认：

```text
Requirement Source = resolved
reviewed_head_sha = current PR head
当前 base 已按项目机制完成所需 fresh validation
required CI/checks 满足当前仓库规则
阻塞 Findings 已清理
Requirement / Contract / Schema 没有在 Review 后发生未审查漂移
```

任一项不成立时只报告当前状态和缺失证据，不强行推进。

## 9. Requirement Source 关闭前 Closure Audit

当 Issue/工单是 Requirement Source，且 Agent 获授权将其关闭为 `completed` / `resolved` 时，按项目真实完成顺序先取得必要的 merge 后 fresh CI、Migration、Change archive 等最终证据，再执行：

```text
重新读取当前 Requirement Source
→ Closure Audit 逐条核对当前验收标准与最终证据
→ 回写真实完成状态并重读确认
→ completed / resolved closure
```

- **只有实际证据支持**的要求才允许标完成；Markdown checklist 只把已满足项从 `[ ]` 改为 `[x]`。`CI 全绿`、PR merge 或 Change checklist 不能自动批量证明自然语言验收项。
- 未满足、未验证且无正式批准延期的适用要求，**不得以 completed / resolved 关闭**；正式延期/不适用按项目已有状态模型和依据记录，不伪装成已实现。
- 有写权限时**先回写** Requirement Source、重读确认，再关闭；**无写权限**或写入失败时报告未同步，不得声称已完成关闭闭环。
- **关闭关键字不得绕过** Closure Audit。若完整完成定义依赖 post-merge evidence，则实现 PR 合并前不得用 `Closes` / `Fixes` / `Resolves` 提前关闭；若 merge 前已能证明全部完成且无后置条件，才按项目规则使用。
- **非 GitHub 平台**使用真实 ticket/work item 的等价验收字段与状态，不强制 Markdown checkbox；没有关闭生命周期的 Spec/RFC 只重新读取核对，不发明 close 动作。
- 不要求为本规则批量改写历史已关闭来源；只有当前交付闭环或用户明确要求时才有界同步。

## 10. 多人协作中的实际边界

- “开发开始时基于最新 main”只能作为良好起点，不是长期保证；真正硬门禁是 merge 前针对**当时最新目标分支**重新验证。
- Agent 看不到其他克隆未 push 的工作；多人 Change/文件/Contract 冲突继续按多人协作 Reference 处理。
- Issue/PR 关联不能替代 Contract Owner。前后端、Schema、Migration 或 public API 冲突仍以项目正式 Contract/Owner 为准。
- Agent Skills 不能自己强制 Branch Protection、Ruleset、required reviewers 或谁能 merge；这些由目标仓库平台配置执行，Agent 负责检查并在不满足时停止。
- 只读 Review 不自动获得创建 Issue、修改 PR、添加 closing keyword、提交、merge 或关闭 Issue 的权限。

## 11. 非 GitHub 平台保持等价语义

GitLab、Gitea、Azure DevOps 或其他平台不需要模仿 GitHub 字面字段，但应保持同等责任：

```text
持久 Requirement Source
→ ticket/spec 与 MR 的稳定追溯
→ reviewed base revision + reviewed head revision
→ 当前 target revision 的 fresh integration validation
→ revision guard
→ merge 后项目要求的新鲜验证
```

平台没有原生 Issue、closing keyword、merge queue 或 required status check 时，不发明不存在的功能；使用项目真实的等价机制并明确未覆盖边界。

## 12. Review / 交付输出至少说明

PR/MR 场景至少报告：

```text
Requirement Source 及状态：resolved / partial / unavailable
reviewed_base_sha / reviewed_head_sha / current_base_sha
读取的关键上游事实源
需求符合性 A1/A2 结论
代码质量与测试充分性 Findings
实际执行的 current-head / current-base 验证
未验证项与原因
是否阻塞 merge，以及阻塞依据
```

没有 Finding 时也不能只写 `LGTM`。必须让后续维护者知道“审的是哪个需求、哪个 base、哪个 head，以及哪些事实仍没有被证明”。
