# 需求来源、Issue 与 PR 追溯治理

本规则只负责 Requirement Source / Issue / PR 追溯、Review revision 与漂移 fail-closed；Review、Git merge/CI、Change/Completion 的详细方法由各自 Owner 承担。

```text
上游正式需求
→ Requirement Source（Issue / Spec / RFC / OpenSpec / 项目正式载体）
→ Change / 施工契约
→ PR / MR
→ 独立 Review
→ 当前目标分支 fresh validation
→ merge
```

## 1. Requirement Source 是上游事实，不是作者自证

Requirement Source 必须让另一位协作者无需作者脑内信息即可恢复：为什么改、目标/范围、完成标准、不变项和继续读取的正式事实源。合法来源由项目治理决定，包括正式 Spec/Roadmap/RFC/ADR、Issue/工单、Figma/Design System、public Contract/Schema/Migration/标准；Greenfield 可暂用本轮已确认需求，但进入多人 PR 前应按项目允许方式持久化。

硬边界：

- Coding Change 是施工契约，**不能把自己当 Requirement Source**；PR title/body、作者 checklist、测试结果和 **CI 全绿**默认也不是需求全集；
- 历史聊天、个人笔记、本地缓存或其他协作者不可访问的私有上下文不能成为多人 PR 的唯一来源；
- Review **不能从代码反推需求**，也不能因实现看似合理补造目标；
- L2/L3 按 Completion Gate 向上追溯；项目允许无需独立需求载体的纯机械 L1 不为形式强制创建 Issue。

## 2. Issue 作为 Requirement Source

进入多人协作或 PR 交付时，先解析已有正式来源；需要 Issue 时必须**先搜索**已有事项：唯一且语义匹配则复用；**多个候选**且范围/Owner/验收有歧义时先消歧；无匹配且有**写授权**才**创建 Issue**；无写授权则记录缺口，不能声称已建立关联。Issue 是索引，不复制已有 Spec/Contract 形成第二事实源。

### Issue Title Contract

项目已有更强 Issue 标题规范时优先；否则 GitHub 默认：

```text
[需求] <简洁目标>
[缺陷] <可观察问题>
[技术变更] <工程目标>
```

`[需求]` 写可观察目标；`[缺陷]` 写已观察偏差而非猜测根因；`[技术变更]` 写架构/CI/性能/安全/维护等工程目标。**标题不承载状态、优先级、Owner、分支名或重复 Issue 编号**。同一 Requirement 身份存在时保持稳定标题语义；身份实质变化再按项目治理决定更新或新建 Owner。

Agent_Skills 自身 chooser 固定为 `需求` / `缺陷` / `技术变更`，title prefix 固定 `[需求] ` / `[缺陷] ` / `[技术变更] `；其他项目和非 GitHub 平台使用自己的等价格式。

### Issue Acceptance Contract：公共 Contract + 类型 Profile + 平台 Profile

**Acceptance Criteria 是 Requirement Source 的最终完成状态 Owner**。Change 只保存 Traceability / Evidence Ledger，PR/MR 只保存交付关系，任何下游载体都不能创建第二套成功标准。

- Acceptance Criteria 使用稳定 `AC1 / AC2 / ...`；同一 Requirement 保持 AC 标识和语义，实质范围变化先更新正式 Owner，再同步下游；
- **Change 不创建第二套需求**：Change 的 R 行必须映射上游 AC 并记录 direct Evidence；
- AC 处置只有 `satisfied / not_applicable / deferred / unresolved`。N/A 要有范围事实；deferred 要有**新的正式 Owner**；`partial / unverified` 属于 unresolved；
- 公共字段至少包括 Acceptance Criteria、验证要求、上游事实源；各类型继续保留自己的场景、复现、兼容迁移、风险回滚等专项字段。

#### Evidence Sufficiency Gate

AC 标为 satisfied / 勾选前，必须取得**充分、直接且与该 AC 匹配**的 Evidence：对应**同一对象、行为、条件**，绑定受验 `revision/commit` 和**必要环境**，并说明证据**实际证明了什么**。一条 AC 含多个独立结果时必须覆盖全部结果，否则保持 unresolved。

`CI Green`、测试存在/数量、`PR merge`、Change `done`/archive、作者说明、Review 无 Finding 都只能是辅助生命周期证据；除非其内容直接证明该 AC，否则不能机械满足 Requirement。依赖 post-merge、迁移、部署、真实数据/Provider、视觉或特定环境的 AC 必须取得相应新鲜 Evidence。无法证明充分时**不得勾选**。

直接 Evidence **不等于必须自动化测试**；可按对象使用 Unit、Integration、Workflow/Acceptance、真实运行、Contract 验证、截图/视觉审查或**人工语义审计**。**测试名称**、**测试文件**本身不是 **Requirement Coverage**。

GitHub 用 task list；GitLab/Gitea/Azure DevOps/Jira 等使用项目真实的**等价 Acceptance/Closure 状态**。项目已有更强 Issue/工单模板或需求系统时优先，**不强制复制 Agent_Skills 的 GitHub Issue Form**。

#### UI Profile 与 Agent 行为解耦

**GitHub Form 只是可选 UI Profile**。项目有更强 Issue/Ticket/Title/Closure Owner 就遵守；**没有安装或复制 Agent_Skills GitHub Forms** 时，Agent 在**创建、规范、更新和关闭 Requirement Source**仍执行本节默认 Contract。**落地 Issue Form 不是 Agent 行为 Contract 生效的前置条件**；多仓任务共享 canonical Contract，但**每个仓库继续使用自己的 Requirement/Change/PR 生命周期**。

#### Issue Creation / Update Live Validation Gate

**创建或实质更新 GitHub Requirement Source** 后必须**重新读取平台上的真实 live Requirement Source**；**未完成这次写后重读**时，**不得把该 Requirement Source 视为 `resolved`**。GitHub 默认 Acceptance 状态必须使用可回写 task list，如 **`- [ ] AC1：...`**；普通 `1. 2. 3.` 编号列表、无稳定 AC、PR/Change checklist 或 **comment-only Evidence** 都**不能冒充 Acceptance 状态 Owner**。

发现不合规时，只有有写权限且能**保持原 Requirement 语义**，才可在同一 Owner 按**原有验收顺序**规范化并**再次重新读取**；**无写权限**、语义不能安全恢复、写失败或**并发漂移**时保持 **`blocked/unresolved`**，不得另造 Requirement。对**仍 open 且继续作为当前 Requirement Source** 的旧 Issue 同样处理；**已关闭历史 Issue** 默认**不批量迁移**，除非用户或项目正式 Owner 明确发起独立历史审计。

### Issue 类型与最少充分内容契约

项目已有更强 Issue/工单模板、RFC 或需求系统时优先；以下仅作为无冲突默认 Contract。按主要完成定义分类，而非按前后端等实现层分类：

- **需求 Issue**：问题背景、目标/可观察结果、用户/调用方场景、范围、非目标、**验收标准**、不变项、上游资料、风险依赖、验证要求；
- **缺陷 Issue**：实际行为、已确认期望及依据、影响范围/严重性、环境/版本、**复现步骤**、原始证据、回归范围、验收标准、验证要求、上游资料；根因无证据时不猜；
- **技术变更 Issue**：动机/工程约束、当前/目标状态、范围、非目标、**兼容与迁移**、**风险与回滚**、验收标准、验证要求、上游 RFC/ADR/Contract/Schema/指标等。

多个独立性质不能为模板方便揉成不可审查事项。required 表示必须显式处理，真实为无/N/A/待确认时写明原因；**模板完整不等于需求已经完整**。范围、验收或上游决定实质变化时更新正式 Owner 并重新检查 Change/PR/测试/Review，不能让旧 AC 静默继续。

### GitHub Issue Form 只是平台 Profile

GitHub 可用 `.github/ISSUE_TEMPLATE/*.yml` 落地上述字段，Acceptance 示例为：

```text
- [ ] AC1：第一个可独立验收结果
- [ ] AC2：第二个可独立验收结果
```

open Issue 缺稳定 AC 时按 Live Validation Gate 处理。项目已有 Form 则遵守；没有但明确要建立平台门禁时，只有写授权和项目治理允许才落地；blank issue 设置由项目决定。Agent 不得用 API/维护者权限规避内容 Contract。**非 GitHub 平台**使用等价 ticket/work item 字段，不要求模仿 GitHub YAML。

## 3. PR 使用稳定 Requirement-Source 关系

项目没有更具体格式时：

```text
Requirement-Source: <项目正式稳定标识>
```

GitHub Issue 可写 `Requirement-Source: #218`；已有 OpenSpec/RFC/ADR/Spec/Roadmap 等更强正式来源时直接引用其稳定标识，**不为了建立追溯关系再创建重复 Issue**。一个 PR 确实实现多个独立来源时可重复多行；跨仓或非 GitHub 同样使用项目已有稳定标识，不自创 URI schema。

`Requirement-Source` 表示 PR 为什么存在；`Closes` / `Fixes` / `Resolves` 表示 merge 后整个 Issue 是否应自动关闭。需要 post-merge evidence 时不得使用关闭关键字，只保留 Requirement-Source，由 Closure Audit 后关闭；只有 merge 已足以满足整个 Issue 时才可使用 closing keyword。不得用多个局部 PR 抢先关闭同一 Requirement。

**创建或更新 PR**后先重新读取真实 PR body，确认引用已写入、来源真实可访问且未错指、范围匹配，再进入下述 live validation。

### Delivery Live Requirement Source Validation

**创建或更新 PR**、**正式 Review**、**PR Ready / 可合并**判断和 **merge preflight** 都必须**重新读取当前 live Requirement Source**。GitHub Issue 除真实存在外，还必须满足当前 Title、最少充分内容、稳定 AC 与 task-list Acceptance Contract，并与 PR/Review 范围匹配；正文、AC、状态或身份漂移后**旧 `resolved` 结论失效**。仅可按 Live Validation Gate 安全规范化并重读，否则转为 `partial/unavailable` 或 `blocked/unresolved`，停止 Ready、可合并和 merge 强结论。

宿主不能修改 PR/Issue 时只报告缺口和建议内容，不得声称已自动关联。

## 4. 机器门禁与 Agent 语义审查分工

若项目要求“没有需求来源不能 merge”，优先把项目 traceability CI 设为 **Required Status Check** 并由 **Branch Protection / Ruleset** 执行。机器适合验证 Requirement-Source 是否存在/可解析、来源是否真实可访问、项目要求的最小结构是否存在；不能假装理解自然语言完整性、语义一致性或实现覆盖，这仍由 Requirement Traceability、Completion Audit 和独立 Review 判断，关键检查不得用 skip 冒充通过。

## 5. PR Review 快照与 Requirement 状态

正式 Review 前记录：PR/MR、base/target、`reviewed_base_sha`、`reviewed_head_sha`、`current_base_sha`、Requirement Source、required checks、授权。随后读取 diff/调用链/测试/文档并继续读取上游来源，不能把 PR description 当替代。

Requirement Source 状态：

- `resolved`：足够重建当前范围目标、成功标准、不变项和关键约束，可继续 A1/A2；
- `partial`：缺少影响范围/接口/数据/兼容/用户行为/验收的事实，可继续已知范围的**代码质量 Review**，但**不得声明整体需求符合**；
- `unavailable`：来源不存在/不可访问/无法确认，可审确定性代码问题，但不得猜需求，**不得声明整体需求符合，也不得声明可合并**。

CI 全绿、作者说明或代码看似正确都不能把 partial/unavailable 升为 resolved。

## 6. base/head 漂移与 merge preflight

head 漂移后读取新增 diff、重判风险、重跑 required validation、re-review Findings；不能因“小 commit”沿用旧 Approval。base 漂移时旧结论只证明旧 base + reviewed head，merge 前必须对当前 base + 待合入 revision 取得项目要求的 fresh validation，可使用 strict checks、**merge queue** 或项目等价机制；**不强制 rebase**。

准备给出“可合并”或 merge 前重新确认：当前 Delivery Live Requirement Source Validation = resolved、`reviewed_head_sha` 等于当前 head、当前 base fresh validation 和 required checks 满足、阻塞 Findings 清零、Requirement/Contract/Schema 无未审漂移。GitHub merge 继续遵守 REST merge + expected head guard；base freshness 与 head guard 不能互替。

## 7. Requirement Source 关闭前 Closure Audit

关闭 Issue/工单为 completed/resolved 前，先取得 required post-merge evidence，**重新读取当前 Requirement Source**并**逐条核对**验收标准；**只有实际证据支持**的项才能完成。状态必须**先回写** Requirement Source 再重读。仍有适用的 partial/unverified/unresolved AC 且没有正式 N/A/deferred 处置时，**不得以 completed / resolved 关闭**。

GitHub 标准顺序：

```text
重新读取当前 Requirement Source
→ 逐条 Requirement → Evidence 审计
→ AC → satisfied / not_applicable / deferred / unresolved
→ `- [ ]` → `- [x]`（仅正式处置项，保留 N/A/deferred 依据）
→ 写回 Issue body
→ 重新读取 Issue，确认 AC/状态/Evidence 无漂移且没有仍适用的未勾选项
→ 执行 close
→ 再次读取 Issue，确认 closed/completed 且 Acceptance 状态仍存在
```

- `satisfied`：至少一项**直接 Evidence**证明对应**可观察结果**，核对**对象、行为、条件**、`revision/commit` 和必要环境；
- `not_applicable`：当前范围事实明确证明 N/A，并保留原因；
- `deferred`：已有新的正式 Owner 和稳定引用；否则仍 unresolved；
- `unresolved`：含 partial/unverified/未满足/关键未知；GitHub 保持 `[ ]`，**仍适用的未勾选项不得关闭**。

Closure comment 可保存详细 AC→Evidence Mapping，但 **comment-only Evidence 不能代替 Issue body Acceptance 状态**；body task list 必须真实写回。写后读取发现写失败、并发修改、AC 漂移或未勾选项即停止；close 后读取不是 closed/completed 只能报告 blocked/incomplete；**无写权限**/写失败不得声称完成；**关闭关键字不得绕过** Closure Audit。

非 GitHub 平台按等价字段/状态执行同一“逐项 Evidence → 状态写回 → 重读 → close → 再读”语义；平台没有某能力时不发明。

## 8. 多人协作与输出边界

开始时基于最新 main 只是起点，真正硬门禁是 merge 前针对当时最新目标分支验证。Agent 看不到未 push 工作；Issue/PR 关联不能替代 Contract Owner；Agent_Skills 不能自行强制平台保护/required reviewers，平台负责执行，Agent 负责检查并在不满足时停止。只读 Review 不自动获得修改 Issue/PR、merge 或关闭权限。

PR/MR Review/交付至少报告：Requirement Source 状态、`reviewed_base_sha / reviewed_head_sha / current_base_sha`、关键上游事实、A1/A2、Findings、测试充分性、实际 current-head/current-base 验证、未验证项与 merge 阻塞依据。没有 Finding 也不能只写 `LGTM`。
