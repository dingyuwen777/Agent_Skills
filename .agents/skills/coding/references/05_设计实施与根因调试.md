# 设计、实施与根因调试

## 现状调查

修改已有项目之前，只读取与任务直接相关的：

- README、规则、需求和架构导航；
- 入口、调用链、数据流和模块 Owner；
- Contract、Schema、Migration、配置和依赖锁定版本；
- 相关实现、测试、错误处理和正常参照；
- 构建、运行、测试和 CI 命令；
- 当前分支、工作区和近期相关变更。

不要依据单个文件重构架构。能从仓库确认的事实先自行检查。

不同语言和工具链的 Manifest、锁文件、wrapper、构建、测试、打包入口按 [03_编程语言与工具链适配规则.md](03_编程语言与工具链适配规则.md) 调查；该文件提供导航，不替代当前仓库实际规则和命令。

## Planning Ownership 与设计门禁

Planning 属于 Coding；不建立独立 Planner，不创建子 Agent、不维护独立任务队列、不调度 Worker，也不建立自主 `plan → act → observe → re-plan` 循环。

L2 建立**最小 Planning Contract**。固定核心只有：目标 / 非目标 / 成功标准、当前系统事实与尚未确认项、受影响能力/Owner、最小方案、可观察结果 / 直接 Evidence、真实风险与未知项。高价值条件字段仍保留为：**受影响能力链 / Owner、复用 / 公共抽象 / 能力归一、Migration / Rollback、风险 / 未知项**；公共接口/Contract、数据/Schema、部署、安全/权限、长期架构/统一 Owner、多个方案的业务/成本取舍等也只在**对应边界真实存在**时加入。经当前事实确认 `not_applicable` 的维度不为了填表向用户逐项确认。L3 对实际存在的重大决策比较 2–3 个真实方案。

L3 比较正确性、兼容性、维护成本、迁移、回滚和验证，并遵循**最上游问题优先**：只有一个会改变下游结果的未决决策时，优先只提请该问题；如果多个未决项**彼此独立**、**都命中 Plan Review Gate**、且都必须在实现前决定，则一次形成有界 **Decision Package**，给出每项推荐、主要依据、真实备选与影响，统一提请用户/Owner 决策，**不人为拆成多轮**逐项确认。**能从事实源恢复的事项不得放入 Decision Package**，普通可逆实现细节也不得借机升级成审批项。只有实际存在的 L3 边界需要在实现前明确；不存在的公共接口/数据/Migration/部署/回滚维度直接记录不适用依据，不把 N/A 变成用户确认清单。保持已确认方案连续性；新事实使原方案不可行时，先解释证据、影响和替代方案，再改变路线。

Current Facts 只来自仓库、运行结果、一手资料或用户/Owner 确认；Planned State 的拟复用、修改、拟新增、删除和未确认必须分开，计划对象不能被当作当前事实。

### Plan Review Gate

公共 Contract、Schema / 数据语义、Migration、长期架构 / 公共抽象 / 统一能力 Owner、核心技术路线、范围明显扩大、多个真实可行方案的业务/成本/兼容/维护取舍，以及其他高成本 / 难逆决策，实施前必须给出推荐方案、主要依据与影响、备选方案和需要用户确认的决策。这里的“公共抽象”只指会改变**稳定架构边界、长期能力 Owner、public/consumer Contract 或任务 Scope** 的抽象决策；局部 helper、同模块复用、行为保持不变且可逆的提取/内联不机械进入审批。用户确认的是决策边界，不是逐文件签字；普通可逆实现细节不机械要求确认。已经由用户或正式 Requirement/ADR/Spec 明确确认的同一决定不重复询问；新事实使其失效才重新进入 Gate。

## 第一性原理与约束下最优解

1. 用可观察行为重述真正目标，区分用户要达到的结果与其预设实现方式。
2. 列出不可违反的硬约束：安全、数据正确性、公共兼容、仓库规则、已确认需求、版本和授权边界。
3. 追踪根因或必要机制，拆掉仅因惯例、历史偶然或工具偏好形成的假设；关键推断说明证据和可证伪条件。
4. 至少考虑保留现有路线的最小增量方案；复杂任务比较 2–3 个真实可行方案，不为凑数制造伪方案。
5. 按正确性、兼容性、简单性、可维护性、可逆性、性能、交付成本和可验证性比较；只有任务有实际性能目标时才用测量结果主张性能最优。
6. 选择满足全部硬约束、机制最少且证据最充分的方案；更复杂架构必须由已观察规模、风险、第二实现或故障模式证明必要。
7. 用失败测试、最小实验、原型或现有正常参照验证关键假设；证据推翻方案时回到约束重新推导，不在错误前提上叠补丁。

“行业最佳实践”只能作为候选和风险清单。若与项目实际版本、架构或兼容边界不一致，以当前事实和经确认目标为准；需要改变既有路线时先完成设计门禁。

## 实施计划

按可独立理解、可独立实现、可独立验证的行为 / 能力边界工作分解，不按文件机械拆分。每一步至少明确：

```text
[Plan Step]
→ Requirement
→ Owner / 行为
→ 修改范围：[文件/模块]
→ Observable Result / 完成判据
→ 直接 Evidence
→ 依赖关系
→ 验证方式：[完整命令/检查项]
```

形成 `Requirement → Plan Step → Observable Result → Evidence`。步骤必须小而完整、可独立验证并明确依赖；不要使用 `TBD`、`TODO` 或“补充适当测试”等不可执行占位。

### Plan → Execution 与 Re-plan Gate

实现不得静默偏离已确认目标、Owner、Contract、范围、兼容/Migration 和验证策略；不得为了让当前实现看起来正确而反向修改 Requirement。原假设/Owner 错误、发现可复用能力或新公共消费者、Contract/Schema/安全/关键依赖变化、实现无法满足 Acceptance 或产生明显重复等实质性新事实触发 Re-plan Gate：先更新计划和必要决策，再继续实现；命中 Plan Review Gate 时先取得用户决策。文件/函数位置、局部命名、测试位置和同一方案内不改变公共语义的小的可逆实现细节只做局部调整，不机械触发完整 re-plan。

## 测试驱动

新增可观察行为和 Bug 修复默认执行：

1. Red：写一个表达真实行为的最小测试；
2. Verify Red：实际运行，确认它失败而不是环境报错，并且因目标行为尚未实现而失败；
3. Green：只写使测试通过的最少代码；
4. Verify Green：运行目标测试及相关测试，读取完整输出和退出码；
5. Refactor：只在绿色后整理重复和命名，不增加行为；
6. Re-verify：重构后再次运行验证。

**behavior-preserving refactor**、低影响可逆且行为/Contract 不变的澄清或复述，不因为“重构/修改”标签机械新增失败测试；先复用已有直接回归、parser/check/readback/diff。只有当前证据无法保护真实新增行为、不变量或具体回归缺口时，才补最小测试。

测试真实行为，避免只验证 Mock、调用次数或内部实现。必须 Mock 时先理解依赖副作用，并把原因写进测试或 Change。

允许的例外包括纯文档、纯配置、生成代码、一次性探索或环境确实无法自动测试。明确说明例外、替代验证和剩余风险。探索代码不能冒充已验证生产实现。

完整验证层级和证据职责按 [07_通用验证与证据策略.md](07_通用验证与证据策略.md)；项目真实存在 Web/API/PostgreSQL/Provider 边界时再叠加 [08_分层测试与验收策略.md](08_分层测试与验收策略.md) 专项规则。

完整流程见 [22_根因调试.md](22_根因调试.md)。诊断、故障处置或性能优化场景由该 Reference 的 routing metadata 自动加载完整规则；普通实现不因引用存在而预加载诊断正文。

## 最小、精准、兼容

- 优先复用标准库和现有依赖；
- 不为少量代码引入依赖或抽象层；
- 不顺手格式化、改名或优化无关代码；
- 删除仅因本次修改失效的内容；
- 保持公共 API/ABI、导入路径或模块路径、CLI、配置、默认值、数据/序列化格式、启动方式、错误类型和关键错误信息兼容；
- 破坏性变化先说明版本策略、迁移、回滚和验证。

不要为了显得完整而创建仓库没有的前后端分层、Repository/Service 抽象、Owner 表、Schema、事件总线、Migration 框架或契约测试基础设施。任务确实需要建立新边界时，把它作为设计决策处理，不把通用建议伪装成仓库现状。

## 代码组织原则

函数拆分以“是否降低理解和维护成本”为判断，不使用固定行数、调用次数或语句数量作为硬门槛。

1. 优先保持主流程清晰：主流程应按业务阶段自然展开，读者能从上到下理解关键路径；不要为了形式上的“整洁”把连续业务逻辑打散，也不要把多个独立责任堆在一个函数中。
2. 在下列情况提取函数，前提是提取后边界更清楚且没有引入额外绕行：
   - 逻辑具有独立、可命名的业务语义；
   - 可以隔离 I/O、网络、数据库事务、文件系统或其他副作用边界；
   - 能显著降低条件分支、嵌套或主流程的认知复杂度；
   - 形成值得独立测试、复用或替换的行为单元；
   - 同一逻辑出现真实重复，提取后能消除重复而不隐藏差异。
3. 不因以下单一因素决定“必须拆”或“禁止拆”：
   - 函数超过某个固定行数；
   - 新函数只有少量语句；
   - 辅助函数当前只调用一次；
   - 为满足“单一职责”、DRY 或其他原则的形式要求。
   这些都只能作为信号，最终以可读性、语义边界、副作用隔离、测试价值和维护成本判断。
4. 提取后如果只是增加跳转层级、转发参数、包装单个已有调用，且没有增加业务语义、边界隔离、测试价值或复用价值，则保持内联，不创建无意义 wrapper/helper。
5. 函数命名表达真实业务或领域意图，避免 `doStep3`、`handleThing` 之类过程性或含糊命名。若无法给提取出的逻辑起一个清楚名字，优先重新审视边界是否成立。
6. 作用域保持最小但不要机械使用闭包：仅模块内部使用的函数不导出；只有确实需要捕获局部上下文且不会降低测试、调试和类型分析能力时才使用嵌套函数。单次调用不是使用闭包的理由。

## 独立可验证能力

独立验证的目的不是增加测试文件数量，而是让有价值的行为在不依赖完整系统启动的情况下能够被快速、重复、可信地验证。

### 什么时候应当建立独立验证闭环

满足以下任一情况时，优先把该能力视为独立验证单元：

- 有明确、可描述的输入和输出；
- 具有独立业务价值或可被其他能力复用；
- 对接网络、数据库、文件系统、消息、外部 SDK 等副作用边界；
- 包含数据转换、分页、状态机、幂等、重试、错误分类等可独立失败的规则；
- 故障排查时需要区分“本能力失败”与“上下游失败”；
- 启动完整系统的成本显著高于验证该能力本身。

不要因为目录叫“module”、类是 public、函数很长或当前只有一个调用方，就机械创建独立测试单元。测试粒度由行为边界、风险、依赖和失败模式决定。

### 一个独立验证闭环至少回答什么

在计划、实现、README/测试说明或现有等价事实源中明确：

1. **生产入口**：正式实现从哪里进入，测试不得复制另一套业务逻辑；
2. **显式输入**：参数、Contract、Fixture、文件、数据库前置状态等；
3. **可观察输出**：返回值、持久化状态、Artifact、事件、错误或其他可断言结果；
4. **可控边界**：哪些依赖使用真实隔离环境，哪些使用 Fake/Stub/Fixture，为什么；
5. **测试层级**：行为/Unit/Component、Contract、Integration、Workflow Acceptance、Golden Path、External Probe、Build/Runtime 或仓库已有等价层级中，哪一层最能证明目标行为；
6. **运行入口**：一个明确命令或最小步骤能够重复执行；
7. **成功判据**：什么结果算通过，什么仍未覆盖；
8. **人类说明**：后续维护者能够快速找到测试位置、依赖和运行方式。

测试代码和本轮执行结果是验证事实；README、测试指南等人类文档负责导航和解释，不复制第二套断言、Schema 或期望值清单。仓库已有统一测试文档或模块 README 规范时沿用它；没有时，只在确有持续维护价值时建立最小说明，不为每个函数新建文档。

### Fixture、Fake 与真实 Probe

- **Fixture**：固定、可复现输入，用来验证转换、Contract 和边界行为；不要把未经脱敏的生产数据直接提交到仓库。
- **Fake/Stub**：隔离不属于当前目标的外部依赖，但测试仍应通过正式生产入口调用目标能力；不要只验证 Fake 自己。
- **真实 Probe**：用于确认真实外部边界、版本或 Provider/设备/远端环境行为；默认不替代普通自动化测试。若有费用、写操作、安全或速率风险，必须显式受控并说明，不默认进入普通 CI。

如果一个能力只能通过复制生产逻辑才能“独立测试”，先修正边界或测试方法，而不是接受两套实现长期漂移。

## 独立调试复用生产实现

调试工具、Raw Probe、示例入口或测试夹具只负责：

- 准备显式输入；
- 注入可控边界；
- 调用正式生产入口；
- 捕获并展示输出。

不得复制正式分页、映射、校验、状态转换、重试、错误处理或写库逻辑。若调试需要不同实现，先证明边界真实存在，并保持同一 Contract。

## 代码注释

## 时间基准

北京时间 `Asia/Shanghai`、外部时区事实保留和展示转换由 [Coding 主规则](../SKILL.md) 直接承担。本 Reference 只补充：Agent 生成的 ISO 8601 时间戳保留明确 `+08:00`；比较、排序或窗口计算前先确认源时区，不能混用不同 tz 的 naive/aware 值。

## 可观测性与日志

何时记录、敏感信息、INFO 噪声、正式业务事实边界、统一日志前缀与结构化等价字段由 [Coding 主规则](../SKILL.md) 直接承担。本 Reference 补充未重复细则：先确认仓库存在可复用的正式 logging/event/telemetry 体系；没有时不为通用“最佳实践”新造框架。优先关注低频重要生命周期、异步或长流程阶段、外部 I/O、Retry/backoff/降级/部分失败/跳过/取消/接管/永久失败，以及能显著缩短定位时间的关键分支。优先复用项目已有稳定 event/关联 ID，不造第二套业务 ID；没有更具体级别约定时按 `DEBUG=高频正常细节`、`INFO=低频重要生命周期/结果`、`WARNING=可恢复异常/重试/部分失败`、`ERROR=永久失败/非法配置/需人工介入`；同一异常优先由真正处理/终止 Owner 记录一次；复用现有 logger/Formatter/脱敏/输出机制，不建平行 FileHandler/telemetry；错误上下文保持最小安全字段。若重要故障仍无法回答执行阶段、业务标识和失败/重试/跳过原因，应补观测；已有正式状态/事件/日志足够时不重复增加。
