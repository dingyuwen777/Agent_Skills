# 端到端交付与合并后收尾

本规则只在用户或项目正式规则明确授权**当前任务**完成端到端交付时加载。普通 Git/PR、只读 Review、单次 commit/push 不因具备 Git 能力自动加载；**授权只改变允许的交付动作，不自动改变任务原本依据影响面判定的 L1/L2/L3**。

## 1. 端到端交付授权

授权按用户要求的完整结果解释，但只覆盖当前任务，不扩展为无限 GitHub、Release、Deploy 或生产操作权限。

### `develop-and-deliver`

用户要求“开发并合并到主分支”“完成开发并交付”等完整结果且未排除中间步骤时，路由为 `授权=允许端到端交付`：

```text
创建或复用 Requirement Source / Issue（确有需要且项目允许时）
→ 通过 live Requirement Source Contract Validation
→ 建立当前任务分支与 Change（适用时）
→ 实现、测试、commit、push、PR
→ required Completion / Review / CI
→ guarded merge
→ Post-Merge Finalization Gate
```

live validation 的正文、规范化和 fail-closed 语义由需求追溯 Owner 负责；通过前不开始正式分支/Change 施工。

### `review-and-deliver`

用户要求对其他开发者 PR“审查通过后合并”等完整结果时，路由为 `授权=允许审查后交付`：

```text
解析并读取 Requirement Source
→ 通过当前 live Requirement Source Contract Validation
→ 冻结 reviewed_base_sha / reviewed_head_sha / current_base_sha
→ 独立 Review 与 required 验证
├─ BLOCK → 停止交付，不 merge；默认交由原作者修复
└─ Review PASS
   → 重新确认 current live Requirement Source、current head/base、required CI/checks、阻塞 Findings
   → Handoff 到 Coding / Git Delivery
   → guarded merge
   → Post-Merge Finalization Gate
```

硬边界：`review-and-deliver` 不降低 Review 独立性；`BLOCK` 未清不得 Handoff；`Review PASS` 只证明实际 reviewed revision，不替代 merge 前新鲜确认。**默认不自动修改**他人生产代码；只有明确 `review-and-fix` 授权才可修复并重新 Review。无法看到对方本地状态时不推断，只审当前可访问事实。

## 2. 不被端到端授权隐式包含的动作

`develop-and-deliver` / `review-and-deliver` 不自动授权 `Release`、`Deploy`、生产 Migration/数据写删、`force push`、共享历史重写、绕过保护规则、删除无关分支/保护分支/默认分支或其他任务资源。上述动作仍需真实授权；端到端授权不能覆盖更高优先级权限、安全和平台门禁。

## 3. Post-Merge Finalization Gate

命中端到端交付授权或项目明确要求合并后收尾时，merge 不是终点：

```text
确认真实 merge commit / 目标分支 HEAD
→ main fresh CI
→ Change archive（适用时）
→ 重新读取 Requirement Source 并执行 Closure Audit
→ Acceptance checklist 同步（GitHub）/ 等价 Acceptance 状态同步（其他平台）
→ 写后重新读取 Requirement Source
→ 关闭 Requirement Source 为 completed / resolved（适用、直接 Evidence 满足且有写权限时）
→ close 后再次读取 Requirement Source
→ 分支清理
→ 最终交付报告
```

硬规则：

- required 的 `main fresh CI`、`Change archive`、`Closure Audit`、Acceptance 写回/重读、关闭或分支清理任一未完成时，**不得报告整个任务完成**，状态为 `blocked/incomplete` 并说明缺口；
- main fresh 必须针对真实 merge 后目标分支 revision；PR/历史 CI 或 merge API 成功不能替代；持久 Change 只有 implementation main fresh 成功后才可 `done` 并归档，归档 revision 仍需自身 fresh CI；
- Closure 语义由需求追溯 Owner 决定：先重读当前 live Requirement Source，再做 Evidence Mapping；Acceptance 状态写回并重读后才可 close，close 后再次读取；需要 post-merge evidence 时不得用 `Closes` / `Fixes` / `Resolves` 绕过；
- 没有对应对象且项目事实证明 `not_applicable` 时不为形式制造；权限/宿主限制导致 required 动作不能执行属于 blocked，不是 N/A；
- 本规则只编排顺序，不复制 REST merge、`expected_head_sha` 或 direct Evidence 细则。

## 4. 分支与 worktree 清理

只清理“当前仓库 + 当前任务 + 已确认 merged + 非默认/保护分支 + 无其他 active worktree/任务继续使用 + 当前宿主可安全删除”的资源。`fork`、他仓分支、未合并/其他任务分支不得越权删除；cleanup 必须晚于 required post-merge 验证和 Requirement/Change 收尾，宿主不支持安全删除时报告缺口。删除任务分支不等于授权删除 tag、Release、部署环境或数据。

## 5. 完成判据与回到主流程

完整端到端完成要求所有适用项成立：Review/CI/merge 门禁、真实 merge revision、main fresh CI、Change archive、Closure Audit、Acceptance 状态写回与重读、Requirement Source close 后重读、任务分支清理；有事实依据的 N/A 除外。任何 required 项受权限/宿主/平台阻塞时只报告 `blocked/incomplete`。最终报告逐项给出 revision、CI、Change、Requirement Source 与 cleanup 状态，不把“merge 成功”缩写成“完整交付完成”。
