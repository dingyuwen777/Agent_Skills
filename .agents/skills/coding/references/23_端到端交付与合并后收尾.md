# 端到端交付与合并后收尾

本规则只在用户或项目正式规则已经明确授权**当前任务**完成端到端交付时加载。普通 Git/PR 操作、只读 Review、单次 commit/push 或没有完整交付授权的任务，不因为具备 Git 能力就加载本规则。**授权只改变允许执行的交付动作，不自动改变任务原本依据影响面判定的 L1/L2/L3 风险等级。**

## 1. 端到端交付授权

端到端交付授权按用户要求的**完整结果**解释，不把同一已确认交付范围机械拆成每一步重新询问；但它只覆盖当前任务本身，不能扩大为无限 GitHub、Release、Deploy 或生产操作权限。

### `develop-and-deliver`

用户明确要求“开发并合并到主分支”“完成开发并交付”“实现后合并 main”或语义等价的完整结果，且没有排除其中某一步时，将当前任务路由为 `授权=允许端到端交付`，执行：

```text
创建或复用 Requirement Source / Issue（确有需要且项目允许时）
→ 建立当前任务分支与 Change（适用时）
→ 实现、测试、commit、push、PR
→ required Completion / Review / CI
→ guarded merge
→ Post-Merge Finalization Gate
```

### `review-and-deliver`

用户明确要求对其他开发者的 PR“审查通过后合并”“Review 通过后合并到主分支并完成收尾”或语义等价的完整结果时，将当前任务路由为 `授权=允许审查后交付`：

```text
解析并读取 Requirement Source
→ 冻结 reviewed_base_sha / reviewed_head_sha / current_base_sha
→ 独立 Review 与 required 验证
├─ BLOCK / 阻塞 Finding
│  → 停止交付，不 merge
│  → 默认交由原作者修复
│
└─ Review PASS
   → 重新确认 current head/base、required CI/checks、阻塞 Findings
   → Handoff 到 Coding / Git Delivery
   → guarded merge
   → Post-Merge Finalization Gate
```

硬边界：

- `review-and-deliver` 不降低 Review 独立性；后续有 merge 授权也不能把作者清单、已有 CI 或实现意图当成 Reviewer 的需求重建；
- `BLOCK` 或任何阻塞 Finding 未解决时不得 Handoff 到 Git Delivery；
- `Review PASS` 表示 Review 当前结论没有阻塞交付的 `BLOCKER/HIGH/重要 MEDIUM`，且本轮 required Review 证据已经满足；它仍只证明实际 reviewed revision 和声明证据范围，不替代 merge 前 current-head/current-base/required checks 的新鲜确认；
- `review-and-deliver` **默认不自动修改**其他作者的生产代码、测试或文档；只有用户明确授权 `review-and-fix` 或等价修改权限，才返回 Coding 修复、取得新鲜 Green 并重新进入 Review；
- 无法证明对方本地是否运行 Agent_Skills、有哪些未 push 状态或私有上下文时，不做推断；只审当前可访问的 Requirement Source、PR diff/commits、Contract/Schema/Migration、测试、CI、正式文档和项目规则。

## 2. 不被端到端授权隐式包含的动作

`develop-and-deliver` / `review-and-deliver` **不自动授权**：

- `Release`、正式版本发布、tag 或 Release asset 修改；
- `Deploy`、生产部署或生产环境变更；
- 生产 Migration、生产数据写入/删除或其他真实不可逆数据动作；
- `force push`、共享历史重写、绕过 Branch Protection/Ruleset/required checks；
- 删除无关分支、保护/默认分支、其他任务分支或不属于当前仓库 Owner 的资源；
- 任何用户明确排除的动作。

这些动作仍需要用户、项目规则或既有长期授权明确允许。端到端授权不能覆盖更高优先级安全、权限或平台门禁。

## 3. Post-Merge Finalization Gate

当当前任务命中端到端交付授权，或项目规则明确要求完成合并后收尾时，PR/MR merge 不是任务终点。真实 merge 成功后继续：

```text
确认真实 merge commit / 目标分支 HEAD
→ main fresh CI
→ Change archive（适用时）
→ 重新读取 Requirement Source 并执行 Closure Audit
→ Acceptance checklist 同步（GitHub）/ 等价 Acceptance 状态同步（其他平台）
→ 写后重新读取 Requirement Source
→ 关闭 Requirement Source 为 completed / resolved（适用、直接 Evidence 满足且有写权限时）
→ close 后再次读取 Requirement Source
→ 分支清理：清理本仓当前任务已合并且确认不再需要的任务分支 / worktree
→ 最终交付报告
```

硬规则：

- 任一 required 的 `main fresh CI`、`Change archive`、`Closure Audit`、关闭 Requirement Source 或分支清理仍未完成时，**不得报告整个任务完成**；只报告已完成阶段、缺失证据和阻塞原因；
- `main fresh CI` 必须针对真实 merge 后目标分支当前 revision；PR CI、历史 CI 或 merge API 成功不能替代；
- 使用持久 Change 时，只有 implementation merge 后 main fresh 成功，才能按 Change Owner 更新为 `done` 并归档；归档提交/PR 仍按其真实 changed scope 取得 fresh CI；
- Requirement Source 的逐项证据和 close 语义继续由需求追溯 Owner 的 Closure Audit 决定；Finalization 必须等 Acceptance 状态真实写回并重读确认后才允许 close，close 后还要再次读取确认最终状态；需要 post-merge evidence 时不得用 `Closes` / `Fixes` / `Resolves` 提前绕过；
- 任一 required 的 Acceptance checklist / 等价状态同步、写后重读、close 或 close 后重读失败时，流程状态必须是 `blocked/incomplete`，不得继续用 cleanup 或最终报告掩盖 Closure 缺口；
- 没有持久 Change、没有可关闭 Requirement Source，或项目正式事实证明某一步 `not_applicable` 时，不为形式制造对象，但必须记录不适用依据；
- 如果 required 收尾动作因为宿主能力、权限或平台限制无法执行，允许**停止并报告 `blocked/incomplete`**，但该阻塞不能被当作 `not_applicable`，也不能把整个交付任务报告为完成；
- 本规则只编排收尾顺序，不复制 GitHub REST merge、`expected_head_sha`、Closure Audit direct Evidence 等既有 Owner 的完整细则。

## 4. 分支与 worktree 清理

分支清理只针对同时满足以下条件的资源：

```text
当前仓库
+ 当前任务
+ 已确认 merged
+ 不是默认/保护分支
+ 没有其他 active worktree / 任务继续使用
+ 当前宿主具备安全删除权限
```

- contributor `fork`、其他仓库来源分支、无删除权限资源、未合并分支、其他任务分支和保护/默认分支不得越权删除；
- cleanup 发生在 required post-merge 验证、Change/Requirement 收尾之后，不能为“整洁”先删掉仍用于诊断、证据恢复或回滚判断的分支；
- 宿主不支持安全删除时，明确报告 cleanup gap，不伪造已清理；
- 删除本任务分支不等于授权删除 tag、Release、部署环境、数据或其他仓库资源。

## 5. 完成判据与回到主流程

只有以下**适用且 required** 的项目全部完成，才能报告完整端到端交付完成：

```text
Review/CI/merge 门禁满足
+ 真实 merge revision 已确认
+ main fresh CI 已取得
+ Change archive 已完成或有事实依据的 not_applicable
+ Closure Audit 已完成
+ Acceptance 状态已同步并完成写后重读确认，或有事实依据的 not_applicable
+ Requirement Source 已关闭且完成 close 后重读确认，或有事实依据的 not_applicable
+ 当前任务分支清理已完成或有事实依据的 not_applicable
```

若任何 required 项因为权限、宿主或平台能力而无法完成，流程可以停止，但最终状态必须是 `blocked/incomplete`，并明确缺失动作、原因和已完成证据；不得把权限阻塞写成完成条件。

回到 Coding 最终报告时，逐项报告实际 revision、CI、Change、Requirement Source 和 cleanup 状态；不得把“merge 成功”缩写成“完整交付完成”。
