# 端到端交付与合并后收尾

本规则处理“开发并提交 PR”“开发并完成端到端交付”“Review 通过后交付”三种授权边界。普通 Git/PR、只读 Review、单次 commit/push 不因具备 Git 能力自动获得 merge 权；**授权只改变允许的交付动作，不自动改变任务原本依据影响面判定的 L1/L2/L3**。

端到端交付授权按用户已经确认的完整结果持续生效，**不把同一已确认交付范围机械拆成每一步重新询问**；但 Requested Action 仍不能突破当前 Effective Authorization、安全边界或平台门禁。

## 1. Requested Action 与 Effective Authorization

用户自然语言描述的是 **Requested Action**，不是权限提升指令。任何 merge、Release、Deploy、生产 Migration/数据写入等高权限动作执行前，都必须重新解析：

```text
Requested Action
+ 目标项目当前规则
+ 当前 authenticated principal
+ 托管平台当前保护规则 / Ruleset / 等价权限事实
→ Effective Authorization
```

硬规则：

- 用户说“合并 main”不能让本来没有目标分支 delivery authority 的身份获得该权限；
- 项目/平台事实无法证明当前 principal 拥有目标分支 delivery authority 时，merge 权限视为**没有确认**，不得用 maintainer token、Bot、bypass、force push 或另一条 API 通路自行升级；
- Requested Action 高于 Effective Authorization 时，在不产生额外风险的前提下完成当前真实授权允许的最大安全范围，并把未执行的高权限动作明确报告为 `BLOCKED_BY_AUTHORIZATION`，不能静默假装完成；
- 平台拒绝权限或保护规则时必须停止，不把拒绝解释成“换一种方式绕过”。

## 2. 三种正式交付模式

### `develop-and-submit`

用户明确要求“开发并提交 PR”“修复后提 PR 给我审”“完成开发到 PR Ready”或语义等价结果时，路由为 `授权=允许开发并提交PR`：

```text
创建或复用 Requirement Source / Issue（确有需要且项目允许时）
→ 通过 live Requirement Source Contract Validation
→ 建立当前任务分支与 Change（适用时）
→ 实现、测试、文档、Completion Audit / 开发侧 Review
→ commit / push / PR
→ current-head required CI
→ PR Ready
→ STOP
```

`develop-and-submit` 的终点就是 **PR Ready**。它不包含 merge、Release、Deploy、生产 Migration/数据写入、post-merge Change 归档、Requirement Closure 或 post-merge cleanup。开发者可以完整执行 Agent_Skills 的 Coding/Testing/Docs/Completion 自检，但这不替代后续 Maintainer Review。

### `develop-and-deliver`

用户明确要求“开发并合并到主分支”“完成开发并交付”“实现后合并 main”或语义等价完整结果时，只有在 **Effective Authorization 已确认允许当前 principal 更新目标分支**时，才进入 `develop-and-deliver`：

```text
创建或复用 Requirement Source / Issue（确有需要且项目允许时）
→ 通过 live Requirement Source Contract Validation
→ 建立当前任务分支与 Change（适用时）
→ 实现、测试、commit、push、PR
→ required Completion / Review / CI
→ guarded merge
→ Post-Merge Finalization Gate
```

如果 Requested Action 要求完整交付，但当前 principal 没有目标分支 delivery authority，则不要把任务整体作废：在安全且已授权范围内完成到 PR Ready，并把 merge 及后续高权限步骤标为 `BLOCKED_BY_AUTHORIZATION`，等待具备权限的 Maintainer 接手。

### `review-and-deliver`

用户明确要求对已有 PR“审查通过后合并”“Review 通过后合并到主分支并完成收尾”或语义等价结果时，先独立 Review；只有 **Review PASS + Effective Authorization 允许当前 principal merge** 时才进入 Git Delivery：

```text
解析并读取 Requirement Source
→ 通过当前 live Requirement Source Contract Validation
→ 冻结 reviewed_base_sha / reviewed_head_sha / current_base_sha
→ 独立 Review 与 required 验证
├─ BLOCK → 停止交付，不 merge；默认交由原作者修复
└─ Review PASS
   → 重新确认 current live Requirement Source、current head/base、required CI/checks、阻塞 Findings
   → 重新确认 Effective Authorization
   ├─ 无目标分支 delivery authority → BLOCKED_BY_AUTHORIZATION
   └─ 有权限 → Handoff 到 Coding / Git Delivery → guarded merge → Post-Merge Finalization Gate
```

硬边界：

- `review-and-deliver` 不降低 Review 独立性；后续有 merge 授权也不能把作者清单、已有 CI 或实现意图当成 Reviewer 的需求重建；
- `BLOCK` 或任何阻塞 Finding 未解决时不得 Handoff；
- **Review PASS 表示 Review 当前结论没有阻塞交付**，并且只证明实际 reviewed revision 和声明 Evidence 范围；不替代 merge 前 current live Requirement Source/current-head/current-base/required checks 和权限的新鲜确认；
- `review-and-deliver` 默认不自动修改其他作者的生产代码、测试或文档；只有明确 `review-and-fix` 或等价授权才返回 Coding 修复、取得新鲜 Green 并重新 Review；
- 无法证明对方本地是否运行 Agent_Skills、有哪些未 push 状态或私有上下文时不推断，只审当前可访问的 Requirement Source、PR diff/commits、Contract/Schema/Migration、测试、CI、正式文档和项目规则。

live validation 的正文、规范化和 fail-closed 语义由需求追溯 Owner 负责；通过前不开始正式分支/Change 施工。

## 3. 不被交付授权隐式包含的动作

`develop-and-submit` / `develop-and-deliver` / `review-and-deliver` 都不自动授权 `Release`/tag/Release asset、`Deploy`、生产 Migration/数据写删等不可逆动作、`force push`/共享历史重写、绕过 Branch Protection/Ruleset/required checks、删除无关分支/保护分支/默认分支/其他任务资源，以及用户明确排除的动作。上述动作仍需用户、项目规则或既有长期授权真实允许；端到端授权不能覆盖更高优先级权限、安全和平台门禁。

## 4. Repository-native Change Archive Contract

如果目标项目对持久 Change 已建立 **repository-native** 自动归档能力，则 Change 的施工生命周期为：

```text
开发 / Review 阶段
changes/active/<change-id>/CHANGE.md
status: ready_for_review（进入 PR Ready 前）

Implementation PR guarded merge
→ 目标仓库归档基础设施
→ 同一 Change ID：active → archive/YYYY-MM
→ status → done
```

这里的 Owner 必须分离：

- 开发者 / Agent 在 Implementation PR 中只维护 Active Change 到 `ready_for_review`；
- Reviewer / Delivery Agent 只负责 Review、merge 门禁和 post-merge 验证；
- **repository-native automation** 才负责真实的 `active → archive`、`status → done` 和对应基础设施提交；
- Agent_Skills **不执行归档 commit，不创建归档 PR**，也不为了“完成收尾”去修改已 merge Implementation PR 的历史；
- repository-native automation 失败、超时、归档结果歧义或目标仓库没有按其正式规则完成 required archive 时，端到端状态保持 `blocked/incomplete`；Agent **不自行接管**归档来掩盖基础设施缺陷；
- 项目没有 repository-native archive 机制时，继续遵守该项目当前真实 Change Owner；通用 Skill 不擅自给项目发明直接写默认分支的自动化。

`archive/done` 的含义是：**该施工交付已经真实进入目标分支并被基础设施冻结**。它**不等价于 Requirement / Issue 已最终 completed/closed**。若 merge 后 main-fresh 失败，已经发生的 merge 和 archive 都是历史事实，不把旧 Change 移回 active；修复或回滚建立新的适当工作单元，Requirement 保持 open 直到 Closure 条件真实满足。

merge SHA、目标分支 commit、Actions/CI Run 等 post-merge 平台事实由真实 PR/Commit/CI Owner 持有；除非项目有更强正式要求，不为了“档案看起来完整”机械复制到 Change 并再次制造治理提交。

## 5. Post-Merge Finalization Gate

命中 `develop-and-deliver` / `review-and-deliver` 或项目明确要求合并后收尾时，Implementation PR merge 不是终点：

```text
确认真实 Implementation merge commit / 目标分支 revision
→ 取得项目要求的 implementation main fresh CI / Evidence
→ 等待并验证 repository-native Change archive（适用时）
→ 验证 archive/done 对应同一 Change ID；项目要求时验证 archive revision 的 governance fresh Evidence
→ 重新读取 Requirement Source 并执行 Closure Audit
→ Acceptance checklist 同步（GitHub）/ 等价 Acceptance 状态同步（其他平台）
→ 写后重新读取 Requirement Source
→ 关闭 Requirement Source 为 completed / resolved（适用、直接 Evidence 满足且有写权限时）
→ close 后再次读取 Requirement Source
→ 分支清理
→ 最终交付报告
```

implementation main fresh CI 与 Change archive automation 可以按目标项目真实 Workflow 并行发生；Finalization 只要求在 Closure 前两类 required Evidence 都已满足，不为了通用流程强制某个固定先后顺序。

硬规则：

- required 的 `implementation main fresh CI`、`Change archive`、`archive governance fresh`（项目要求时）、`Closure Audit`、Acceptance 写回/重读、关闭或分支清理任一未完成时，**不得报告整个任务完成**，状态为 `blocked/incomplete` 并说明已完成阶段、缺失证据和原因；
- main fresh CI 必须针对真实 Implementation merge 后目标分支 revision；PR/历史 CI 或 merge API 成功不能替代；
- Change archive 成功只证明施工生命周期冻结，不替代 main-fresh、自然语言 Acceptance 或 Closure Audit；
- Closure 语义由需求追溯 Owner 决定：先重读当前 live Requirement Source，再做 Evidence Mapping；Acceptance 状态写回并重读后才可 close，close 后再次读取；需要 post-merge evidence 时不得用 `Closes` / `Fixes` / `Resolves` 绕过；
- Acceptance checklist/等价状态同步、写后重读、close 或 close 后重读任一失败均保持 `blocked/incomplete`，不能用 cleanup 或最终报告掩盖；
- 没有持久 Change、没有可关闭 Requirement Source，或项目事实证明某一步 `not_applicable` 时不为形式制造对象，但要记录依据；权限/宿主/平台限制导致 required 动作无法执行属于 blocked，不是 N/A；
- 本规则只编排顺序，不复制 REST merge、`expected_head_sha`、archive implementation 或 direct Evidence 的详细实现。

## 6. 分支与 worktree 清理

只清理同时满足“当前仓库 + 当前任务 + 已确认 merged + 非默认/保护分支 + 无其他 active worktree/任务继续使用 + 当前宿主可安全删除”的资源。contributor `fork`、他仓来源分支、无删除权限资源、未合并/其他任务分支不得越权删除；cleanup 必须晚于 required post-merge 验证和 Requirement/Change 收尾，不能为整洁提前删掉诊断/证据恢复需要的资源；宿主不支持安全删除时报告 cleanup gap。删除任务分支不等于授权删除 tag、Release、部署环境或数据。

## 7. 完成判据与回到主流程

### `develop-and-submit`

完成判据是：当前授权范围内的实现/测试/文档/Completion 已完成，PR 当前 head 达到项目定义的 Ready 和 required CI；最终报告必须明确 **PR Ready / 未 merge**，不能把它缩写成完整交付完成。

### `develop-and-deliver` / `review-and-deliver`

完整端到端完成要求所有适用且 required 项成立：Review/CI/merge 门禁、真实 Implementation merge revision、implementation main fresh CI、repository-native Change archive（适用时）、archive governance fresh（项目要求时）、Closure Audit、Acceptance 状态写回与重读、Requirement Source close 后重读、任务分支清理；只有事实依据充分时可记 N/A。任何 required 项受权限/宿主/平台阻塞时只能报告 `blocked/incomplete`，不得把权限阻塞写成完成条件。最终报告逐项给出实际 revision、CI、Change、Requirement Source 与 cleanup 状态，不把“merge 成功”缩写成“完整交付完成”。
