# 系统级分析与代码整洁收口

## 系统级分析与能力归一

系统级分析先于局部实现，但不等于全仓扫描。围绕当前任务沿真实能力链闭合：

```text
入口 / 消费者
→ 调用链、数据流、状态流
→ 能力 Owner / Contract
→ 状态与副作用
→ 现有实现 / tests / docs / ops
→ 方案与验证
```

- 先查同类生产入口和现有实现，区分可复用能力、真实重复，以及因生命周期、安全、事务、版本等边界必须独立的实现。
- 真正隔离时局部修复；已有能力满足语义时**复用现有正确实现**；稳定真实重复时抽**公共实现**；同一能力被多处维护规则、状态或事实时，优先收敛**单一事实源**和明确**能力 Owner**，形成 `Owner → Contract/入口 → 实现/状态 → consumers → tests/docs/ops` 的**统一能力治理链**。
- **不要为抽象而抽象**：只有代码相似但语义、生命周期、失败、安全或事务边界不同，不强行共用。
- 局部补丁若绕过 Owner、制造第三套实现、第二份状态或第二套规则，重新检查复用或能力归一。
- 系统性方案说明复用项、必须保留的差异、公共/统一 Owner、兼容/Migration 和验证闭环。

### Causal / Diagnostic Coverage Gate

诊断、故障处置或性能问题存在跨阶段、异步、并发、部分失败等复合信号时，系统级分析必须沿**当前真实存在**的端到端链检查哪些阶段可能解释当前 symptom。按项目事实选择可能存在的：

```text
入口 / admission
→ 排队 / 调度
→ 并发 / 串行
→ 等待 / 外部 I/O
→ 处理 / 计算
→ 持久化 / commit / flush
→ 结果发布 / 通知
→ retry / timeout / cancellation
→ partial failure / recovery
→ 资源竞争 / pool / lock
→ 消费者状态刷新
```

这是一组**调查维度，不是固定架构模板**：不存在的阶段不得为了模板硬造，也不机械全仓扫描。只读取与当前 symptom、真实调用/数据/状态流和独立 failure boundary 有直接关系的最少充分代码、配置、运行证据、测试与日志。发现某阶段与 symptom 无关时可以有证据地排除；发现新的真实边界时单调扩展调查范围。

在完整根因结论前做 **Omission / Coverage Audit**：检查是否仍有未查看的链路阶段、未解释的症状、未覆盖的独立 failure boundary，或已有因素只能解释部分现象。性能主诉不能遮蔽同一能力链上已被证据确认的 correctness / 数据完整性 / cancellation 等缺陷；但没有证据关联的邻近问题也不能无边界扩大为本任务根因。

## 受影响代码域整洁收口

持久实现完成时，对本次触及文件、模块及直接相邻责任域做整洁审计，使整体清晰、易读、可维护。

- 清理因本次变化确认无用的**死代码**、**废弃分支**、**重复 helper**/wrapper、未使用 import/变量、debug/TODO 和其他**垃圾残留**。
- 删除前不能只看“零引用”；检查 public API/外部 consumer、配置/DI、**反射/动态加载**、**插件注册**、生成代码/脚本、**Migration/回滚**、deprecated/兼容路径等隐式入口。
- **无法确认安全时不删除**，记录未验证项或拆成后续任务。
- **不把代码清理扩大成无关重构**，不覆盖用户工作；历史大清理另立任务。
- 清理后重读受影响文件并重跑目标测试和相关回归。
