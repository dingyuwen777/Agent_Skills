# 方案落地、架构设计与渐进式规划

本 Reference 只在真实**方案讨论 / 技术方案 / 架构设计**场景加载，负责三件事：

1. 把其他聊天、同事、文档、工具或旧时间点形成的方案安全映射到当前仓库；
2. 在确有结构设计问题时判断能力 Owner、接口负担、真实变化点和架构质量；
3. 对路径尚不可完整确定的超大任务使用渐进式规划，直到可以回到正常 Implementation Plan。

普通 L1/L2 实现、路径已经清晰的功能开发，不为了“代码设计得更好”机械加载本 Reference。Planning Contract、Plan Review Gate、TDD、实现与 Re-plan 仍由 [05_设计实施与根因调试.md](05_设计实施与根因调试.md) 负责；多人/多 Agent 的 blocker DAG 与 Wide Refactor 细节由 [09_多人和多智能体并行协作.md](09_多人和多智能体并行协作.md) 负责。

## 1. 外部 / 既有方案先作为 Proposal

来自其他聊天、同事、文档、工具、旧分支或较早时间点的方案首先是 **Proposal**，不是当前仓库事实、Requirement Source 或自动授权。实施前按当前项目真实规则、代码、Contract、Schema/Migration、Manifest/lock、测试、CI 和正式设计核验它的前提。

把影响实施的条目分成：

- **仍成立**：当前事实继续支持，可以沿用；
- **已过时**：版本、代码、接口、架构或约束已变化，按当前事实调整；
- **与当前事实冲突**：先说明冲突和影响，不为了照搬方案改写正确事实；
- **需要 Owner 决策**：只有冲突会实质改变业务语义、public Contract、Schema/数据、安全/权限、不可逆动作或重大技术路线时才提请决定。

保持用户原本要解决的目标和仍有效的已确认决定，不因为方案来自其他会话就全部推翻，也不因为方案写得完整就跳过当前事实核验。落实时建立：

```text
方案目标 / 已确认决定
→ 当前真实 Owner / 入口 / Contract
→ 需要修改的最小实现
→ 直接 Evidence
```

无法映射的方案条目不能静默遗漏，也不能硬塞进不合适模块；如果只是实现位置、局部命名、测试位置等可从当前仓库自行恢复的差异，直接按当前事实调整，不把它升级成用户审批。

## 2. Architecture / Codebase Design

只有任务确实需要新增公共能力、改变稳定模块职责、跨多个调用点重构，或当前结构明显阻碍正确修改/验证时，才进入架构设计判断。以下术语是分析概念，不要求目标项目重命名现有 Service、Module、API 或其他正式术语。

### 2.1 职责与接口

检查：

- **职责集中**：同一业务规则、状态或能力是否有明确 Owner，还是多个调用方各自维护一份；
- **接口负担**：调用者为了正确使用能力必须了解多少方法、参数、调用顺序、错误、配置和内部细节；接口复杂度接近实现复杂度时要警惕浅封装；
- **Pass-through / wrapper**：中间层是否只是转发参数和调用，没有隐藏复杂度、隔离失败边界、提供兼容、复用或可观测价值；
- **Shotgun Surgery**：一个可观察行为变化是否长期迫使大量分散位置同步修改；如果是，先寻找应该集中变化的真实 Owner，而不是继续复制规则。

### 2.2 真实变化点与可测试边界

- 只有行为、依赖或实现已经存在第二种真实变化需要时，才建立可替换 seam / adapter；一个实现加“未来也许会换”不是充分依据；
- 调用者和测试优先通过同一个稳定入口观察行为；如果测试必须绕过公开入口触达大量内部细节，先检查边界是否设计错误；
- 不为了“更易 Mock”复制生产逻辑或制造只服务测试的平行接口；
- 现有局部实现已经正确、清晰、可验证时，不为了套用设计概念扩大成架构重构。

### 2.3 Locality / Leverage

好的结构应尽量让知识、变化、修复和验证集中在正确位置，同时让多个调用者通过较小稳定入口获得足够能力：

```text
Locality
→ 一类变化尽量集中在一个正确 Owner

Leverage
→ 一个稳定入口承载足够行为，避免每个 caller 重复理解内部机制
```

删除一个抽象后，如果复杂度只是重新散回多个 caller，说明它可能在隐藏真实复杂度；如果删除后复杂度反而消失，说明它可能只是无价值转发。这个 deletion test 只作为设计证据，不是自动删除规则。

### 2.4 多方案设计

重大、难逆且存在多个真实边界方案时可以 **design-it-twice**：至少比较两个真实可行设计在以下方面的差异：

- 正确性与业务表达；
- 调用者接口负担；
- Locality / Leverage；
- public Contract / 兼容；
- Migration / 回滚；
- 测试与可观测性；
- 长期维护成本。

比较完成后仍遵守既有 Plan Review Gate。没有真实取舍时不为形式制造第二方案。

## 3. 大型任务渐进式规划

只有任务**明显跨多会话/多阶段，并且当前还无法可靠写出完整实施路径**时使用。普通 L1/L2 或路径已经清晰的 L3 不进入此流程。

先维护最小决策地图：

```text
Destination
→ 最终要达到的可观察结果

Decisions So Far
→ 已有证据支持且仍有效的决定

Current Frontier
→ 当前已经足够具体、可以立即调查或决策的问题

Blocked
→ 已经明确，但依赖前置决定或事实的问题

Not Yet Specifiable
→ 知道后面可能需要处理，但当前连问题边界都无法准确描述的部分

Out of Scope
→ 明确不属于本次 Destination 的内容
```

规则：

1. 只有现在已经能精确描述的问题才进入 Current Frontier / Blocked；
2. 暂时无法准确描述的内容留在 Not Yet Specifiable，不提前编造 ticket、任务数量或完整架构；
3. 每解决一个 Frontier 项，就更新 Decisions So Far、真实 blocker 和新暴露的问题；
4. 只并行真实无依赖的调查/决策；需要人工业务/Contract/数据/安全决定时才提请 Owner；
5. 路径已经清晰、主要未知项能够界定后立即停止决策地图，进入正常 Planning Contract、Vertical Slice、Validation Matrix 与 Implementation；
6. 用户只授权讨论方案时，到正式实施方案为止，不因为“下一步已经清楚”自动修改生产代码或执行 Git。

## 4. 从方案回到实施

正式实施前把结论压缩成当前项目可执行的最小计划，而不是把完整讨论历史塞给实现 Agent：

```text
目标 / 非目标 / 成功标准
→ 当前事实与仍有效决定
→ 当前 Owner / Contract / Schema / 依赖边界
→ Vertical Slices / blockers（需要拆分时）
→ Migration / Rollback（真实存在时）
→ Validation Matrix / 直接 Evidence
→ 仍需 Owner 决策的事项
```

复杂功能的纵向切片默认从真实用户/调用者入口切到可观察结果；多人并行、blocker DAG/frontier 与 expand → migrate batches → contract 的 Wide Refactor 例外按 [09_多人和多智能体并行协作.md](09_多人和多智能体并行协作.md) 执行。

如果当前事实已经推翻原方案的关键机制，先更新方案和必要决策；如果只是文件位置、局部实现、测试位置等可逆细节变化，直接按当前仓库调整，不重复让用户确认已解决的问题。
