# L1 轻量实现与验证路径

本 Reference 专门处理**风险已经被当前事实确认属于 L1** 的轻量实现与验证。它解决一个常见误区：对目标仓库做了持久修改，并不自动意味着必须进入完整 Feature / Bug / Change / Docs / Review 流程。

它不是风险降级通道。进入本路径的前提是当前事实已经足以证明影响隔离；任何隐藏的公共、数据、安全、依赖、运行时、协作或交付边界出现后，必须立即重新路由并升级。

## 1. 两种轻量场景

### 一次性代码 / Scratch

用户只需要 snippet、scratch code、小脚本示例或局部算法实现，并且没有目标仓库持久修改时，继续使用 Coding Core 的 Scratch Fast Path：

```text
确认最少输入 / 输出 / 运行约束
→ 直接实现最小代码
→ parse / compile / run / targeted test
→ 如实报告证据和限制
```

不要为了“没有仓库”制造仓库调查、Change、Docs、Review 或 Git。

### Repository L1 Fast Path

已有目标仓库，且本次会持久修改真实项目文件，但同时满足以下条件时，可以继续保持 L1：

- 行为不变的机械修改，或边界明确、影响隔离的极小修复；
- 不改变 public API / ABI / CLI、公开配置、serialization、文件格式、Schema、Migration 或数据语义；
- 不改变认证授权、Secret、隐私、安全策略、不可逆数据操作或生产写入边界；
- 不改变依赖、Runtime、Package Manager、Build Tool、CI gate、部署、恢复或 Release 机制；
- 不改变跨模块 / 跨消费者 Contract，也没有需要协调的跨 Owner / 多 PR 交接；
- 当前项目规则没有额外要求正式 Change、独立 Review、Docs 更新或更强交付门禁。

**行数、文件数或“看起来很简单”不能单独证明 L1。** 一行 public flag、数据库列、权限判断或数据格式修改仍可能是 L2/L3。

## 2. 最小事实恢复

Repository L1 只读取能直接决定本次正确性的最少事实：

```text
目标路径适用的 AGENTS / CONTRIBUTING / 项目规则
→ 直接相关实现
→ 必要调用点 / consumer
→ 直接相关测试或正常参照
→ 当前分支 / 工作区 / diff（持久修改时）
```

不因为进入正式仓库就机械扫描全部 README、架构、所有 Contract、全部测试或 CI。若调查中发现真实公共/数据/安全/依赖/运行时边界，再退出本路径并按新的风险恢复对应完整事实。

## 3. 最小实现

实现要求：

- 只改当前目标所需的最少代码；
- 不顺手重构、改名、格式化无关文件；
- 不新增未来占位、兼容层、抽象或依赖；
- 保持现有 public behavior、Contract、数据与运行方式，除非当前极小修复的成功标准明确要求局部行为纠正且仍不触及稳定边界；
- 保留用户未提交工作，不使用破坏性 Git 操作。

## 4. 已确认根因的小 Bug

一个 Bug 可以是 L1，但必须同时满足：

- 原始症状和根因已经由当前代码、稳定复现、失败证据或明确正常参照确认；
- 修复点局部、失败边界隔离；
- 不涉及 public Contract、Schema/数据、安全/权限、依赖/Runtime、部署或跨 Owner 语义；
- 可以用低成本回归直接证明修复。

这种任务不应仅因为 `阶段=缺陷修复` 就自动加载完整根因调试规则。最小路径是：

```text
确认已有根因证据
→ 建立或复用最小回归
→ 最小修复
→ targeted validation
→ 相关最小回归
```

如果根因未知、错误跨边界、需要提出和证伪假设、存在 Incident / 性能 / 并发 / 数据一致性问题，必须增加 `执行模式=诊断`，由正式路由加载完整根因调试规则。连续修补不能用 L1 Fast Path 规避根因调查。

## 5. L1 targeted validation

L1 仍然必须验证，但默认只选择**最便宜、稳定、直接证明当前失败边界**的证据。常见形式包括：

- Markdown / JSON / YAML / schema parser；
- compile / typecheck / lint 的受影响目标；
- 单个函数、组件或模块的 targeted test；
- Bug 的最小 regression test；
- CLI 的一个直接 invocation；
- 修改生成物时的 targeted drift / regen check；
- 受影响构建入口在确有独立构建风险时执行。

L1 不需要为了形式建立八层 Validation Matrix，也不因为宿主具备 `测试` 能力或当前正在执行 `验证` 就自动加载完整通用 Validation Reference。

但证据强度不能被夸大：

```text
Unit / Mock ≠ public consumer
Unit / Mock ≠ 真实 persistence/runtime
局部 compile ≠ package/release artifact
```

如果当前目标需要证明这些更强边界，说明风险事实已经超出本轻量路径，应重新路由。

## 6. Docs Impact 与 Review

实现后做一次快速语义判断：

```text
人类需要理解、使用、维护、部署或排障的当前事实是否改变？
```

- 没有改变：`Docs Impact: not_applicable`，不加载 Docs，不制造无意义文档 diff；
- 有改变：进入 Docs targeted/full 的正式路由。

独立 Review 同样按真实触发事实进入，不是 Repository L1 的固定终点。以下事实出现时应升级：

- 用户显式要求 Review/Audit；
- PR/Change Ready 或项目规则要求独立复核；
- 跨 Owner / 多 PR 交接；
- 风险调查升级为 L2/L3。

如果目标分支受保护，只升级到该仓库真实要求的 Git/PR/required checks 流程；**Protected Branch 本身不反向触发 Issue、独立 Change 或 Deep Review。**

## 7. 退出与升级条件

发现以下任一事实后立即退出 Repository L1 Fast Path：

```text
行为变化已经不再是极小且隔离
public API / ABI / CLI / config / serialization / file format
Schema / Migration / 数据语义 / 数据保留删除
认证 / 授权 / Secret / 隐私 / 安全 / 不可逆操作
依赖 / Runtime / Package Manager / Build / CI / deploy / release
跨模块 Contract / 跨消费者 / 跨 Owner / 多 PR
根因未知或需要系统性诊断
正式 Change / Completion Gate / Docs / Review / PR / Release 门禁
```

重新按当前真实事实判断 L2/L3，并加载对应完整 Reference；已经进入轻量路径不能成为继续降级的依据。

## 8. 完成条件

只有同时满足以下条件，才能结束一个 Repository L1 实现：

```text
目标和范围仍然是当前版本
+ 修改保持在已确认 L1 边界
+ targeted validation 有本轮新鲜证据
+ Docs Impact 已判断并闭环
+ 没有遗漏真实 Review / Git / 项目门禁
+ 未验证项和剩余风险已如实报告
```

这条轻量路径减少的是无关上下文和治理成本，不减少正确性、证据和升级责任。
