# 分层测试与验收策略

这份规则用于回答一个常见问题：**一个存在 UI/API/Persistence/外部依赖边界的功能，应该用 Mock、Integration、Contract、Real Cross-component 还是真实 External Dependency Probe 来证明？**

目标不是把所有测试都做成最真实、最昂贵的端到端，而是让每一层证明它最擅长证明的事实，并用少量跨层 Golden Path 证明系统真正接通。

本文件是专项 profile，不是所有项目默认模板。CLI、Library、Mobile、Embedded、Data、IaC 等没有这些真实边界时，使用 [07_通用验证与证据策略.md](07_通用验证与证据策略.md) 的通用维度，不制造 Browser、数据库或 Provider 层。

## 核心原则

默认职责是：

```text
Browser / UI Mock Acceptance
→ 广覆盖用户可见行为和状态

Backend / API / Persistence Integration
→ 广覆盖服务器业务规则、事务/一致性、持久化、异步 Runtime

Contract / Generated Consumer
→ 保证生产者和消费者使用同一机器 Contract

Real Cross-component Golden Path
→ 少量关键路径证明真实组件组装后确实接通

External Dependency / Provider Probe
→ 极少、有界地验证第三方服务、远端环境或硬件当前真实事实；默认不作为普通 CI 回归主力
```

不要把“更接近生产”误解成“所有场景都应该 Real Cross-component”。测试层越真实，通常越慢、越贵、越容易受环境影响，也越难稳定制造失败边界。因此：

- **状态空间广度**优先放在可控、便宜的层；
- **服务器/持久化真实语义**由真实 Backend/API/Persistence Integration 证明；
- **跨组件接线事实**用少量真实链路证明；
- **外部依赖当前事实**用有界 Probe 单独证明；
- 任一层都不得声称证明自己没有实际运行的下游边界。

## 1. Browser / UI Mock Acceptance

### 证明什么

在真实 Browser / UI 运行时中，用可控的 API/HTTP/RPC Mock 或项目已有等价机制驱动界面，证明：

- 页面、路由、菜单、按钮、表单、弹窗/抽屉等真实交互入口可操作；
- enabled / disabled、权限/资格和状态表达正确；
- UI 向服务端发出的 method、URL、query、payload 或等价 request 正确；
- loading、empty、queued、running、retry、partial success、success、failure、cancel 等用户可见状态正确；
- 4xx/5xx、业务错误或项目定义的错误 Contract 被正确显示，并保留必要的 request/correlation 标识；
- 轮询、刷新、A→B→A 切换、缓存失效、跨页跳转和最终结果入口正确；
- UI 不根据猜测编造服务端不存在的历史、状态或结果。

### 默认覆盖宽度

对存在用户界面的业务，Browser / UI Mock Acceptance 通常应是**用户可见状态覆盖最宽的一层**。真实系统难以稳定制造的边界，例如第 2 次 Retry、部分成功、某 Scope 失败、临时服务异常、空页、权限/资格变化，优先在这一层穷举。

### 不能证明什么

Browser / UI Mock **不能单独证明**：

- 真实 Route/Controller/Handler 确实接受该请求；
- 服务端 Validation/业务守卫与 Mock 一致；
- 真实数据库/文件/队列/其他 Persistence 的事务、约束、锁和数据真正写入；
- Worker/Job/Scheduler/后台进程真正执行；
- 外部 Provider/远端服务真正返回数据；
- 从 UI 到最终持久化/异步结果的真实链路已经接通。

例如项目实际使用 FastAPI + Pydantic + PostgreSQL 时，上述边界分别包括真实 FastAPI Route、Pydantic validation 和 PostgreSQL 事务；项目使用 Spring/MySQL、ASP.NET/SQL Server、Go/DynamoDB 等时必须替换成它自己的真实边界。

因此禁止把 `Browser Mock passed` 描述成 `Real Full-stack passed` 或“真实后端已闭环”。

## 2. Backend / API / Persistence Integration

### 证明什么

使用真实服务端入口和任务实际依赖的真实 Persistence/Runtime Dependency，验证：

- Service / Domain / Repository / Handler 等真实业务规则；
- HTTP/RPC status、错误 Contract、validation 和后端边界；
- 数据约束、事务/原子性、锁、幂等、Fencing、Migration；
- Job 创建与 Worker/Handler/后台 Runtime 状态转换；
- 查询、分页、资格判断、current/history 或项目等价读模型、最终持久化结果；
- 失败、重试、取消、并发、接管等服务器状态机。

Persistence 必须跟随项目事实：

- 依赖 PostgreSQL 的 UNIQUE/FK/CHECK、事务隔离、`SKIP LOCKED`、advisory lock 等语义时，使用真实 PostgreSQL；
- 依赖 MySQL/SQL Server/SQLite/DynamoDB/MongoDB/文件系统/对象存储等具体语义时，验证对应真实实现或项目批准的高保真测试环境；
- 不允许用语义明显不同的替代品冒充真实依赖，也不为了“企业级”把实际 SQLite 项目强迫成 PostgreSQL。

### 为什么不把这些都交给 Browser

这些问题多数与 DOM/UI 无关。直接在后端/Persistence 层验证更快、更稳定，失败时也更容易定位根因。

### 不能证明什么

它不能证明真实 Browser/客户端中的交互、视觉状态、按钮条件、导航和跨页面体验正确；也不能单独证明多个真实组件按部署配置组装后一定接通。

## 3. Contract / Generated Consumer

### 证明什么

对存在正式机器 Contract 的边界，验证生产者和消费者说的是同一种语言，例如：

```text
Source Contract / Schema
→ OpenAPI / JSON Schema / protobuf / GraphQL / IDL / public type
→ Generated Client / SDK / Consumer Type（项目存在时）
→ Contract compatibility / drift check
```

如果项目实际使用 Pydantic → OpenAPI → Generated TypeScript Client，这只是该项目的一种实现；Java DTO/OpenAPI、protobuf stub、GraphQL generated types、C/C++ protocol header 等都可以映射到同一职责。

它防止出现：Mock 自己使用字段 A、真实生产者已经改成字段 B，而两边各自测试仍然绿色。

### 不能证明什么

Contract 一致不等于业务行为正确，也不等于数据库/Worker/UI 已真实运行。

## 4. Real Cross-component Golden Path

### 证明什么

让真实关键组件组装运行。例如 Web Full-stack 可能是：

```text
Browser
→ Frontend
→ Generated Client（存在时）
→ Real API
→ Real Persistence
→ Real Worker / Runtime（存在时）
→ Real Persistence
→ Browser 看到最终结果
```

其他项目可能是：

```text
Desktop Client → Real Service → File/DB → refreshed UI
Producer → Real Broker → Consumer → Storage
API → Queue → Worker → Object Store → API Result
```

它回答的是：

> 前面分别验证过的组件，真正连在一起时能不能工作？

### 默认覆盖宽度

Real Cross-component 默认只保留**少量高价值 Golden Path**，通常覆盖：

- 一个最关键成功链；
- 有独立价值时再增加一个代表性失败/恢复链；
- 公共接线、配置、进程边界发生重大变化时增加对应路径。

不要为了覆盖每个 UI 状态复制大量真实跨组件场景。状态穷举优先由 Browser/UI Mock 和 Backend/Persistence Integration 承担。

### 不能证明什么

一条 Golden Path 通过不等于所有错误状态、资格组合、并发边界和外部依赖异常都已覆盖。

## 5. External Dependency / Provider Probe

### 证明什么

仅在任务确实依赖外部系统当前真实能力、字段、分页、错误、计费、权限或硬件行为时，有界调用生产 Adapter/Operation/SDK/Device boundary，验证：

- endpoint / operation / 参数当前可用；
- Sanitized Raw/response shape 与 Mapper/Parser 假设一致；
- pagination / stable ID / capability / protocol 与真实响应一致；
- 必要的费用、限流、权限、错误或设备边界。

### 固定边界

- 默认关闭；
- 不进普通 CI，除非仓库已有明确批准的专门机制；
- 明确请求/费用/数据/设备范围；
- 不打印 Secret；
- 不默认写生产库/生产资源；
- 失败要区分代码缺陷与供应商/网络/权限/硬件环境不稳定。

Fixture/Fake/Mock 回归不能声称证明外部依赖此刻在线；真实 Probe 也不应替代稳定 Fixture/Parser/Mapper/Contract 回归。

## 6. Validation Matrix

L2/L3 Change 在实现前按当前任务边界建立 Validation Matrix。每一层只使用：

```text
required
not_applicable
```

`required` 要写本次要证明的 Scope；完成前补当前 Evidence。`not_applicable` 必须说明为什么该层对当前任务没有独立证明价值，不能为了少跑测试而省略。

推荐模板：

```markdown
| Layer | Required | Scope / Evidence |
| --- | --- | --- |
| Browser / UI Mock Acceptance | required | 用户可见状态、请求 payload、错误/结果闭环 |
| Backend / API / Persistence Integration | required | 业务守卫、真实 Persistence、异步 Runtime（适用时） |
| Contract / Generated Consumer | required | 正式机器 Contract 与消费者/生成物无漂移 |
| Real Cross-component Golden Path | required | 1 条关键成功链真实接通 |
| External Dependency / Provider Probe | not_applicable | 本次不修改第三方/远端/硬件当前能力或协议事实 |
```

矩阵不是固定测试数量配额。例如可以出现很多 Browser/UI Mock、很多 Backend Integration，但只有一条 Real Cross-component；也可以是纯后端任务没有 Browser 层。

## 7. 任务类型默认选择

### 有用户界面的新功能或行为变化

通常：

- Browser / UI Mock Acceptance：`required`，覆盖用户状态空间；
- Backend/API Integration：只要后端行为受影响就 `required`；
- Contract：公共 API/生成 Consumer 受影响时 `required`；
- Real Cross-component：存在跨组件关键链时至少一条 Golden Path；纯前端表现修改可 `not_applicable`；
- External Probe：仅外部依赖当前事实变化时需要。

### 纯后端/Persistence

Browser 可 `not_applicable`；Backend/API/Persistence Integration 通常是主证据。公共 Contract 受影响时补 Contract；存在关键跨进程链时考虑 Real Cross-component。

### Provider / Adapter / Mapper / Parser

稳定 Fixture/Operation/Adapter/Mapper/Parser 测试是主回归；只有需要确认供应商、远端系统或设备当前真实事实时才跑有界 Real Probe。若能力最终暴露给用户，还应在上层补 UI/API/Workflow 证据。

### 纯文档/配置/生成物

记录 TDD 例外，以解析、链接、生成差异、静态检查、构建或仓库一致性为证据；不要为了填 Matrix 编造无价值 Browser/DB/Full-stack 测试。

## 8. Completion Audit 与 Review

进入 Ready 前，不只问“测试是不是绿”，而要问：

1. Requirement 的用户可见行为是否有 Browser/UI 证据（适用时）；
2. 服务器规则和 Persistence 是否有 Backend/真实依赖证据（适用时）；
3. 公共边界是否有 Contract 证据；
4. 是否至少有足够的 Real Cross-component Golden Path 证明关键接线，而没有用 Mock 冒充；
5. 外部依赖事实是否真的需要 Probe；需要时是否有界、可审计；
6. `not_applicable` 是否有真实依据；
7. 是否存在“某一层已经通过，所以跳过另一层独立风险”的错误推理。

Review 必须按证据等级陈述结论，例如：

- `Browser Mock Acceptance passed`；
- `PostgreSQL Integration passed`（项目实际使用 PostgreSQL 时）；
- `MySQL/Filesystem/... Integration passed`（按项目实际依赖）；
- `Real Cross-component Golden Path passed`；

不要笼统写“E2E 全通过”掩盖测试实际使用了 Mock 还是实链。

## 9. 常见反模式

禁止：

- 所有状态都做成 Real Cross-component，导致慢、脆、难制造失败；
- 只有 Browser Mock，却宣称后端/Persistence/Worker 已真实闭环；
- 只有 Backend tests，却没有验证重要用户可见行为；
- Mock 手写第二套与正式 Contract 脱节的类型/字段体系；
- 为了测试方便关闭真实数据库/Persistence 约束；
- 把付费/不稳定外部 Probe 塞进普通 CI；
- 固定“每个功能必须 N 个 Mock + M 个 Integration + 1 个 Full-stack”而忽略实际风险；
- 看到任一层绿色就用它替代 Completion Audit。

## 10. CI / Workflow 成本控制

本节只在 UI/API/Persistence/外部依赖这些专项边界真实存在、并且需要设计或优化永久 CI/Workflow 时生效。通用的 Workflow Responsibility Audit 与 Evidence Preservation Mapping 以前置规则 [07_通用验证与证据策略.md](07_通用验证与证据策略.md) 为准；这里不另造第二套审计协议，只说明怎样保持本文件各层测试的原始职责。

### 不要在不同层重复穷举同一状态空间

默认分工继续保持：

```text
Browser / UI Mock Acceptance
→ 用户可见状态空间最宽
→ loading / empty / retry / partial / errors / route / payload 等便宜且可控地覆盖

Backend / API / Persistence Integration
→ 服务器规则、事务/一致性、约束、异步 Runtime、持久化、并发与错误 Contract 广覆盖

Contract / Generated Consumer
→ 机器接口漂移与生产者/消费者一致性

Real Cross-component Golden Path
→ 少量关键真实接线
→ 不负责穷举所有 UI/错误状态

External Dependency / Provider Probe
→ 只证明外部系统当前真实事实
→ 默认不做普通 CI 的稳定回归主力
```

因此 Workflow 优化可以减少**重复执行**，但不能把这些层直接折叠为一个“更真实的 E2E”。Cross-component 更真实，不代表它更适合覆盖所有状态；Browser Mock 更快，也不能冒充 Backend/API/Persistence Integration。

### 优先消除无关触发

永久 Workflow 的触发范围应与实际风险对应。例如：

- 只改人类说明文档、Agent governance 或其他与产品 Runtime/Contract/用户流程无关的文件时，不应仅因为“仓库有 Full-stack”就机械启动真实 UI + API + 数据库 + Worker；治理/文档自己的必要检查仍要运行；
- 纯前端视觉/局部交互变化，在没有 API Contract、Backend、Persistence 或 Runtime 风险时，可以有依据地不触发数据库/真实后端层；
- 纯后端/Persistence 变化如果没有 UI consumer 行为变化，可以不运行无独立价值的 Browser 状态穷举，但 public Contract 和真正消费者受影响时仍要验证；
- Compose、entrypoint、image、migration、bootstrap、secret/runtime topology 等变化应由 Runtime/Compose 层证明，不能只靠 Unit 或 Browser Mock；
- 外部 operation/真实字段没有变化时，普通业务 PR 不因为“更保险”每次访问真实 Provider/远端系统。

这里的 `not_applicable` 必须来自 changed scope 和真实调用链分析，不能为了 CI 更快事后补理由。

### PR、main、release 可以有不同职责

同一个项目可以合理保留：

```text
PR
→ 快速但充分地阻止错误进入 main

main push
→ 证明合并后的集成状态

release
→ 对实际发布候选 artifact/image/bundle 做不可替代验证
```

这三层即使都出现 build/test 字样，也可能证明不同事实。只有 Workflow Responsibility Audit 证明某次执行没有独立责任后，才可以合并或取消；不能仅按命令文本重复就删除。

### Cross-component 的目标是接线，不是测试数量

Real Cross-component 成本高时，优先检查是否存在这些反模式：

- 同一成功路径因为页面细节变化复制成多条近似场景；
- 已在 Browser Mock 覆盖的大量错误状态又在真实链逐条制造；
- 已在 Backend/Persistence Integration 稳定覆盖的事务/失败组合又通过 UI 驱动一遍；
- 每个 PR 不论改动范围都重建同一完整环境；
- 同一 image/artifact 在多个 Job 重复构建而没有独立身份需求。

优化后仍应保留至少足以证明关键跨组件事实的 Golden Path。需要代表性失败/恢复链时保留，但不固定“每个功能必须一成功一失败”的数量配额。

### External Probe 不能用来替代稳定回归

如果真实 External Probe 慢、贵或受网络/设备影响，正确方向通常是：

```text
稳定 Fixture / Parser / Mapper / Contract 回归
+ 必要时有界真实 Probe
```

而不是：

```text
每个 PR 都打真实外部依赖
```

反过来，如果本次任务就是确认外部系统当前字段/分页/错误/计费/硬件事实，Fixture 也不能因为便宜而冒充当前真实证据。

### 精简完成后的专项反查

UI/API/Persistence/External Dependency Workflow 精简后，至少反查：

1. Browser/UI Mock 是否仍承担用户**状态空间**广覆盖；
2. **Backend / API / Persistence Integration** 是否仍真实运行受影响服务器/持久化边界；
3. Contract / Generated Consumer 是否仍能阻止机器接口漂移；
4. **Real Cross-component Golden Path** 是否仍有足够少量路径证明关键真实接线；
5. **External Dependency / Provider Probe** 是否仍只在真正需要当前外部事实时执行；
6. 是否消除了明确的**无关触发**和**重复**工作，而不是只把测试命令搬到另一个文件；
7. 最终陈述是否仍按每层实际运行的**证据**范围报告，没有用“E2E 全绿”掩盖层级差异。
