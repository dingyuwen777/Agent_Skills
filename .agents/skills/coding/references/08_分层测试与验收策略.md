# 分层证据边界与 Testing Handoff

本 Reference 是 **Coding 的 Evidence Profile**，不是第二套 Testing 方法库。它只回答：当当前 Coding 任务真实存在 UI / API / Persistence / 外部依赖边界时，通用 Validation Matrix 应映射成哪些更具体的证据层、每层最多能支持多强的完成结论、什么时候必须 Handoff Testing。

具体的 Test Strategy、Scenario-based Black-box Acceptance、User Journey、Exploratory Testing、Integration/Contract/Golden Path/External Probe、Regression、Fixture/Fake/Mock/Harness 设计与系统性测试执行，由 [`.agents/skills/testing/SKILL.md`](../../testing/SKILL.md) 及其当前 canonical rules 唯一负责。Coding 保留开发期 TDD、Requirement Traceability、Validation Matrix、Completion Audit 和“本次交付必须证明哪些独立失败边界”的治理责任。

## 1. 从通用验证层映射真实边界

只有项目真实存在对应边界时才映射：

```text
用户 / Workflow Acceptance
→ Browser / UI Acceptance（存在真实 UI 时）

集成 / Persistence / Runtime Dependency
→ Backend / API / Persistence Integration（存在对应服务端/持久化时）

接口 / Contract
→ Contract / Consumer（存在正式机器 Contract 或公共消费者时）

跨组件 Golden Path
→ Real Cross-component Golden Path（存在多个真实组件接线时）

外部依赖 Probe
→ External Dependency / Provider Probe（当前任务确实依赖远端/第三方/硬件事实时）
```

没有 UI 时不制造 Browser；没有数据库时不制造 Persistence；没有外部 Provider 时不制造 Probe。项目实际使用 PostgreSQL、MySQL、SQL Server、SQLite、DynamoDB、文件系统、对象存储或其他依赖时，只能声明实际运行过的真实语义。

## 2. Evidence Boundary

Coding 在 Completion / Review / Delivery 中只允许作与证据边界一致的陈述：

| 证据层 | 可以证明 | 不能单独证明 |
| --- | --- | --- |
| Browser / UI Acceptance | 用户入口、交互、可见状态、请求语义在受测 UI 边界成立 | 真实 Backend/DB/Worker/Provider 已接通 |
| Backend / API / Persistence Integration | 服务端规则、真实 Persistence/Runtime、状态与副作用在受测边界成立 | Browser/客户端真实体验与跨组件接线 |
| Contract / Consumer | Producer/Consumer 的机器 Contract/兼容边界一致 | 业务行为、Persistence、UI 已正确运行 |
| Real Cross-component Golden Path | 少量真实关键组件组装后确实接通 | 全部错误状态、数据组合、并发边界都已覆盖 |
| External Dependency / Provider Probe | 外部系统此刻在有界请求内返回的真实事实 | 稳定回归、未来可用性或未探测场景 |

固定禁止：

- `Browser Mock passed` 不得写成 `Real Full-stack passed`；
- Fake/语义不同的替代依赖不得冒充当前任务真正依赖的 Persistence/Runtime；
- 一条 Golden Path 不得冒充全部状态空间；
- External Probe 不得替代稳定 Fixture/Parser/Mapper/Contract 回归；
- CI 绿色不得替代 Requirement Completeness 或未运行边界。

## 3. Coding 什么时候必须叠加 Testing

如果当前任务只需要开发期最小 Red/Green、局部 Unit/Component Regression，且没有独立测试工程风险，继续留在 Coding。

出现以下任一真实需求时，通过 Router/Handoff 叠加 Testing：

- Test Strategy / Test Gap 设计；
- 用户/调用者 Journey、黑盒或探索式测试；
- 系统性 Integration / Contract / Workflow / Golden Path / Probe；
- Bug 的独立复现、Regression 或复测；
- Fixture/Fake/Mock/Harness 的专业设计；
- Review 发现已有 Evidence 不足，需要新增/调整测试。

推荐协作：

```text
Coding
→ 声明 Requirement / Risk / required Evidence boundary
→ Testing 设计并执行最小充分测试
→ Evidence / Defect
→ 生产缺陷返回 Coding 修复
→ Testing Regression
→ 需要独立合并/发布判断时返回 Review
```

Testing 无法取得时不能用本 Reference 的摘要、旧记忆或 Coding 自己的临时方法冒充专业测试已经完成。

## 4. CI / Workflow 责任

永久 CI/Workflow 的选择、成本、触发、路径过滤、证据守恒和 Branch Protection/Release Gate 影响继续由 [07_通用验证与证据策略.md](07_通用验证与证据策略.md) 负责；本 Reference 不维护第二套 CI 规则。

测试层在 CI 中如何稳定实现，由项目真实测试体系和 Testing 当前 canonical rules决定。较真实层通常更慢、更易受环境影响，因此“更真实”不能推出“所有场景都应该进入 Full-stack/E2E”。任何优化都不得通过删除独立失败边界、降低证据等级、取消必要断言或把外部不稳定性伪装成代码绿色来实现。

## 5. Completion Audit

Coding 在 Ready 前按实际任务反查：

1. 当前 Requirement 的每个独立风险是否有直接 Evidence；
2. 每个 Evidence 是否只声明实际运行的边界；
3. `not_applicable` 是否有项目事实依据；
4. 需要专业测试方法时是否已经 Handoff Testing，而不是在 Coding 中复制第二套方法；
5. 是否存在“某一层绿色，所以跳过另一层独立风险”的错误推理；
6. 未运行的边界是否明确列为未验证，而不是被笼统的“E2E/系统测试通过”覆盖。

这个 Profile 可以告诉 Coding **需要证明什么**，但不能替代 Testing 告诉团队 **怎样设计并执行对应测试**。
