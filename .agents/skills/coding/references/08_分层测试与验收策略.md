# 分层测试与验收策略

本规则只在项目真实存在 Web/UI、API/Service、Persistence/Runtime、Machine Contract、跨组件或外部依赖边界时加载。它回答：**Mock、Integration、Contract、真实跨组件 Golden Path 和 External Probe 分别应该证明什么？**

核心目标不是“越真实越好”，而是让每层证明最适合的独立事实，再用少量真实链路证明组装。

## 1. 推荐职责层

```text
UI / Client Mock Acceptance
→ 广覆盖用户/调用者可见状态和请求语义

Backend / API / Persistence Integration
→ 广覆盖服务端规则、事务/持久化、异步运行边界

Contract / Generated Consumer
→ 保证生产者与消费者使用同一机器 Contract

Real Cross-component Golden Path
→ 少量关键路径证明真实组件组装确实接通

External Dependency / Provider Probe
→ 极少、有界验证第三方/硬件/远端当前真实事实
```

名称可以按项目生态调整，但证明责任不能被改名消除。

## 2. UI / Client Mock Acceptance

在真实客户端运行时中，用可控 Mock/Fake 驱动用户/调用者工作流，验证：

- 页面/视图/命令入口/交互可操作；
- loading、empty、success、failure、retry、cancel 等真实状态；
- enabled/disabled 资格；
- method/URL/query/payload/消息内容等请求语义；
- 错误表达、轮询/刷新、结果入口；
- 客户端不根据猜测编造服务端不存在的历史/状态。

不能单独证明：真实服务路由、真实 persistence、异步 Worker、外部 Provider 或完整跨组件链路。

## 3. Backend / API / Persistence Integration

使用项目真实服务入口和**项目真实 persistence/runtime dependency** 验证：

- Service/domain 规则；
- status/error contract；
- 事务、约束、锁、幂等、并发、Migration；
- 异步 Job/Worker/handler 状态转换（项目实际存在时）；
- 查询、分页、最终持久化结果；
- 失败、重试、取消、接管、资源生命周期。

数据库例子必须跟随项目事实：

- 依赖 PostgreSQL 特有锁/事务语义就使用真实 PostgreSQL；
- 实际是 MySQL/SQL Server/SQLite/MongoDB/DynamoDB/文件系统等，就验证相应真实语义；
- 禁止用语义不同的替代品冒充目标 persistence；
- 也禁止为了“更企业级”强迫原本只依赖 SQLite/文件系统的项目引入 PostgreSQL。

这一层不能证明真实浏览器/客户端体验。

## 4. Contract / Generated Consumer

项目存在机器 Contract 时，验证生产者和消费者说的是同一种语言，例如：

```text
Schema / IDL / API source
→ generated client/types/code
→ compatibility / drift check
```

可能是 OpenAPI、GraphQL、protobuf、JSON Schema、IDL、ABI、serialization schema 等。不能用手写 Mock 类型形成第二套事实。

Contract 一致不等于业务行为正确，也不等于 persistence/客户端已真实运行。

## 5. Real Cross-component Golden Path

让真实关键组件组装运行，例如：

```text
Client → API → Persistence → Async Runtime → Client Result
CLI → Config → Library → Runtime Dependency → Output
Producer → Message → Consumer → Storage
Package Build → Install → Consumer Smoke
```

默认只保留：

- 最关键成功链；
- 有独立价值时一个代表性失败/恢复链；
- 公共接线/配置/进程边界重大变化时对应路径。

不要把所有状态复制成昂贵全链测试。状态广度优先由更便宜层覆盖。

## 6. External Dependency / Provider Probe

仅在任务确实需要确认外部系统此刻真实能力、字段、协议、错误、费用、权限或硬件行为时有界执行。

固定边界：

- 默认关闭；
- 不进普通 CI，除非仓库已有批准机制；
- 明确请求/费用/数据范围；
- 不打印 Secret；
- 不默认写生产数据；
- 失败区分代码缺陷、网络、供应商/硬件和权限；
- Probe 有时效性，不替代稳定 Fixture/Fake/Contract 回归。

## 7. Validation Matrix

L2/L3 按真实风险记录：

| Layer | Required | Scope / Evidence |
| --- | --- | --- |
| UI / Client Mock Acceptance | required / not_applicable | 用户/调用者状态与请求语义 |
| Backend / API / Persistence Integration | required / not_applicable | 服务规则、真实 persistence/runtime、事务/状态机 |
| Contract / Generated Consumer | required / not_applicable | 机器 Contract 与 consumer 漂移/兼容 |
| Real Cross-component Golden Path | required / not_applicable | 少量关键真实接线 |
| External Dependency / Provider Probe | required / not_applicable | 只有外部当前事实需要确认时 |

Matrix 不是固定测试数量配额。

## 8. 任务选择

### 有 UI/客户端的新功能

- UI/Client Mock：通常 required，覆盖用户状态；
- Backend/Persistence：只要服务端行为受影响就 required；
- Contract：公共接口/generated consumer 受影响时 required；
- Cross-component：存在关键真实接线时少量 required；
- External Probe：只有外部当前事实变化时 required。

### 纯 Backend/Persistence

UI 可不适用；Integration 通常是主证据。公共 Contract 变化补 Contract；跨进程关键链存在时考虑 Golden Path。

### External Adapter / Mapper

稳定 Fixture/Adapter/Mapper 测试是主回归；只有需要确认外部当前事实时跑有界 Probe。若能力最终暴露给用户/consumer，还需要上层 Workflow/Contract 证据。

### 纯文档/配置/生成物

记录 TDD 例外，用解析、链接、generated diff、静态检查、build 或仓库一致性为证据；不编造 UI/Persistence/Full-stack 测试。

## 9. Completion Audit / Review

进入 Ready 前检查：

1. 用户/consumer 可见要求是否有适用 Workflow 证据；
2. 服务端和 persistence/runtime 是否有真实 Integration 证据；
3. 公共边界是否有 Contract 证据；
4. 是否有足够的真实跨组件 Golden Path，而没有用 Mock 冒充；
5. External Probe 是否真的必要且有界；
6. `not_applicable` 是否有真实依据；
7. 是否用某一层绿色错误替代另一层独立风险。

结论要按证据等级精确表述，不笼统写“E2E 全通过”。

## 10. CI / Workflow 成本控制

永久 Workflow 优化先按 [07_通用验证与证据策略.md](07_通用验证与证据策略.md) 做 Workflow Responsibility Audit 和 Evidence Preservation Mapping。

默认分工：

```text
Mock/Acceptance
→ 状态空间广度

Backend/Persistence Integration
→ 服务规则、事务、持久化、异步/并发

Contract
→ 机器接口漂移

Cross-component Golden Path
→ 少量真实接线

External Probe
→ 只证明外部当前事实
```

因此可以减少**重复执行**，但不能把不同证据责任直接折叠成一个“更真实的 E2E”。优先消除无关触发、重复 setup/build/install、重复状态穷举，再考虑缓存/artifact reuse/并行/changed-scope。

## 11. 常见反模式

禁止：

- 所有状态都做真实全链，导致慢、脆、难制造失败；
- 只有客户端 Mock 却宣称真实服务/persistence/Worker 已闭环；
- 只有 Backend tests 却忽略关键用户可见行为；
- Mock 手写第二套 Contract；
- 为测试方便关闭真实约束；
- 把付费/不稳定 Probe 偷塞普通 CI；
- 固定“每功能 N Mock + M Integration + 1 E2E”；
- 看到任一层绿色就跳过 Completion Audit。
