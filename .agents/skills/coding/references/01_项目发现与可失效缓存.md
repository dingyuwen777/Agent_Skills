# 项目发现与可失效缓存

## 目标

首次进入仓库时找到高价值事实入口；后续只做廉价失效检查和任务相关读取，避免重复递归搜索。不要试图把整个仓库或需求正文复制进缓存。

“每次扫描最新变动”是指每个独立任务先执行失效检查，并在可见候选事实源变化时刷新索引；不是每一轮对话都重新阅读全部文档。缓存减少重复定位，不能取消任务相关真实文件的重读。

Greenfield / Repository Bootstrap 也使用本发现流程，但此时“没有找到 Manifest/锁文件/CI/Contract”可能只是工程事实尚未建立，不应被误判为现有仓库缺陷。先记录已确认目标、硬约束和缺失的工程事实，再由任务路由决定哪些需要本次建立。

## 触发时机

- 首次进入仓库或缓存缺失：建立索引。
- Greenfield / Prototype 开始建立工程基线：先做一次受限发现，区分已有资料和待建立事实。
- 每个独立开发任务或新工作会话开始：先检查缓存和最新可见变化。
- `pull`、同步、切换分支、rebase、历史改写后：重新检查。
- 规则、需求、Contract、Schema、Migration、清单、配置或测试入口可能变化时：重新检查。
- 同一任务内没有仓库状态变化：复用本次结果，不为形式重复执行。

只读任务未经写入授权时，不创建或刷新磁盘缓存；执行等价的内存内有界检查。

## 发现顺序

1. 定位真实仓库根目录；若从子目录开始，向上寻找版本控制根和规则文件。
2. 先读取根到目标路径上适用的 `AGENTS.md` 或同等规则，并记录优先级；索引同时识别常见的 Claude、Copilot、Cursor、Gemini 和 Windsurf 规则入口，但是否自动生效仍以宿主为准。
3. 识别根 README、贡献说明、需求/PRD/Spec/RFC、架构/ADR、Contract/Schema、Migration、配置、依赖及锁文件、CI 和测试入口。
4. 只沿规则导航和任务关键词读取相关内容。不要因为目录存在就全量加载正文。
5. 排除 `.git`、依赖目录、构建产物、缓存、虚拟环境、符号链接和明显二进制文件。不要读取或缓存 `.env`、凭据、密钥和生产数据。
6. 对实际读到的材料记录路径、适用范围，以及它描述当前行为、目标行为还是背景信息；发现相互冲突时不要静默确定权威性。
7. 有界检查模块边界、前后端分工、API/事件/Schema、数据 Owner、Migration 或契约测试等候选事实；未发现时记录检查范围并跳过，不创建占位架构或规则。
8. 如果仓库几乎为空或只有需求资料，明确进入 Greenfield：缺失项先作为“尚未建立”记录，不自动从个人经验补全框架、目录、数据库或 CI。

## 持久索引

标准路径固定为：

```text
.agents/project-context.json
```

这个路径属于项目根目录下的 `.agents/`。它是**本地可失效导航缓存，不提交 Git**；目标项目应通过 `.gitignore`、本地 exclude 或等价机制避免把它加入版本控制。不能为了共享缓存而把它当作团队事实源。

项目缓存中的 `generated_at` 必须使用北京时间 `Asia/Shanghai`（UTC+8），ISO 8601 值保留明确的 `+08:00` 时区偏移；不得依赖宿主机器本地时区，也不得把 UTC 时间伪装成北京时间。

索引只保存：

- 相对路径；
- 事实源分类；
- 文件大小和 SHA-256；
- 文档首个标题；
- 高价值目录摘要；
- `package.json` 中实际存在的 scripts；
- 生成器版本和 Git 基线信息；
- 使用北京时间并带明确偏移的生成时间。

不要保存绝对路径、需求正文、源代码摘要、凭据或推断出的架构结论。每个克隆、worktree 或本地工作目录维护自己的缓存，并在使用前执行失效检查。

## 首次运行

只有在项目写入已获授权且宿主有持久文件系统时才落盘：

```text
python <skill>/scripts/coding.py discover --root <repo> --json
```

检查输出中的 `documents` 和 `directories`，然后读取本次任务所需的真实文件。脚本只发现入口，不替代人工理解。

如果任务是只读分析或 Review：

- 可以运行只读目录和文件检查；
- 未经授权不要创建或刷新 `.agents/project-context.json`；
- 在当前会话内维护临时导航；
- 明确说明没有形成跨会话缓存。

如果是 Greenfield：

- 允许 `documents` 很少甚至为空；
- 缺少 Manifest/lock/test/CI 只说明这些事实尚未建立；
- 先按 `02_跨项目研发任务路由.md` 的 Greenfield 流程确认哪些基线属于本次目标；
- 新建基线后重新 discover，让缓存反映已经真实建立的事实。

## 后续运行

再次运行同一命令：

- `cache_hit`：候选事实源没有可见变化。复用路径索引，但仍读取目标实现、调用链和相关测试。
- `refreshed`：候选路径、内容、Git 历史或工作区状态影响了索引，已重建。
- `created`：此前没有可读索引。

Git 仓库优先比较已索引提交、工作区候选文件状态和相关路径；非 Git 仓库比较候选路径及已知文件指纹。普通源代码内容变化不会强制重建文档索引，因为实现任务仍会直接读取真实代码。`cache_hit` 只能支持“未发现候选事实源变化”，不能支持“仓库没有任何变化”。

## 必须刷新或重建的情况

- 缓存 schema 或生成器不兼容；
- 缓存损坏；
- 关键规则、需求、Contract、Migration、清单或测试入口新增、删除、移动或修改；
- Git 历史改写导致旧基线不再是当前提交祖先；
- 缓存来自另一仓库、克隆/worktree 或路径逃逸；
- 用户明确要求完整刷新。

刷新失败时保留原错误并重新做受限发现。不要静默使用已知过期的索引。

## 缓存的正确用途

缓存回答“事实源在哪里”，不回答“当前实现一定怎样”。执行任务时至少重新读取：

- 任务涉及的规则和需求；
- 实际入口和调用链；
- 数据流、接口或配置；
- 相关测试和错误处理；
- 当前 Git diff 与工作区状态。

如果缓存与仓库冲突，以仓库当前内容为准并刷新缓存。

缓存没有列出某类仓库约束时，只能说明“在本次受限发现范围内未找到”。若当前任务不依赖该约束，跳过；若缺失事实会改变接口、数据或验收结果，停止实质修改并请求决策。Greenfield 场景则按路由把确需建立的缺失事实纳入设计，而不是把缺失本身当现有系统错误。

## 无脚本或无持久文件系统

使用宿主自带文件搜索按同一分类进行受限发现。不要创建另一种平台专属缓存格式。无法持久化时明确说明后续新会话仍可能重新发现；不要承诺“以后不再扫描”。
