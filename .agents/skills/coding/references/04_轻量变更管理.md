# 轻量 Change 管理

## 原则

重要变化需要可独立理解、实现和验收的施工契约。复杂度通过同一变更记录的章节深度增加，不通过固定生成多套 proposal/spec/design/tasks 增加。

Change 是**施工契约**，不是自身的上游需求全集：

```text
用户已确认决定 / 正式 Roadmap / Spec / Feature/Release 完成定义
→ 当前变更契约
→ 实现
→ 测试与运行证据
```

## 1. 先选治理载体，不发明平行制度

Requirement Traceability、Validation Matrix、Completion Audit 是通用语义；文件目录和第三方格式不是。

顺序：

1. 先发现项目已有 Change/RFC/Spec/OpenSpec/Issue/ADR 等正式治理；
2. 如果现有机制能完整承载目标、成功标准、范围/非目标、上游追溯、验证计划/证据、完成审计和交付状态，优先使用；
3. Coding CLI **只解析 `coding-change/v1`**，不会擅自改写未知第三方治理格式；
4. 如果项目原生治理不能直接被 Coding CLI 解析，但项目要求继续用原生治理，则按项目机制执行人工/项目自有机器门禁；
5. 只有明确选择 Coding 自带载体时才创建 Coding Change；发现已有治理但无法无损映射时，不静默再造平行体系。

## 2. Coding Change 当前 schema

只有：

```text
coding-change/v1
```

不读取、不迁移、不兼容历史 schema。旧 schema 若存在，应先由项目明确迁移/删除策略；本 Skill 不提供兼容分支。

## 3. Coding Change root

默认 fallback：

```text
.agents/changes/
├── active/
└── archive/
```

如果目标项目已经明确使用受支持的：

```text
changes/active/
changes/archive/
```

CLI 会沿用它，避免为了目录偏好制造第二套。

需要显式选择时使用：

```text
--change-root <repo-relative-path>
```

Change root 必须是安全仓库相对路径，不允许绝对路径或 `..` 逃逸。

## 4. 何时需要

- L1：通常不创建 Coding Change；
- L2：新功能、行为变化、重要 Bug、多文件修改、多人并行或需要正式追踪；
- L3：public API/ABI/CLI/格式、Schema/Migration、跨模块 Contract、架构、认证授权、安全、部署、重大依赖或破坏性兼容变化。

如果项目已有等价治理，使用它而不是额外创建 Coding Change。

## 5. ID 与元数据

Coding Change ID：

```text
CHG-YYYYMMDD-kebab-case
```

Frontmatter 至少包含：

- `schema`、`id`、`title`、`level`、`status`；
- `owner`、`branch`、`created`、`updated`；
- `completion_gate`；
- `depends_on`；
- `affected_areas`、`affected_paths`；
- `contracts`、`data_changes`。

新模板固定：

```text
completion_gate: required
```

元数据来自仓库事实或已确认设计。不存在 Contract/数据资源/Owner/Migration 时使用空列表，不为完整感造名字。

## 6. 必需内容

每个 Coding Change 至少写：

1. 目标；
2. 可观察成功标准；
3. 范围与非目标；
4. 必须保持不变；
5. 已确认关键决策；
6. Requirement Traceability；
7. Validation Matrix；
8. Completion Audit；
9. 小而完整任务；
10. 验证计划和本轮新鲜证据；
11. 文档影响；
12. Commit/PR/发布状态。

L3 再增加：方案比较、公共兼容策略、Migration/部署顺序、回滚、安全/性能/运维风险和用户确认的上游决策。

## 7. Requirement Traceability

来源可以是：

- `user:<标识>`；
- 仓库正式 Roadmap/Spec/Feature/ADR/README/规则中的上游要求；
- 必要外部事实源 `external:<标识>`；
- 仓库相对路径/URL。

当前 Change 不能引用自己作为 Requirement Source。

状态只允许：

```text
satisfied
explicitly_deferred
not_applicable
not_satisfied
```

Ready 前 `not_satisfied` 必须清零；Source/Evidence 不能保留占位值。

## 8. Validation Matrix

默认判断：

```text
行为 / Unit / Component
接口 / Contract
集成 / Persistence / Runtime Dependency
用户 / Workflow Acceptance
跨组件 Golden Path
外部依赖 Probe
Build / Package / Runtime
Docs / Governance / Other
```

每层只写 `required` 或 `not_applicable`。测试数量按风险决定，不设置固定配额。Web/UI/API/Persistence 等真实存在时可映射到 [08](08_分层测试与验收策略.md) 的专项层。

## 9. Completion Audit

进入 `ready_for_review` 前完成：

1. `upstream_re_read`：重新读取上游事实源；
2. `change_coverage`：比较上游要求与当前变更，找遗漏；
3. `reverse_audit`：按真实项目边界做反向能力审计，并复核 Validation Matrix；
4. `unresolved_cleared`：`not_satisfied` 清零，延期/不适用有依据。

## 10. 状态

```text
proposed → approved → in_progress → ready_for_review → done
                         └────────→ blocked
```

- 没有真实批准时不伪造 `approved`；
- `blocked` 只用于真实阻塞并记录解除条件；
- 代码写完但尚未完成集成通常是 `ready_for_review`；
- `done` 后不得继续留在 active；
- 机器门禁通过不能替代业务语义 Review。

## 11. Ready Check

Coding Change：

```bash
python .agents/skills/coding/scripts/ready_check.py --root . --require-active-ready
```

显式 carrier：

```bash
python .agents/skills/coding/scripts/ready_check.py --root . --change-root .agents/changes --require-active-ready
```

PR 可使用 `--changed-since <base-sha>` 只要求本 PR 变动的 gated Active Change Ready。

## 12. 需求变化与归档

- 完成前改变同一目标：先回上游要求和 Traceability，再更新当前变更；
- 目标根本变化：关闭/冻结原变更，创建新单元；
- 已归档后新需求：创建新变更，不改写历史；
- 不得通过删除 `completion_gate`、降低状态或改成“后续优化”绕过门禁；
- 归档仅表示治理记录完成，不自动证明代码已合并/发布；归档时 Commit/PR/发布状态必须如实记录。
