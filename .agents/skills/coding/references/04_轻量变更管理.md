# 轻量任务契约与 Change 管理

## 原则

先把“任务必须想清楚”与“必须新增一份持久 Change 文件”分开。L2/L3 都需要目标、成功标准、范围、不变项、风险和验证足够明确，但只有真实需要长期协作、审计或正式完成门禁时，才升级成独立持久施工契约。

**最小充分任务契约**可以由当前已经确认、可供执行和审查的事实承载，例如本轮用户决定、PR body、Issue/工单、Spec/OpenSpec/RFC、项目已有 Change/Proposal；不为了形式重复生成第二份 `CHANGE.md`。

当确实使用 Change 时，把一个重要变化作为一个可独立理解、实现和验收的工作单元。复杂度通过同一施工契约的章节深度增加，不通过固定生成 proposal、spec、design 和 tasks 四套文件增加。

Change 是**施工契约**，不是自身的上游需求全集。正式 Stage / 子 Stage / Roadmap / Feature / Release 单元必须保持：

```text
用户已确认决定 / 正式 Roadmap / Spec / Stage / Feature 完成定义
→ 当前 Change / 项目等价施工契约
→ 实现
→ 测试与运行证据
```

不能因为 Change 自己的成功标准全部勾选，就跳过对上游完成定义的重新核对。

## 何时创建或认领施工契约

- L1：行为不变的机械修改，或边界明确且影响隔离的极小修复。不要为形式创建 Change。
- L2：必须建立**最小充分任务契约**，但默认不要求独立持久 Change。只有出现跨 Owner、跨 PR、跨会话长期开发、复杂依赖/阶段、正式审计、项目规则明确要求变更记录，或本任务确实需要 Completion Gate 时，才创建或认领独立施工契约。
- L3：公共 API/ABI/CLI/数据格式、Schema、Migration、跨模块 Contract、架构、认证授权、安全、部署、重大依赖或破坏性兼容变化，必须有稳定的持久施工契约，并补充方案比较、Migration、部署、回滚和风险。

因此：

```text
L2 ≠ always CHANGE.md
L2 = 任务目标和验收必须清楚
L3 = 持久施工契约 + 深度治理
```

发现隐藏影响时把 L1 升为 L2、把 L2 升为 L3。不要为了少写文档而降级，也不要为了展示流程完整性预付没有真实价值的治理文件。

## 先发现项目已有治理，不制造平行制度

L2/L3 在**确实需要持久施工契约**时，先检查目标仓库是否已有正式变更治理，例如：

- OpenSpec；
- RFC / ADR / Design Proposal；
- GitHub/GitLab Issue + PR 约定；
- 项目自己的 `changes/`、`specs/`、`proposals/`；
- 其他由 `AGENTS.md`、`CONTRIBUTING` 或 CI 明确要求的载体。

如果已有载体能够承载当前任务实际需要的：

```text
目标 / 成功标准
范围 / 非目标 / 不变项
关键决策
Requirement Traceability
Validation Matrix
Completion Audit
任务与验证证据
交付状态
```

就复用项目已有载体，不为了 Coding 再创建平行 Change。普通 L2 如果当前最小充分任务契约已经足够，且不存在持久化/门禁需要，也不因为“项目没有 Change 系统”而自动创建 Coding Change。

如果已有机制不能承载当前任务**实际 required** 的语义：

- 不静默降低需求追溯、验证或已存在的 Completion Audit 门禁；
- 先按项目规则判断是否允许增加最小附属记录；
- 需要实质改变项目治理时按上游设计决策处理；
- Coding CLI 不猜 OpenSpec/RFC 等第三方 schema，也不自动改写它们。

只有任务需要持久施工契约、项目又没有可复用治理机制时，才使用 Coding 自带 Change。

## Coding Change carrier、目录和 ID

Coding 自带 Change 使用当前唯一 schema：

```text
coding-change/v1
```

**不读取、不迁移、不兼容旧 Change schema。** 发现旧格式时应按目标项目自己的历史/迁移策略显式处理，不能让工具默默接受后继续。

默认 carrier：

```text
.agents/changes/
├── active/
│   └── CHG-YYYYMMDD-short-name/
│       └── CHANGE.md
└── archive/
    └── YYYY-MM/
        └── CHG-YYYYMMDD-short-name/
            └── CHANGE.md
```

如果目标仓库已经正式使用顶层：

```text
changes/active/
changes/archive/
```

承载同一类 Coding Change，工具沿用该现有 carrier，不为通用化强制搬迁。

如果仓库存在 OpenSpec 等不同治理体系、又不存在已确认的 Coding carrier，`new-change` 必须拒绝静默创建平行目录，并要求先按项目规则确定承载方式。

ID 使用 `CHG-YYYYMMDD-kebab-case`。一个 Change 默认只有一个 Owner 和一个主分支；协作者写进任务或决策区，不并列多个模糊 Owner。

## 必需元数据

Coding 自带 `coding-change/v1` 保持 frontmatter 扁平，便于没有 YAML 依赖的工具读取：

- `schema`；
- `id`、`title`、`level`、`status`；
- `owner`、`branch`、`created`、`updated`；
- `completion_gate`；
- `depends_on`；
- `affected_areas`、`affected_paths`；
- `contracts`、`data_changes`。

新模板固定：

```text
schema: coding-change/v1
completion_gate: required
```

它表示**一旦选择 Coding Change 作为持久施工契约**，该 Change 在进入 Ready/Archive 时必须通过 Requirement Traceability 与 Completion Audit 门禁；不是说所有 L2 都必须先创建这个文件。

不要用自然语言“可能改很多地方”代替影响元数据。路径尽量写仓库相对目录或文件；Contract 和数据资源使用仓库既有正式名称。

元数据必须来自仓库事实或已确认设计。仓库没有适用的 Contract、数据资源、模块 Owner 或 Migration 时，对应列表使用 `[]`，不得为显得完整而造名称。只有本次需求明确建立新接口或数据资源、且其名称和边界已通过设计门禁时，才记录计划中的新对象。

`coding.py` 对当前 schema、必需字段、状态、依赖 ID 和安全相对路径执行严格校验。任一 Active Change 损坏或使用不受支持的结构时，状态与冲突检查会失败并要求先修正记录；不要把无法解析的记录静默当成“无冲突”。

## 必需内容

每个新的 Coding Change，或项目等价**持久施工契约**，至少写清：

1. 目标；
2. 可观察成功标准；
3. 范围与非目标；
4. 必须保持不变；
5. 已确认关键决策；
6. Requirement Traceability；
7. Validation Matrix；
8. Completion Audit；
9. 小而完整的任务；
10. 验证计划和本轮新鲜证据；
11. 文档影响；
12. Commit、PR 和发布状态。

L3 追加：

- 2–3 个可行方案和推荐依据；
- 公共接口或数据兼容策略；
- Migration 与部署顺序；
- 回滚方式；
- 安全、性能和运维风险；
- 用户确认的上游决策。

方案比较从目标、硬约束和必要机制出发，至少包含保留现有路线的最小增量方案；推荐的是当前证据下的最优可行解，不宣称未经测量或无法证明的绝对最优。

Greenfield L2 先使用与当前探索/实现阶段匹配的最小充分任务契约；只有命中上述持久化条件时才升级为本节完整结构。Greenfield L3 仍要求持久施工契约。“必须保持不变”可以来自用户已确认约束、预期平台、兼容目标和组织政策；不存在的旧 API/Schema 不要伪造为兼容对象。

## Requirement Traceability

对 `completion_gate: required` 的 Coding Change，或项目等价 gated 单元，编码前从上游事实源提取当前单元要求并维护追溯。来源可以是：

- 本轮用户明确批准决定：`user:<简短标识>`；
- 仓库内正式 Roadmap、Spec、Stage/Feature 完成定义、Blueprint/Guide/README 中适用的上游要求；
- Greenfield 的正式需求、环境和已确认技术决策；
- 必要时显式外部事实源，但不能用当前 Change 自身代替正式需求来源。

状态只允许：

```text
satisfied
explicitly_deferred
not_applicable
not_satisfied
```

规则：

- `satisfied` 必须有实际实现/测试/运行证据；
- `explicitly_deferred` 必须有正式批准的延期依据；
- `not_applicable` 必须说明为什么当前单元不适用；
- `not_satisfied` 可以在开发中存在，但进入 `ready_for_review` / 等价 Ready 前必须清零；
- Source、Evidence 不得在 Ready 时保留 `TBD/TODO/待确认/待实现/尚未验证` 等占位内容；
- 机器检查只能验证结构、状态、占位符和仓库路径存在性，不能替代语义判断。

普通轻量 L2 即使没有独立 Change，也必须能说明“本次目标/验收来自哪里”，但不为了满足表格格式而生成一份新的持久载体。详细强门禁见 [10_完成定义追溯门禁.md](10_完成定义追溯门禁.md)。

## Validation Matrix

对 L2/L3，在实现前根据当前任务的真实失败边界选择验证层，并在完成前补新鲜证据。Validation Matrix 首先是一种**验证思维与证据选择**；轻量 L2 可以在内部计划、PR body 或项目已有载体中保持最小等价记录，不要求为了矩阵单独创建 Change。

通用规则见 [07_通用验证与证据策略.md](07_通用验证与证据策略.md)。默认从以下语义维度判断：

```text
行为 / Unit / Component
接口 / Contract
集成 / Persistence / Runtime Dependency
用户 / Workflow Acceptance
跨组件 Golden Path
外部依赖 Probe
Build / Package / Runtime
Docs / Governance / Other
```

每一层只写：

```text
required
not_applicable
```

规则：

- `required`：写清这层要证明的独立风险和 Scope，完成前补当前测试/运行证据；
- `not_applicable`：写明为什么该层对当前任务没有独立证明价值；
- 不要求每个任务机械执行全部层；
- Unit/Component 不能冒充 public consumer、真实 persistence/runtime、package 或跨组件接线；
- Mock/Fake 不能声称证明没有实际运行的数据库、文件系统、外部服务、设备或进程；
- Golden Path 默认只保留少量关键真实接线，不用它穷举全部状态；
- 外部依赖 Probe 只有真实第三方/硬件/远端事实需要确认时才执行，并保持有界、可审计、默认不进普通 CI；
- Build/Package/Runtime 在源代码测试无法证明产物或启动事实时承担独立证据；
- 测试数量由行为边界与风险决定，不设固定配额。

项目真实存在 Web/API/PostgreSQL/Provider 边界时，再叠加 [08_分层测试与验收策略.md](08_分层测试与验收策略.md) 的专项层：

```text
Browser Mock Acceptance
Backend/API/PostgreSQL Integration
Contract / Generated Client
Real Full-stack Golden Path
Real Provider Probe
```

这些专项细节全部保留：Browser Mock 负责广覆盖用户可见状态但不能冒充真实 API/DB/Worker；Backend/PostgreSQL 负责服务器规则、事务和持久化；Contract 防机器接口漂移；Real Full-stack 只用少量 Golden Path；Provider Probe 只有真实外部事实需要确认时有界执行。

CLI、Library、Mobile、Embedded、Data、IaC 等没有这些边界的项目不为了模板制造 Browser/PostgreSQL/Provider 层，而应使用通用矩阵中真实对应的 Workflow、Runtime、Build、Device、Plan 等证据。

Validation Matrix 是语义验证计划，不由 `ready_check.py` 自动判断测试是否充分；Agent/Reviewer 必须检查每个 `required` 层的 Evidence 是否真的证明对应风险。

## Completion Audit

对持久 gated Change，进入 `ready_for_review` / 项目等价 Ready 前，不先按当前 Change 的 checklist 验收，而是重新读取上游事实源并执行：

1. `upstream_re_read`：独立重建上游完成定义；
2. `change_coverage`：比较上游要求和当前 Change，寻找 requirement omission；
3. `reverse_audit`：对适用边界做反向能力审计，并复核 Validation Matrix 的 required/not_applicable 与证据等级；
4. `unresolved_cleared`：确认 `not_satisfied` 清零，延期/不适用都有依据。

轻量 L2 没有独立 gated Change 时，不制造一份形式化 Completion Audit 文件；但在给出强完成/可交付结论前仍要重新核对当前任务的上游目标、验收和未验证项，确保没有因为省掉文档而省掉语义检查。

反向审计按项目真实边界选择，例如：

- 前后端：`后端能力 → 前端入口` 与 `前端动作 → 后端真实支持`；
- CLI：`public command/flag → handler → stdout/stderr/exit/副作用`；
- Library/SDK：`public API → consumer`；
- 异步：`请求 → 状态/错误/恢复 → 最终结果`；
- Schema/Migration：`writer → migration → reader/consumer`；
- Package/Release：`source → artifact → install/startup`；
- Infra：`config → render/plan → runtime/deploy boundary`（仅在授权范围）；
- Greenfield：`确认的目标/约束 → 新建工程基线 → build/test/package/startup → 最小用户/consumer 结果`。

没有对应边界时记录不适用依据，不制造新机制。

## 状态

Coding 自带 Change 只使用：

```text
proposed → approved → in_progress → ready_for_review → done
                         └────────→ blocked
```

- 没有用户或项目要求的批准时，不伪造 `approved`。
- 仅在真实阻塞时用 `blocked`，并记录阻塞条件。
- 代码写完但尚未集成通常是 `ready_for_review`，不是 `done`。
- 对 gated Change，进入 `ready_for_review` 前必须完成 Traceability、Validation Matrix、Completion Audit 和机器 Ready Check；CI 全绿不能替代上游需求完整性复核。
- 完成声明必须有成功标准、测试、文档、Requirement Traceability、Validation Matrix、Completion Audit 和 Git 状态证据；这里的形式化字段只约束已经选择的 gated Change，不把普通轻量 L2 反向升级成 Change。

项目已有治理使用不同状态名时，不要求改成这些英文状态；必须建立语义等价关系，并按项目自己的机器 gate 和状态流程执行。

Coding Change 本地最终检查：

```bash
python .agents/skills/coding/scripts/ready_check.py --root . --require-active-ready
```

PR CI 若使用 Coding Change，可通过 `--changed-since <base-sha>` 只要求当前 PR 改动的 gated Active Change Ready，避免其他并行 Change 阻塞；main push 可以要求当前 carrier 中所有 gated Active Change Ready。项目现有 CI 若已有更严格规则，继续遵守。

## 需求变化

- 有持久施工契约时，完成前改变同一目标：先回到上游要求，更新 Traceability，再更新当前 Change/项目等价施工契约；在关键决策中记录重要取舍。
- 轻量 L2 没有独立 Change 时，同一目标发生实质变化也必须更新当前最小任务契约/PR body/正式来源，并重做受影响验证；不能因为没有 Change 就让范围漂移不可见。
- 目标或范围根本改变且存在 Change：关闭或冻结原 Change，创建新 Change。
- 已归档后出现新需求：创建新的适当工作单元，不改写历史。
- 不得通过删除 `completion_gate`、降低项目现有 gate 或把未满足项静默改成“后续优化”绕过门禁。

## 当前事实与历史

README、正式需求、Contract、Schema 和架构文档描述系统现在是什么。归档 Change/ADR/历史记录保存为什么改变、当时如何选择以及如何验证。不要要求维护者通过顺序阅读所有历史 Change 才能理解当前系统。

## 归档门禁

只有已经使用持久 Change/等价施工契约的任务才存在本节归档动作；不要为了“有归档记录”给原本不需要 Change 的任务补建再归档。

归档前逐项确认：

- gated 单元状态已经达到项目定义的完成态；Coding Change 为 `done`；
- Requirement Traceability、Validation Matrix 和 Completion Audit 仍完整；
- 成功标准有证据；
- 目标和相关测试已运行；
- 静态检查、类型检查和构建按影响范围完成；
- 正式文档已同步或有无需同步的依据；
- 兼容、Migration、部署与回滚状态明确；
- Commit、PR、合并或发布状态如实记录。

Coding 自带归档仅移动 Git 文件，不自动代表代码已合并或发布。未经授权不要提交、推送、合并或部署。
