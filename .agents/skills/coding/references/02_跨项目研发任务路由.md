# 跨项目研发任务路由

这份规则回答：**本次任务应该加载哪些研发流程，而不是把所有规则机械套到所有项目？**

它把 Coding 的固定质量门禁与项目形态、研发阶段、实际语言/工具链和任务风险组合，使同一套 Skill 可以用于 Greenfield、Library、CLI、Web、Backend、Mobile、Data、Embedded、Infra、Monorepo 等项目。

## 1. 四维路由

```text
项目形态
× 研发阶段 / 任务类型
× 编程语言 / 工具链
× 风险等级 L1 / L2 / L3
→ references
→ Validation Matrix
→ Change / Review / Git 门禁
```

四个维度互相独立：

- Python 不等于 Backend；
- TypeScript 不等于 Frontend；
- Web 不等于某一种数据库；
- 同一仓库可以同时匹配 Full-stack + Monorepo + IaC；
- 空仓库不等于“可以随意选择任何默认架构”；
- 文件数量/代码行数不能降低接口、数据、安全或部署风险。

## 2. 路由卡

在计划或 L2/L3 变更契约中至少明确：

```text
执行模式：只读分析 / 诊断 / 方案 / 实现 / Review / Git / Release / 运维
项目形态：真实匹配的一个或多个形态
研发阶段：Greenfield / Onboarding / Design / Feature / Bug / Refactor / Review / Delivery / Migration / Security / Spike
语言 / 工具链：实际版本事实、Manifest、lock、build/test 入口；Greenfield 则写已确认选择
风险等级：L1 / L2 / L3
影响边界：模块、接口、数据、配置、运行时、外部依赖、用户行为
选中的 references：为什么适用
Validation Matrix：哪些 required / not_applicable
Git 授权：分支、提交、PR、合并、发布权限
```

## 3. 项目形态

### Library / SDK

关注 exported/public API、package/module compatibility、serialization/ABI/semver、examples/docs、package artifact。不要机械要求 Browser、数据库或部署。

### CLI / Developer Tool

关注 command/argument/stdin/stdout/stderr、exit code、filesystem/process/environment、cross-platform、安装/package artifact。用户验收可以是真实 CLI workflow。

### Service / Backend / API

关注 request/response 或 RPC/event contract、domain/service rule、persistence/runtime dependency、concurrency/transaction/retry、observability/security/runtime。只有真实依赖存在时才加载对应专项。

### Frontend / Web UI

关注 route/state/component、交互、accessibility、network contract、build/runtime asset。后端不在本仓库时不要把 Mock 描述成真实 Backend 证据。

### Full-stack Application

至少有两个真实组件边界。区分组件自身行为证据和跨组件真实接线证据；Golden Path 只证明关键链路，不穷举状态。

### Mobile / Desktop

关注 View/State、platform SDK、device/simulator、permissions/storage/network、signing/build/package。不要强加 Browser 测试术语。

### Data / Batch / ETL / ML

关注 input schema、deterministic transform、data quality、partition/checkpoint/idempotency、model/artifact/version、orchestration/reproducibility。不要用昂贵在线模型替代稳定回归。

### Embedded / Systems

关注 compiler/toolchain/target、memory/concurrency/timing、hardware abstraction、protocol/binary format、simulator/HIL/device。Host 测试不能冒充 Target/HIL。

### Infra / IaC / Build / Release Tooling

关注 declarative config、build graph、image/package、plan/diff、environment/secret、deploy/rollback。`validate`、`plan`、dry-run 和真实 apply/deploy 是不同证据等级；未授权不得改真实环境。

### Monorepo / Polyglot

确认 repo root、workspace/module root、共享 Contract/Schema、root/子目录规则优先级、多套工具链、changed scope 的下游消费者。不要把一个子项目的工具替换成全仓默认。

### Documentation / Configuration / Migration-only

允许 TDD 例外，但仍需要格式匹配的解析、链接、schema、dry-run、generated diff、build 或运行验证。

## 4. Greenfield / Repository Bootstrap

Greenfield 是正式研发阶段，不是“没有规则”。

开始前先形成：

```text
业务/产品目标
目标用户/调用者
可观察成功标准
范围与非目标
安全/隐私/合规硬约束
数据持久化与生命周期要求（若存在）
运行环境/目标平台
性能/容量/SLO（确实需要时）
部署/交付方式约束
已有外部 Contract/协议/资产
```

然后区分：

- **已确认决定**：直接执行；
- **可验证外部事实**：查官方一手资料；
- **上游取舍**：会改变接口、数据、兼容、部署或长期维护时才提请用户/Owner；
- **实现细节**：在约束下选择最小充分方案，不把个人偏好升级成业务决策。

复杂技术路线至少比较 2–3 个真实方案，其中必须包括“最小现有/简单路线”。确认后只建立必要基线：Runtime/Compiler、Manifest/lock、目录、最小测试/build、必要 CI。不要提前引入数据库、消息队列、微服务、插件系统、复杂发布链或兼容层。

### Prototype / Spike

必须写明：

- 非生产性质；
- 临时放宽的工程约束；
- 不能放宽的安全/数据/凭据边界；
- 成功/失败退出判据；
- 生产化前需要补齐的 Contract、测试、可靠性、部署和文档。

探索结果不能直接冒充生产实现。

## 5. 既有仓库阶段

### Repository Onboarding / Fact Recovery

先读适用规则，读取 [01](01_项目发现与可失效缓存.md)，识别 Manifest/lock/version/build/test/CI/requirements/architecture/contract 入口。不先重构、升级或从聊天猜实现。

### Requirement / Design / Technical Decision

先恢复现状和上游需求；L2/L3 读取 [04](04_轻量变更管理.md) 与适用 [10](10_完成定义追溯门禁.md)。有实质取舍时比较真实方案；关键语义未决时不静默实现。

### Feature / Behavior Implementation

读取 [05](05_设计实施与根因调试.md)，默认 Red → Verify Red → Green → Verify Green → Refactor → Verify Again，并按 [07](07_通用验证与证据策略.md) 建立风险匹配证据。

### Bug / Failure / Incident

完整错误/日志/栈 → 稳定复现 → 环境差异 → 调用/数据流 → 正常参照 → 可证伪根因假设 → 单变量实验 → 回归失败用例 → 单一修复。连续三次修复假设失败后停止叠补丁。

### Refactor / Performance / Maintainability

先证明行为基线。Refactor 不偷改 public behavior；性能优化先有可复现基线和瓶颈证据；不顺手升级或换框架。

### Code Review / Audit

读取 [11](11_两阶段复核与完成前验证.md)。同仓有 Review Skill 时，Coding 完成事实恢复/四维路由/风险权限后切入 Review。Review 默认不等于修改授权。

### Integration / PR / Release / Delivery

使用本轮新鲜证据；检查上游需求、Validation Matrix、Completion Audit、diff、CI、generated artifact、文档和实际 artifact/runtime。合并/发布/部署必须有授权。

### Dependency / Runtime Migration

先确认当前锁定版本、upstream release/security/compatibility、breaking change、Migration/rollback、full regression。普通 Feature 不顺手完成升级。

### Security / Permission / Irreversible Data Operation

认证授权、安全策略、Secret、不可逆删除/迁移、生产数据写入即使代码少也按高风险处理。

## 6. 语言 / 工具链

读取 [03](03_编程语言与工具链适配规则.md)。Profile 只提供“去哪里找事实、常见验证是什么”，不授权升级、换包管理器、把示例命令当仓库命令、引入新测试框架或重排目录。

## 7. 风险等级

以主 `SKILL.md` 为准。项目形态和语言不能降低风险。发现隐藏影响时升级等级；不要为了少写记录或少跑测试而降级。

## 8. 规则优先级与 Overlay

```text
系统/开发者/用户
→ 目标路径适用的项目规则
→ 已确认 Spec/ADR/Contract/Schema/代码/测试/locks/CI
→ Coding 通用规则
→ profile 示例/最佳实践候选
```

本 Skill 作者明确指定的中文注释、所有函数函数级中文说明、中文 Git 提交、北京时间和统一人类日志前缀属于 Coding 自身跨项目硬规则；其他语言版本、框架、数据库、目录、CI 和业务规则不得从某个项目复制进通用核心。
