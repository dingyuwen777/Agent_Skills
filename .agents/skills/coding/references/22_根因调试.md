# 根因调试

本 Reference 负责生产问题的诊断深度与根因完整性。目标不是把每个 Bug 都变成重型调查，而是做到：**简单问题快速闭合，复杂问题不得过早闭合**。

## Diagnostic Escalation Gate

找到第一个成立因素后，先判断它是否足以解释当前问题，而不是自动宣布“完整根因”。

### Lightweight

局部、稳定、单因果问题满足以下全部条件时允许简单问题快速闭合：

- 已有因素可以解释全部已观察症状；
- 没有未解释的独立失败边界；
- 没有性能、并发、异步、队列/批处理、retry/timeout/cancellation、partial failure、数据完整性、状态不同步、修复后仍有症状等复合诊断信号；
- 相邻真实调用点没有与该解释矛盾的直接证据。

此时不要求大型假设矩阵、全仓扫描、独立 Testing 或昂贵 E2E；用最便宜且直接的证据确认、修复并回归即可。

### Standard

原因尚不确定、涉及跨模块/跨边界，或首个因素不能解释全部现象时，扩展到真实调用链、数据流、状态流、配置和相关正常参照，建立**候选因果集合**，逐项验证当前最有解释力的因素。

### Systemic

性能、卡顿、偶发、并发/异步、队列/批处理、外部 I/O、timeout/retry/cancellation、partial failure、数据遗漏/重复、状态不同步、资源竞争或“修过一次仍存在”等复合信号出现时，必须进入 Systemic。先沿 [21_系统级分析与代码整洁收口.md](21_系统级分析与代码整洁收口.md) 恢复当前真实能力链，再执行 **Causal / Diagnostic Coverage Gate**：只检查当前项目真实存在且可能影响 symptom 的阶段，例如：

```text
入口 / admission
→ 排队 / 调度
→ 并发 / 串行
→ 等待 / 外部 I/O
→ 处理 / 计算
→ 持久化 / commit / flush
→ 结果发布 / 通知
→ retry / timeout / cancellation
→ partial failure / recovery
→ 资源竞争 / pool / lock
→ 消费者状态刷新
```

这些是调查维度而非固定架构：不存在的阶段不得为了模板硬造，也不机械全仓扫描。只沿当前 symptom 的真实调用/数据/状态流与独立 failure boundary 读取最少充分代码、配置、日志、测量和测试；新证据暴露真实边界时再单调扩展。

升级只根据当前事实单调发生；没有复合证据时不为显得全面而扩大范围。

## 调试基础动作

无论诊断最终停在哪一级，都保留以下高价值动作：

1. 读取完整错误、警告和调用栈；
2. 稳定复现并记录精确条件；
3. 检查近期变更和环境差异；
4. 跨组件边界跟踪输入、输出、配置和状态；
5. 在仓库中寻找同类正常参照并列出差异；
6. 对当前候选中的具体因素提出一个可证伪假设，说明“若 X 是原因，应观察到 Y；若不是，应出现 Z”；
7. 用最小实验一次改变一个变量，避免多个变化同时发生导致因果不可判定；
8. 用失败用例、日志/trace、测量、正常参照或受控 Probe 把候选标记为 confirmed / ruled out / unknown；
9. 修复后运行目标回归和与当前真实 failure boundary 匹配的相关验证。

假设失败时回到证据，不在旧补丁上继续叠加。连续三次修复假设失败后停止，重新审视架构、前提、环境和观测手段，并向用户报告原始错误与下一步证据需求。

## 多因素根因模型

Standard/Systemic 不默认只有一个根因。对候选因果集合中的已确认项，按其与 symptom 的真实因果关系区分：

- `primary cause`：对主要 symptom 有直接且主要解释力的原因；
- `contributing factor`：独立增加问题发生概率、耗时或严重度的因素；
- `amplifier`：未必单独制造问题，但会放大其他原因；
- `secondary defect`：调查中确认的另一个真实缺陷，可能影响同一能力链，但不是主要 symptom 的首要原因；
- `symptom`：可观察结果，不得反过来冒充原因；
- `ruled out`：已有直接证据排除的候选；
- `unknown`：当前证据不足，仍需观测或实验。

**第一个 confirmed factor 不等于完整根因。** 如果多个已确认因素分别影响总耗时、正确性、取消、状态推进或恢复，它们可以同时成立；不能为了得到一个简洁答案把其他有直接证据的因素省略。

## Omission / Coverage Audit 与结论强度

在说“完整根因”“问题已经找到”之前，至少反查：

- 是否仍有未查看的链路阶段；
- 是否仍有未解释的症状；
- 是否有未覆盖的独立 failure boundary；
- 当前因素是否只能解释部分现象；
- 是否存在与当前结论冲突的代码、日志、状态或测量；
- 性能目标是否遮蔽了已确认的 correctness、数据完整性、partial failure 或 cancellation 缺陷；
- 是否把 `unknown` 当成已排除。

审计未闭合时，输出只能称为**已确认因素 / 候选根因**，并说明剩余未知项；不能用单一“根因是 X”覆盖尚未解释的事实。

## 修复后的 symptom-level 验证

诊断修复不能只证明“改掉了 X”，还要回到**整体用户 symptom**验证目标是否真正改善或消失，并按当前项目真实可测的**分阶段指标 / 边界**证明主要贡献因素。

性能/异步类可以按真实架构选择 `queue / wait / processing / commit / tail / cancellation` 等阶段测量；这些只是候选观测维度，不存在的指标不得为了模板硬造。数据正确性、状态推进、重试、恢复、遗漏/重复等边界同理按真实项目选择。

如果修复一个因素后，其他已确认因素仍可造成原 symptom，就不得声明问题已解决；应说明已经消除什么、仍由什么贡献、是否需要继续修复或另立有边界的后续任务。

需要独立用户路径、系统性黑盒/探索式或复杂 Integration/Regression 来证明真实行为时，按当前 Testing Handoff 条件叠加对应专业验证；普通局部诊断不因为存在本 Reference 就自动变成完整测试项目。
