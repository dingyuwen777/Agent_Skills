# 多人和多 Agent 并行协作

## 支持范围

通过 Git 可见的 Change 元数据或项目已有等价治理记录提供责任划分、依赖表达、冲突预警和集成门禁。不要把它描述成实时协同基础设施。本规则只拥有多人/多 Agent 的责任、冲突、Delegation、并发、Handoff 与集成；不复制 Coding / Testing / Review / Research / Figma 专业规则。

只对仓库已有或当前 Change 已确认建立的边界执行协作约束；没有真实 Contract、Schema、Owner、Migration 或并行边界时，不创建占位机制。

## 开始工作前与冲突处理

先同步**已授权同步**的仓库状态，读取进行中施工单元，确认 ID、Owner、分支、状态及 `affected_areas`、`affected_paths`、`contracts`、`data_changes`、`depends_on`。使用 `coding-change/v1` 时执行：

```text
python <skill>/scripts/coding.py conflicts --root <repo> --json
```

退出码 `2` 表示发现需要协调的显式重叠，不代表脚本故障。同步、切换分支、rebase、共享 Contract 或 Active Change 变化后重新检查；旧的“无冲突”结果不能覆盖新状态。项目使用 OpenSpec、RFC/ADR 或其他治理载体时，按项目已有工具/规则做等价检查。

至少检查相同/父子路径、模块 Owner、API/事件/消息格式 Contract、Schema/Migration/数据语义、配置/权限/部署资源、测试数据/固定端口/共享环境和未完成依赖；信息不足时只写“基于当前可见状态未发现冲突”。

- 无重叠：允许并行，各自保持独立成功标准和验证。
- 可协调重叠：明确先后顺序、冻结点、共同 Owner 或拆分边界。
- Contract、Schema 或数据语义冲突：先统一设计和 Migration 顺序，不静默并行。
- 前端、后端或其他生产者/消费者以同一已确认 Contract 为准；共享 Contract、Schema 或 Migration 默认单一 Writer，冻结后消费者再并行。
- 复用仓库已有契约测试；不存在时只按真实风险增加最小验证，不为清单引入新框架。

## 多 Agent 派发

本节是多 Agent 唯一 **Orchestration Contract**；Router 仍不创建子 Agent、不拆分或调度开发任务。默认 **Vertical Slice**；blocker→DAG，**frontier** 才并行；Wide Refactor 用 `expand → migrate batches → contract`。

### Value Gate

只拆有真实独立价值的 Agent，按收益相对启动、交接、重复读取和冲突成本判定：

- `NO_SPLIT`：局部、强顺序、共享状态紧密，或协调成本不低于收益；保持单 Agent。
- `MAY_SPLIT`：存在独立候选，但并行、上下文隔离或独立复核收益不确定；可拆可不拆。
- `MUST_SPLIT`：存在可独立验收单元，且有两个以上实质 frontier、明显上下文隔离收益、明确独立验证/Review 价值，或用户明确要求多 Agent；**宿主支持时必须拆**。

宿主无可用 subagent/delegation、能力被禁用、Provider 未注册或当前环境无法安全使用时，说明原因后**降级为单 Agent 正常执行**；不得因本规则自身阻塞任务，也不得冒充已拆分。项目自己的独立 Review、权限、安全、CI 等 required gate 仍照常生效。

只并行派发真正独立的任务：没有未满足顺序依赖、每个任务能独立验证、给子 Agent 最少但充分的目标/范围/事实源/验收。不要给子 Agent 整段会话历史代替任务契约。多个 Writer 只有在路径、Contract/Schema、共享状态和验证环境均隔离时并行；否则单 Writer + 只读 Agent 或串行 Worker。不要制造 merge conflict 再把冲突成本算成收益。

### 角色

只启用有独立价值的最少角色：`Explorer`=read-only 项目事实探索；`Researcher`=read-only 外部事实核验；`Worker`=scoped write Vertical Slice；`Tester`=默认 read-only 独立验证（授权后可写测试资产）；`Reviewer`=read-only 独立审查。Role 只定义目标、范围、权限和输出责任，专业方法仍进入真正命中的 Skill；不按岗位名机械建 Agent，不用同质 Agent 投票代替证据。

### Delegation Contract

只有宿主真实支持子 Agent / worker 能力并且实际决定拆分时才建立；**不创建 Planner，不维护任务队列，不新增长期 Worker/调度控制面**。每个子任务至少显式携带：

- **子任务目标**：可观察、可独立验收；
- **输入事实**：当前 revision、Requirement/Contract、已确认决定；
- **允许读取范围**；
- **允许写入范围**：只读时明确只读；
- **依赖**：blocker / 上游 slice / 冻结 Contract；
- **预期输出**；
- **必须返回的 Evidence**；
- **父 Agent 集成验证**。

返回至少表达 `completed|blocked|failed`、summary、facts/evidence、changes、validation、risks、needs_parent_decision，不要求统一 wire format。授权只在同目标、同范围、同副作用等级内传递；父 Agent 的 Git/merge/Release 权限不自动下放。

主 Agent 不把子 Agent 的“完成”文本当 Evidence；必须读取真实产物和结果。子 Agent 返回后，主 Agent 必须：

1. 检查实际 diff 和工作区；
2. 复核需求符合性；
3. 检查任务之间重叠和集成风险；
4. 运行目标及整体相关验证；
5. 只依据实际证据更新 Change 状态。

### Multi-Agent Visibility Contract

- 单 Agent：实质工程任务简短说明 `NO_SPLIT`，或 `MAY_SPLIT/MUST_SPLIT` 因收益/宿主能力降级。
- 实际拆分：启动前报告判定、Agent 数量、Role/Scope、read/write 与 parallel/sequential。
- 运行中：只报关键完成、Finding、失败/阻塞和职责变化，不刷 spawn/message/wait 日志。
- 完成时：汇总真实 Agent 的 Scope、状态、主要产出/Evidence及是否采用；未实际启动不得制造角色记录。
- 宿主 Agents Window / 任务树只是补充 UI，不是唯一用户可见渠道。

### Host Adapter Contract

每次先检测当前宿主真实 capability；Adapter 只负责“怎么委派”，不成为通用规则 Owner：

- `Codex`：原生 subagent/custom-agent/delegation 可用时使用，不固化模型、并发或配置路径。
- `Claude Code`：原生 subagent/delegation 可用时使用，只传 scope/permission/handoff。
- `Cursor`：使用原生 subagents；并行 Writer 优先隔离 worktree/environment，无隔离则单 Writer/串行。
- `DeepSeek Harness`：检查 `ctx.subagents` / provider registry；有 Provider 才委派，无 Provider 就单 Agent，普通任务不自动安装/切换 Provider。

统一边界：native first、capability detect before delegate、宿主配置不是 canonical Owner、能力缺失自动单 Agent、provider/worktree/cloud/model 不扩大授权；具体命令、路径、model ID、嵌套深度按当前版本需要再核验。

## 分支与工作区

多人或高风险并行优先使用项目既有隔离分支或 worktree，但只有用户和仓库规则授权时才能创建。创建隔离环境后先运行基线测试；基线失败时区分既有失败和本次回归。

## 固有限制

- 本地独占创建只能防止同一工作区同时使用相同 Change ID，不能锁住远端克隆。
- 看不到另一克隆尚未提交或推送的 Change。
- 两个 Agent 从相同基线同时启动时可能都判断无冲突；记录同步后必须重新检查。
- Owner 和影响范围是协作约定，Skill 不能强制执行。
- 没有通知、看板、在线状态、租约或自动合并能力。

跨克隆可靠协作要求团队及时提交并共享正式变更记录；同步策略、Branch Protection 和 PR 门禁由仓库自身负责。
