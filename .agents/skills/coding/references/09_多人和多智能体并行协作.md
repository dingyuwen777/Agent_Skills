# 多人和多 Agent 并行协作

## 支持范围

通过 Git 可见 Change/项目等价记录承担多人/多 Agent 的责任、依赖、冲突、Delegation、并发、Handoff 与集成；不要把它描述成实时协同基础设施，也不复制 Coding / Testing / Review / Research / Figma 专业规则。只约束真实已有/已确认边界，不为不存在的 Contract、Schema、Owner、Migration 或并行关系造机制。

## 开始工作前与冲突处理

先同步**已授权同步**状态，读取进行中施工单元并确认 ID/Owner/分支/状态、影响路径/Contract/数据与依赖。使用 `coding-change/v1` 时执行：

```text
python <skill>/scripts/coding.py conflicts --root <repo> --json
```

退出码 `2` 表示需协调的显式重叠。同步、切分支、rebase、共享 Contract/Active Change 变化后重查；旧“无冲突”不覆盖新状态。其他治理载体按项目规则等价检查。

至少检查路径/Owner、API/事件/格式 Contract、Schema/Migration/数据、配置/权限/部署、共享测试环境和依赖；信息不足只写“基于当前可见状态未发现冲突”。

- 无重叠：允许并行，各自保持独立成功标准和验证。
- 可协调重叠：明确先后顺序、冻结点、共同 Owner 或拆分边界。
- Contract、Schema 或数据语义冲突：先统一设计和 Migration 顺序，不静默并行。
- 前端、后端或其他生产者/消费者以同一已确认 Contract 为准；共享 Contract、Schema 或 Migration 默认单一 Writer，冻结后消费者再并行。
- 复用仓库已有契约测试；不存在时只按真实风险增加最小验证，不为清单引入新框架。

## 多 Agent 派发

本节是多 Agent 唯一 **Orchestration Contract**；Router 仍不创建子 Agent、不拆分或调度开发任务。默认 **Vertical Slice**；blocker→DAG，**frontier** 才并行；Wide Refactor 用 `expand → migrate batches → contract`。

### Value Gate

只拆有真实独立价值：`NO_SPLIT`=成本≥收益；`MAY_SPLIT`=收益不确定；`MUST_SPLIT`=存在可独立验收单元，且多个独立 frontier、上下文隔离或独立复核收益明确。用户明确要求多 Agent 也不能跳过独立价值判定。宿主支持时 `MUST_SPLIT` 必拆；无 delegation/禁用/无 Provider 时说明并**降级为单 Agent**，不阻塞、不冒充，也不绕过项目既有门禁。

只并行派发真正独立的任务：没有未满足顺序依赖、每个任务能独立验证、给子 Agent 最少但充分的目标/范围/事实源/验收。不要给子 Agent 整段会话历史代替任务契约。多个 Writer 只有在路径、Contract/Schema、共享状态和验证环境均隔离时并行；否则单 Writer + 只读 Agent 或串行 Worker。不要制造 merge conflict 再把冲突成本算成收益。

### Delegation Depth / Budget / Writer Guard

Agent_Skills delegation 默认 **root-only**：只有 Main/Parent 发起；**child 默认不得**再 delegate。默认 `active child budget = 3`，这是成本/协调预算而非可绕过宿主硬上限；只有 Parent 能基于额外独立 frontier、隔离和明显收益显式授权更深/更多 delegation，宿主不支持则不模拟。

**Single Writer Lease**：同一 checkout 或 shared mutable state 默认同时只有一个 write-capable Worker。只有 worktree/environment、路径、Contract/Schema、共享状态和验证环境都隔离时，Parent 才能发放多个 writer lease；任一条件不满足就串行。

### 角色

只启用最少角色：`Explorer`/ `Researcher` 只读事实，`Worker` 限定写，`Tester` 默认只读验证，`Reviewer` 只读审查。Role 只定目标/范围/权限/输出，专业方法仍归 Coding / Testing / Review / Research / Figma；不按岗位名机械建 Agent。

### Delegation Contract

只有宿主真实支持子 Agent / worker 能力并且实际决定拆分时才建立；**不创建 Planner，不维护任务队列，不新增长期 Worker/调度控制面**。每个子任务至少显式携带：

- **子任务目标**：可观察、可独立验收；
- **输入事实**：`base_revision`（当前可获得的 Git/工作区等价版本事实）、`decision_epoch`、Requirement/Contract 与已确认决定；
- **允许读取范围**；
- **允许写入范围**：只读时明确只读；
- **依赖**：blocker / 上游 slice / 冻结 Contract；
- **预期输出**；
- **必须返回的 Evidence**；
- **父 Agent 集成验证**。

`decision_epoch` 是当前 task/session 内的单调决策版本；Requirement、Contract、Schema、Scope、Authorization 或 Acceptance 发生会改变执行判断的实质变化时递增。它不要求落盘，也不为无关文本变化机械递增。

子 Agent 最终 Handoff 使用轻量稳定 Envelope，不强制统一 JSON wire protocol：

```text
STATUS
SCOPE
REVISION
SUMMARY
EVIDENCE
CHANGES
VALIDATION
RISKS
PARENT_DECISION
```

`REVISION` 回报实际观察到的 base revision / decision epoch；拿不到时写 unknown，不能猜。

授权只在同目标、同范围、同副作用等级内传递；父 Agent 的 Git/merge/Release 权限不自动下放。

主 Agent 不把子 Agent 的“完成”文本当 Evidence；必须读取真实产物和结果。子 Agent 返回后，主 Agent 必须：

1. 检查实际 diff 和工作区；
2. 复核需求符合性；
3. 检查任务之间重叠和集成风险；
4. 运行目标及整体相关验证；
5. 只依据实际证据更新 Change 状态。

### Delegation Freshness Gate

Parent 收到 child 结果先比较 `base_revision` / observed revision 与 `decision_epoch`。相关代码/Contract 已变化或 epoch 不一致时标记 `STALE_RESULT`：先重读受影响事实并重新验证 Evidence，再决定复用、局部重跑或丢弃；旧结果不能直接驱动写入、Review 结论或完成状态。

### Child Failure / Retry Guard

只对明确 transient 的同一 delegation 自动重试，默认最多 **1 次**；权限、Contract、确定性测试失败等非 transient 原因不机械重试。再次发生同类失败时 `STOP_CHILD_RETRY`，由 Parent fallback、换方案或 replan，禁止无限 respawn。

### Evidence Conflict Gate

多个 Agent 结论冲突时**禁止投票**或按数量取多数。Parent 依据 current revision、source owner、正式 Contract、可复现 test/probe 与更直接 Evidence 裁决；证据仍不足就保持 `UNKNOWN` 并只调查会改变决定的缺口。

### Join / Cancel Guard

证据已充分，或 child 已 stale / obsolete 时，不为“等所有 Agent”继续付出成本；宿主支持 interrupt/cancel 时停止无价值后台 child。进入交付前，required child 不得处于未知 running 状态，write-capable child 不得仍持有活动写入。

### Orchestration Ledger

Parent 在当前 task/session 内维护最小 `Orchestration Ledger`：split decision、`decision_epoch`、active children、writer lease、repair round、blocking findings、follow-ups。它只用于跨轮次/压缩恢复编排事实，**不落盘、不入 Git、不新增服务**；真实代码、Git/CI、Requirement 与 Evidence 仍是事实源。

### Repair Loop Owner

Main/Parent 是 **Repair Loop Owner / Finding Admission Gate**；Reviewer 不直接派 Worker。仅接纳的 `IN_SCOPE_BLOCKING` 由 Parent 以**最少充分** Finding/Evidence/scope/验收重建 Worker Delegation，不转发**完整对话历史**；继续/停止/replan 服从 Review Convergence Guard。

### Multi-Agent Visibility Contract

启动前报告判定、Agent 数量、Role/Scope、读写和并行关系；运行中仅报关键变化；结束汇总真实 Agent/Evidence。未启动只报单 Agent；宿主无能力时说明降级，不能只靠宿主 UI。

### Host Adapter Contract

先探测真实 capability：`Codex`、`Claude Code`、`Cursor` 用可用原生 delegation；Cursor 多 Writer 优先隔离 worktree/environment；`DeepSeek Harness` 检查 `ctx.subagents` / provider registry。Adapter 只负责委派；无能力即单 Agent，不自动装 Provider、不固化模型/并发/路径、不扩大授权或成为 canonical Owner。

DSH Adapter 可以用 `maxDepth` / `toolFilter` 缩小 Agent_Skills role 的递归和直接 mutation surface，但 `toolFilter` 不是安全权限格或 sandbox；不得据此宣称 DSH readonly 与宿主级 read-only enforcement 等价。真正的权限仍服从 DSH 当前 permission/sandbox 与 Parent 授权边界。

### Effectiveness Feedback

补完安全/收敛 Guard 后，不继续凭感觉增加 Agent、角色或规则。需要调 `NO_SPLIT/MAY_SPLIT/MUST_SPLIT`、active budget 或返修阈值时，优先用真实历史任务比较 wall-clock、Agent 数、repair rounds、CI rerun、人工干预，以及宿主可得的 token/tool calls；不为此自动上传 telemetry。

## 分支与工作区

多人或高风险并行优先使用项目既有隔离分支或 worktree，但只有用户和仓库规则授权时才能创建。创建隔离环境后先运行基线测试；基线失败时区分既有失败和本次回归。

## 固有限制

- 本地独占创建只能防止同一工作区同时使用相同 Change ID，不能锁住远端克隆。
- 看不到另一克隆尚未提交或推送的 Change。
- 两个 Agent 从相同基线同时启动时可能都判断无冲突；记录同步后必须重新检查。
- Owner 和影响范围是协作约定，Skill 不能强制执行。
- 没有通知、看板、在线状态、租约或自动合并能力。

跨克隆可靠协作要求团队及时提交并共享正式变更记录；同步策略、Branch Protection 和 PR 门禁由仓库自身负责。
