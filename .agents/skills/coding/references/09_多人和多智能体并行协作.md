# 多人和多 Agent 并行协作

## 支持范围

通过 Git 可见的 Change 元数据或项目已有等价治理记录提供责任划分、依赖表达、冲突预警和集成门禁。不要把它描述成实时协同基础设施。

只对仓库已有或当前 Change 已确认建立的边界执行协作约束。没有前后端分离、API/事件 Contract、Schema、数据 Owner、Migration 或契约测试时，不创建占位机制；继续按真实文件、模块和行为范围协作。

## 开始工作前

1. 同步用户已授权同步的仓库状态；不要擅自 pull、push 或切换分支。
2. 读取项目当前正式变更治理中的所有进行中单元；使用 Coding 自带 Change 时读取当前 carrier 的 `active/*/CHANGE.md`。
3. 确认当前 Change/施工单元的唯一 ID、Owner、分支和状态。
4. 写清 `affected_areas`、`affected_paths`、`contracts`、`data_changes` 和 `depends_on`；项目已有治理使用其他字段时保持语义等价。
5. 使用 Coding 自带 `coding-change/v1` 时执行显式冲突检查：

```text
python <skill>/scripts/coding.py conflicts --root <repo> --json
```

退出码 `2` 表示发现需要协调的显式重叠，不代表脚本故障。

同步、切换分支、rebase、共享 Contract 更新或其他 Active Change 元数据变化后重新执行。旧的“无冲突”结果不能覆盖新状态。

如果项目使用 OpenSpec、RFC/ADR 或其他治理载体，Coding CLI 不假装能够解析它没有实现的 schema；先按项目已有工具/规则检查并行状态，再把同样的真实冲突维度纳入人工 Review。

## 冲突维度

不要只比较源码目录。至少检查：

- 相同文件、相同目录或父子路径；
- 同一模块 Owner 或跨模块边界；
- 同一 API、事件、消息格式或其他 Contract；
- 同一表、字段、索引、Migration 链或持久化语义；
- 同一配置键、环境变量、权限或部署资源；
- 同一快照、测试数据、固定端口或共享外部环境；
- 一个 Change 依赖另一个尚未完成的行为。

某一维度在有界发现中不存在时跳过；不要因为检查清单列出它就推断项目应当拥有它。

## 处理结果

- 无重叠：允许并行，但各自保持独立分支、成功标准和验证。
- 可协调重叠：明确先后顺序、接口冻结点、共同 Owner 或拆分后的文件边界，并记录决策。
- Contract、Schema 或数据语义冲突：阻止静默并行；先统一设计和 Migration 顺序。
- 信息不足：不要写“无冲突”，写“基于当前可见状态未发现冲突”，并列出不可见范围。

仓库已有共享边界时额外遵守：

- 前端、后端或其他生产者/消费者不得分别猜测字段、枚举、错误、时间、单位、分页和兼容语义；以同一已确认 Contract 为准。
- 共享 Contract、Schema 或 Migration 的语义修改使用一个明确 Owner，或先完成共同变更再并行消费者实现；不要让多个 Change 静默定义同一语义。
- 只在仓库已有流程或协作者明确同意时设置并行冻结点；记录具体版本、提交、Schema 或决策，不能只写“接口已定”。
- 使用仓库已有契约测试或兼容检查；不存在时不引入新框架。若风险需要新增验证，按设计门禁提出最小测试方案。

## 多 Agent 派发

本节是多 Agent 的唯一 **Orchestration Contract**。它只决定“是否拆、谁做、何时并行、怎样交接和怎样向用户报告”，不复制 Coding / Testing / Review / Research / Figma 的专业执行规则，也不把 Router 变成 Planner、任务队列或 Worker 调度器。

### 1. Value Gate：先证明收益，再创建 Agent

先按 Coding Core 得到 `NO_SPLIT / MAY_SPLIT / MUST_SPLIT`。判断只看真实收益和依赖，不看“任务听起来很大”、文件数量或希望展示多 Agent。

#### `NO_SPLIT`

保持单 Agent，典型事实包括：

- 一个边界明确的小功能、已确认根因的小 Bug、局部文档/配置修改；
- 子步骤强顺序依赖，后一步必须消费前一步尚未形成的结果；
- 多个候选子任务会频繁读写同一文件、Contract、Schema、状态或工作区；
- 每个候选子任务太小，启动、恢复上下文和 Handoff 成本预计不低于执行本身；
- 只有形式上的“前端 / 后端 / 测试”分类，却不能形成独立可验收结果。

`NO_SPLIT` 不因为宿主支持很多 Agent 就升级。

#### `MAY_SPLIT`

存在独立候选，但收益尚不稳定，例如两个中等规模只读调查、外部 Research 与仓库探索、或附加价值接近协调成本的 Tester / Reviewer。主 Agent 根据当前规模、上下文压力、宿主能力和副作用决定是否拆；选择不拆时不为形式创建 Agent。

#### `MUST_SPLIT`

只在至少一个以下事实成立、且确实存在可独立验收的工作单元时成立：

1. 当前 frontier 有两个及以上实质、互不阻塞的子任务，并行能明显降低等待时间或主上下文负担；
2. 存在大量代码探索、日志、外部 Research、浏览器/设计调查等高上下文噪声工作，隔离后能明显保护主 Agent 的需求、决策和集成上下文；
3. 当前风险使独立验证 / 独立 Review 具有明确可靠性收益，且该工作可以在不同上下文中独立重建事实；
4. 用户明确要求本任务使用多 Agent，且不存在更高优先级安全、权限或项目规则冲突。

`MUST_SPLIT` 是“宿主有能力时必须拆”的编排结论，不是新的项目完成门禁。当前宿主没有可用 subagent/delegation、能力被禁用、provider 未注册或当前环境无法安全使用时：

```text
报告 MUST_SPLIT 判定
→ 说明当前宿主能力缺口
→ 降级为单 Agent
→ 按原 Coding / Testing / Review / Research / Figma 与项目门禁继续正常执行
```

不得仅因为多 Agent 能力缺失把本可正常完成的工程任务标为 blocked/incomplete，也不得声称“已拆分”。如果目标项目本身另有必须由独立身份完成的 Review、审批、权限或安全门禁，则该既有门禁仍按自己的规则决定是否阻塞；本降级规则不能绕过它。

### 2. 角色只表达职责，不复制专业规则

默认只从以下五个语义角色选择最少充分集合。角色不是固定编制，也不是每次全部启动：

| Role | 默认权限 | 独立价值 | 专业执行入口 |
| --- | --- | --- | --- |
| `Explorer` | read-only | 恢复代码、调用链、Contract、失败位置等项目事实，吸收搜索噪声 | 当前项目规则 + 实际命中的分析/开发规则 |
| `Researcher` | read-only | 核验外部、最新、会变化或需要一手来源的事实 | Research，必要时组合 Analysis/Coding |
| `Worker` | scoped write | 实施一个边界清楚、可独立验证的 Vertical Slice | Coding 及任务真正命中的 Testing/Docs/Figma 等 |
| `Tester` | 默认 read-only；明确授权时可写测试资产 | 独立验证用户/调用者行为、回归和 Evidence 缺口 | Testing；发现生产缺陷后返回 Coding |
| `Reviewer` | read-only | 从需求和当前事实独立重建预期并审查实现/Evidence | Coding + Review |

硬规则：

- Role prompt 只写目标、范围、权限和输出责任，不复制专业规则正文；子 Agent 进入自己的任务后仍读取当前项目适用规则并取得真正命中的专业约束；
- 不按“架构师 / 产品经理 / DBA / DevOps”等岗位名称机械创建 Agent；只有新的独立目标、上下文隔离或 Evidence 责任才增加角色；
- 一个 Role 可以有多个实例，但每个实例必须有不同且不重叠的真实 Scope；不得用多个同质 Agent 对同一问题“投票”代替证据；
- 默认由父 Agent 承担 fan-out / integration；子 Agent 不递归扩张 Agent 树，除非宿主明确支持且当前子问题再次满足 Value Gate。

### 3. Delegation Contract

只有宿主真实支持子 Agent / worker 能力，并且 Value Gate 决定实际拆分时，才建立最小 Delegation Contract；**不创建 Planner，不维护任务队列，不新增长期 Worker/调度控制面**。

每个子任务至少显式携带：

- Role 与一个可观察、可独立验收的目标；
- 当前 revision、Requirement/Contract、已确认决定和必要输入事实；
- 允许读取范围与允许写入范围；
- blocker / 上游 slice / 冻结 Contract 等依赖；
- 预期输出和必须返回的 Evidence；
- 父 Agent 收回结果后需要执行的集成验证。

返回语义至少覆盖：`status(completed|blocked|failed)`、summary、facts/evidence、changes、validation、risks、needs_parent_decision。它是语义 Contract，不要求所有宿主输出相同 JSON/YAML wire format。

授权连续性只在同目标、同范围、同副作用等级内传递；父 Agent 拥有 Git/merge/Release 权限不代表子 Agent 自动获得。新 public Contract、Schema、数据、安全、不可逆操作或重大路线决策必须回到父 Agent / Owner 的既有门禁。

### 4. 并发与写隔离

- 多个 read-only Explorer / Researcher / Reviewer / Tester 在输入事实已冻结且彼此无依赖时可以并行；
- 多个 Writer 只有在写入路径、Contract/Schema、共享状态和验证环境均可隔离时才并行，优先使用宿主/项目已有 worktree、独立 branch、cloud environment 或等价隔离；
- 无安全隔离能力时改成单 Writer + 其他只读 Agent，或串行 Worker；
- 共享 API/事件 Contract、Schema/Migration、同一配置键、同一文件、同一状态机默认只有一个 Writer；消费者可在 Contract 冻结后并行；
- 不用并行制造 merge conflict，再把冲突解决成本算成“多 Agent 收益”。

### 5. Multi-Agent Visibility Contract

多 Agent 是否真正发生必须对用户可见，但不把底层 spawn/message/wait 日志刷给用户。

**任务开始 / 首次判定：**

- `NO_SPLIT`：对实质性工程任务简短说明“本任务保持单 Agent”，必要时给一句原因；
- `MAY_SPLIT` 但不拆：说明当前收益不足以覆盖协调成本，继续单 Agent；
- 实际拆分：启动前说明 `MAY_SPLIT/MUST_SPLIT`、实际 Agent 数量、Role、每个 Scope、read-only/write 和 parallel/sequential 关系；
- `MUST_SPLIT` 但宿主无能力：说明当前宿主不支持/未提供可用 subagent，已降级为单 Agent 继续执行。

**运行中：**只在 Agent 完成关键阶段、发现高价值 Finding、阻塞/失败，或动态增加/取消 Agent 时更新；动态调整说明原因和新职责，不持续转播内部日志或推理。

**完成时：**汇总实际启动过的 Agent 及其 Role、Scope、状态、主要产出/Evidence、失败和父 Agent 是否采用结果。没有真正启动子 Agent 时只报告单 Agent，不制造虚假角色记录。

宿主自己的 Agents Window、任务树、background 状态或日志只是补充 UI；父 Agent 的自然语言状态不能完全依赖这些 UI 才可理解。

### 6. Host Adapter Contract

canonical Orchestration 只拥有行为语义；Adapter 只回答“当前宿主怎样执行已经决定的 delegation”。每次先检查当前宿主实际暴露的能力，不能只按品牌名假设。

| Host | Adapter 边界 |
| --- | --- |
| `Codex` | 当前宿主暴露原生 subagent/custom agent/delegation 时使用其原生能力；已有项目级 agent 配置可复用，但本 Contract 不要求生成固定 `.codex/agents` 文件，也不绑定模型名、并发数或易变命令。 |
| `Claude Code` | 当前表面支持 multiple/subagents 时使用其原生 delegation；Role 只提供 scope/permission/handoff，不复制 Claude 专属第二套工程规则。 |
| `Cursor` | 使用当前原生 subagents；并行 Writer 优先用当前可用的 isolated worktree/environment，无法隔离时退回单 Writer/串行。兼容 agent 文件可复用，但不是 canonical Owner。 |
| `DeepSeek Harness` | 先检查当前 `ctx.subagents` / provider registry 是否存在可用 provider；有 provider 才 delegation，没有 provider 就降级单 Agent。不得为普通任务自动安装、切换或配置新的 provider。 |

通用 Adapter 硬规则：

1. capability detect before delegate：工具/Provider/权限真实存在才调用；
2. native first：优先宿主原生 delegation，不另造常驻调度服务；
3. no host-specific source of truth：宿主 role/config 是 projection 或项目配置，不成为通用规则 Owner；
4. graceful single-agent fallback：宿主能力缺失只使多 Agent 收益不可用，不使任务自动失败；
5. preserve authorization：切换 provider、worktree、cloud agent 或模型不能扩大权限/副作用；
6. fresh capability facts：具体命令、配置路径、model ID 和嵌套深度只有当前任务真实需要时再核验，不写成跨版本硬编码。

### 7. 父 Agent 集成责任

子 Agent 的 `completed` 只是候选结果，不是完成 Evidence。父 Agent 收回后必须检查实际 diff/底层证据、复核需求与 revision、检查跨 Agent 重叠/Contract 漂移、运行或核验相关 Fresh Evidence，并按现有 Coding/Review/Testing 门禁处理 Finding。只有真实集成结果才能更新 Change、PR、完成和交付状态。

## 分支与工作区

多人或高风险并行优先使用项目既有的隔离分支或 worktree 流程，但只有用户和仓库规则授权时才能创建。创建隔离环境后先运行基线测试；基线失败时区分既有失败和本次回归，不把失败隐藏或归因给错误对象。

## 固有限制

- 本地独占创建只能防止同一工作区同时使用相同 Change ID，不能锁住远端克隆。
- 看不到另一克隆尚未提交或推送的 Change。
- 两个 Agent 从相同基线同时启动时可能都判断无冲突；记录同步后必须重新检查。
- Owner 和影响范围是协作约定，Skill 不能强制执行。
- 没有通知、看板、在线状态、租约或自动合并能力。

跨克隆可靠协作要求团队及时提交并共享正式变更记录；同步策略、Branch Protection 和 PR 门禁由仓库自身负责。
