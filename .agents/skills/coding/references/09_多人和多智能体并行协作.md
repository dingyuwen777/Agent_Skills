# 多人和多 Agent 并行协作

## 支持范围

通过 Git 可见的变更元数据、真实路径和共享 Contract 提供责任划分、依赖表达、冲突预警和集成门禁。不要把它描述成实时协同基础设施。

只有项目选定了 Coding Change carrier 时才使用 Coding CLI 的冲突检查；项目使用其他治理体系时按项目原生机制比较影响范围，不为了 CLI 再造一套平行 Change。

## 开始前

1. 同步用户已授权同步的仓库状态；不要擅自 pull/push/切换分支；
2. 读取项目选定治理载体中的进行中变更；
3. 确认当前变更 ID/Owner/branch/status（项目有这些概念时）；
4. 写清 affected paths/modules、Contract、data/schema、config/runtime、generated files、shared tests/fixtures、dependency/release resources；
5. 使用 Coding Change carrier 时执行：

```text
python <skill>/scripts/coding.py conflicts --root <repo> --json
```

显式 carrier：

```text
python <skill>/scripts/coding.py conflicts --root <repo> --change-root <path> --json
```

退出码 `2` 表示发现显式重叠，不代表脚本故障。

同步、切换分支、rebase、共享 Contract 更新或变更元数据变化后重新检查。

## 冲突维度

至少检查真实适用的：

- 相同文件/目录或父子路径；
- 同一模块/Owner；
- 同一 API/事件/消息/ABI/CLI/格式 Contract；
- 同一 Schema/Migration/persistence 语义；
- 同一配置键、权限或部署资源；
- 同一 snapshot/fixture/固定端口/共享外部环境；
- 一个变更依赖另一个尚未完成行为。

不存在的维度跳过，不从清单反推项目必须拥有它。

## 结果处理

- 无重叠：允许并行，各自保持独立成功标准和验证；
- 可协调重叠：明确先后顺序、冻结点、共同 Owner 或文件边界；
- Contract/Schema/数据语义冲突：阻止静默并行，先统一设计和迁移顺序；
- 信息不足：只能写“基于当前可见状态未发现冲突”，并列不可见范围。

## 多 Agent 派发

只并行派发真正独立的任务：无顺序依赖、不写同一文件/接口/共享状态、可独立验证，并给最少充分目标/范围/事实源/禁止项/验收。

子 Agent 返回后主 Agent必须：

1. 检查实际 diff；
2. 复核需求符合性；
3. 检查交叉冲突和集成风险；
4. 重新运行目标及整体相关验证；
5. 只依据实际证据更新变更状态。

## 分支与工作区

多人/高风险并行优先沿用项目既有隔离分支/worktree，但只有授权时创建。创建隔离环境后先跑基线测试；基线失败要区分既有失败和本次回归。

## 固有限制

- 文件系统独占创建只能保护同一工作区，不能锁远端克隆；
- 看不到另一克隆未提交/未推送状态；
- 两个 Agent 同时从同一基线启动时可能都判断无冲突；同步后必须重新检查；
- Owner/影响范围是协作协议，不是强制锁；
- Skill 没有通知、看板、在线状态、租约或自动合并能力。
