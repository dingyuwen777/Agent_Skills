# 多人和多 Agent 并行协作

## 支持范围

通过 Git 可见的 Change 元数据或项目已有等价治理记录提供责任划分、依赖表达、冲突预警和集成门禁。不要把它描述成实时协同基础设施。

只对仓库已有或当前 Change 已确认建立的边界执行协作约束。没有前后端分离、API/事件 Contract、Schema、数据 Owner、Migration 或契约测试时，不创建占位机制；继续按真实文件、模块和行为范围协作。

## 开始工作前

1. 同步用户已授权同步的仓库状态；不要擅自 pull、push 或切换分支。
2. 读取项目当前正式变更治理中的所有进行中单元；使用 Coding 自带 Change 时读取当前 carrier 的 `active/*/CHANGE.md`。
3. 确认当前 Change/施工单元的唯一 ID、Owner、分支和状态。
4. 写清 `affected_areas`、`affected_paths`、`contracts`、`data_changes` 和 `depends_on`；项目已有治理使用其他字段时保持语义等价。
5. 使用 Coding 自带 `coding-change/v1` 时执行显式冲突检查：

```text
python <skill>/scripts/coding.py conflicts --root <repo> --json
```

退出码 `2` 表示发现需要协调的显式重叠，不代表脚本故障。

同步、切换分支、rebase、共享 Contract 更新或其他 Active Change 元数据变化后重新执行。旧的“无冲突”结果不能覆盖新状态。

如果项目使用 OpenSpec、RFC/ADR 或其他治理载体，Coding CLI 不假装能够解析它没有实现的 schema；先按项目已有工具/规则检查并行状态，再把同样的真实冲突维度纳入人工 Review。

## 冲突维度

不要只比较源码目录。至少检查：

- 相同文件、相同目录或父子路径；
- 同一模块 Owner 或跨模块边界；
- 同一 API、事件、消息格式或其他 Contract；
- 同一表、字段、索引、Migration 链或持久化语义；
- 同一配置键、环境变量、权限或部署资源；
- 同一快照、测试数据、固定端口或共享外部环境；
- 一个 Change 依赖另一个尚未完成的行为。

某一维度在有界发现中不存在时跳过；不要因为检查清单列出它就推断项目应当拥有它。

## 处理结果

- 无重叠：允许并行，但各自保持独立分支、成功标准和验证。
- 可协调重叠：明确先后顺序、接口冻结点、共同 Owner 或拆分后的文件边界，并记录决策。
- Contract、Schema 或数据语义冲突：阻止静默并行；先统一设计和 Migration 顺序。
- 信息不足：不要写“无冲突”，写“基于当前可见状态未发现冲突”，并列出不可见范围。

仓库已有共享边界时额外遵守：

- 前端、后端或其他生产者/消费者不得分别猜测字段、枚举、错误、时间、单位、分页和兼容语义；以同一已确认 Contract 为准。
- 共享 Contract、Schema 或 Migration 的语义修改使用一个明确 Owner，或先完成共同变更再并行消费者实现；不要让多个 Change 静默定义同一语义。
- 只在仓库已有流程或协作者明确同意时设置并行冻结点；记录具体版本、提交、Schema 或决策，不能只写“接口已定”。
- 使用仓库已有契约测试或兼容检查；不存在时不引入新框架。若风险需要新增验证，按设计门禁提出最小测试方案。

## 多 Agent 派发

### Value Gate 与 Host Adapter

`NO_SPLIT`=拆分成本不低于收益；`MAY_SPLIT`=有独立候选但收益不确定；`MUST_SPLIT`=存在两个以上实质独立 frontier、明显上下文隔离/独立复核价值，或用户明确要求。`MUST_SPLIT` 在宿主有原生 subagent/delegation 时必须拆；无能力、被禁用或 Provider 未注册时告知用户并降级为单 Agent 正常执行，不因此阻塞，也不绕过项目原有 Review/权限/安全/CI 门禁。

只选最少充分角色：`Explorer`（只读事实）、`Researcher`（只读外部核验）、`Worker`（限定写入）、`Tester`（默认只读验证）、`Reviewer`（只读审查）。Role 只定义目标/范围/权限/输出，专业方法仍由 Coding / Testing / Review / Research / Figma 承担。

### Multi-Agent Visibility Contract

实际拆分前报告判定、Agent 数量、Role/Scope、read/write 与并行/顺序；运行中只报关键完成、Finding、失败/阻塞和职责变化；结束时汇总真实 Agent 与 Evidence。未启动只报告单 Agent；宿主无能力时明确说明已降级。

Adapter 先检测真实 capability：`Codex` / `Claude Code` / `Cursor` 使用当前可用 native delegation，Cursor 多 Writer 优先隔离 worktree/environment；`DeepSeek Harness` 先查当前 `ctx.subagents` / provider registry。有能力才委派，不自动安装 Provider、绑定固定模型/并发数或复制第二套规则。
默认 **Vertical Slice**；blocker→DAG，**frontier** 才并行；Wide Refactor 用 `expand → migrate batches → contract`。

只并行派发真正独立的任务：

- 没有顺序依赖；
- 不写相同文件、接口或共享状态；
- 每个任务能独立验证；
- 给子 Agent 最少但充分的目标、范围、事实源和验收标准。

不要给子 Agent 整段会话历史代替任务契约。

### Delegation Contract

只有宿主真实支持子 Agent / worker 能力并且当前 frontier 存在可独立并行切片时，才建立最小 Delegation Contract；**不创建 Planner，不维护任务队列，不新增长期 Worker/调度控制面**。

每个子任务至少显式携带：

- **子任务目标**：一个可观察、可独立验收的结果；
- **输入事实**：当前 revision、Requirement/Contract、已确认决定和必要上下文，不用整段聊天替代；
- **允许读取范围**：需要恢复事实的仓库/模块/设计/外部只读边界；
- **允许写入范围**：无写权限时明确只读；有写权限时限定文件/模块/资产与副作用等级；
- **依赖**：必须已经满足的 blocker、上游 slice 或冻结 Contract；没有依赖时写无；
- **预期输出**：diff/Findings/测试结果/设计变更/调查结论等明确产物；
- **必须返回的 Evidence**：实际命令、revision、测试/运行/截图/Trace 或未验证边界；
- **父 Agent 集成验证**：主 Agent 收回结果后需要执行的 diff/冲突/Requirement/整体回归与 Completion 检查。

授权连续性只在同目标、同范围、同副作用等级内传递；父 Agent 拥有 Git/merge/Release 权限不代表子 Agent 自动获得。子 Agent 暴露新 public Contract、Schema、数据、安全、不可逆操作或重大路线决策时必须回到父 Agent / Owner 的现有决策门禁。

主 Agent 不把子 Agent 的“完成”文本当 Evidence；必须读取真实产物和结果，并把多个 slice 在当前 base/head 上重新集成验证。

子 Agent 返回后，主 Agent 必须：

1. 检查实际 diff 和工作区；
2. 复核需求符合性；
3. 检查任务之间重叠和集成风险；
4. 运行目标及整体相关验证；
5. 只依据实际证据更新 Change 状态。

## 分支与工作区

多人或高风险并行优先使用项目既有的隔离分支或 worktree 流程，但只有用户和仓库规则授权时才能创建。创建隔离环境后先运行基线测试；基线失败时区分既有失败和本次回归，不把失败隐藏或归因给错误对象。

## 固有限制

- 本地独占创建只能防止同一工作区同时使用相同 Change ID，不能锁住远端克隆。
- 看不到另一克隆尚未提交或推送的 Change。
- 两个 Agent 从相同基线同时启动时可能都判断无冲突；记录同步后必须重新检查。
- Owner 和影响范围是协作约定，Skill 不能强制执行。
- 没有通知、看板、在线状态、租约或自动合并能力。

跨克隆可靠协作要求团队及时提交并共享正式变更记录；同步策略、Branch Protection 和 PR 门禁由仓库自身负责。
