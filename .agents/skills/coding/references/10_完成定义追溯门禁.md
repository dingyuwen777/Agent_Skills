# Stage / Change 完成定义追溯门禁

这份规则解决一个特定失败模式：实现、测试和当前任务记录都看起来完整，但一开始漏掉了上游正式要求，导致 CI 全绿仍过早宣布 Stage / Feature / Release 单元完成。

它对**持久 gated L2、所有 L3、正式 Stage/Migration/Release/Architecture Change/Greenfield Bootstrap，以及项目明确要求 Completion Gate 的单元**使用完整 Requirement Traceability + Validation Matrix + Completion Audit。普通轻量 L2 仍必须向上核对目标和验收，但不为了形式生成完整 Change 表格或归档记录。

因此，`风险=L2` 本身不再触发本 Reference；只有明确 Completion Gate、正式交付/仓库初始化或 L3 等事实出现时才加载完整门禁。普通轻量 L2 的最小完成核对继续由 Coding Core 与最小充分治理规则执行，不能因为不加载本文件而省掉新鲜验证或上游目标核对。

## 核心关系

需求事实的方向固定为：

```text
用户已确认决定 / 正式 Roadmap / Spec / Stage / Feature 完成定义
→ 当前任务契约 / 持久 Change / 项目等价施工契约
→ 实现
→ 测试与运行证据
```

`CHANGE.md` 是施工契约，不是自身需求全集。PR body、Issue、OpenSpec、RFC/ADR 或其他当前施工记录也不能反过来成为自己的需求全集；它们只有在项目明确把其作为上游 Requirement Source 时才承担对应上游角色。

### 轻量 L2 的最小完成核对

普通 L2 如果没有独立 gated Change，在给出“完成 / 可交付 / 可合并”这类强结论前至少执行：

```text
re-read current requirement source / confirmed task facts
→ 目标、范围、非目标和验收是否仍是当前版本
→ 关键不变项是否保持
→ required 验证是否有本轮证据
→ 未验证项、延期和未知项是否如实暴露
```

这可以记录在当前任务、PR body、Review 输出或项目已有载体中，不要求为了打勾生成 `Requirement Traceability` Markdown 表或 `Completion Audit` 文件。若任务出现跨 PR/跨 Owner/长期审计/正式门禁等持久治理价值，则先按 Change Reference 升级，再使用下面完整门禁。

## Requirement Traceability

Coding 自带的持久 gated Change 使用：

```text
schema: coding-change/v1
completion_gate: required
```

当前工具**只支持 `coding-change/v1`，不读取、不迁移、不兼容旧 schema**。项目使用其他正式治理体系时，不要求改成 Coding schema，但必须由项目自己的事实源承载等价需求追溯语义。

并维护 `# Requirement Traceability` 表。每一条上游要求只允许四种状态：

- `satisfied`：已有当前实现和验证证据；
- `explicitly_deferred`：已有用户/正式事实源批准的延期依据；
- `not_applicable`：有明确事实证明对当前单元不适用；
- `not_satisfied`：尚未满足，不能进入 Ready。

`Source` 优先引用仓库内正式事实源；本轮用户明确批准决定可以使用 `user:<标识>`。当前 Change 不得把自己作为 Requirement Source。

Greenfield 的 Requirement Source 可以是本轮正式需求、用户已确认技术决定、目标平台/运行环境约束、组织政策或外部标准；不能因为仓库还没有代码就把 Agent 自己的默认技术选择写成上游 Requirement。

机器检查只能验证表结构、状态、占位内容和仓库路径存在性。Agent/Reviewer 仍必须判断：上游要求是否被完整提取、Evidence 是否真的证明对应语义。

普通轻量 L2 不要求创建该表，但仍必须能回答“目标/验收从哪里来、哪些已证明、哪些没有证明”。

## Validation Matrix

持久 gated L2/L3 Change 必须按 [07_通用验证与证据策略.md](07_通用验证与证据策略.md) 建立 `# Validation Matrix`，明确各验证维度是 `required` 还是 `not_applicable`。

普通轻量 L2 仍按同一策略选择验证层，只是可以把这一判断保留为任务内部计划、PR/Review 说明或项目已有载体，不为矩阵本身创建独立 Change。

通用默认考虑：

```text
行为 / Unit / Component
接口 / Contract
集成 / Persistence / Runtime Dependency
用户 / Workflow Acceptance
跨组件 Golden Path
外部依赖 Probe
Build / Package / Runtime
Docs / Governance / Other
```

核心边界：

- 行为 / Unit / Component 用于便宜、稳定地覆盖局部业务规则、算法、状态和组件行为，但不能冒充 public consumer、真实依赖、package 或跨组件接线；
- 接口 / Contract 证明 public API/ABI/CLI/Schema/格式或生产者/消费者的机器接口和兼容语义一致；
- 集成 / Persistence / Runtime Dependency 证明只有真实数据库、文件系统、进程、队列、SDK、runtime service 等参与时才能成立的事实；
- 用户 / Workflow Acceptance 证明用户或调用者从真实入口看到的输入、输出、状态和错误闭环；“用户”可以是 Browser 用户、CLI 操作者、SDK consumer、Mobile 用户或 Batch Operator；
- 跨组件 Golden Path 用少量高价值真实路径证明多个组件组装后确实接通，不负责穷举所有状态；
- 外部依赖 Probe 只在第三方服务、真实硬件或远端环境的当前事实需要确认时有界执行，默认不作为普通稳定 CI 主力；
- Build / Package / Runtime 证明正式构建、打包、安装、镜像、target 或启动事实，不能被源码 Unit 自动替代；
- Docs / Governance / Other 承担文档、配置、生成物、架构/Owner、Secret、Policy、Change/Ready 等非运行时但真实影响交付的证据。

Matrix 不要求每个任务机械执行全部层，也不设固定测试数量配额。`not_applicable` 必须有事实依据；`required` 必须在 Ready/强完成结论前有新鲜证据。

### Web / API / PostgreSQL / Provider 专项 profile

如果项目真实存在这些边界，再叠加 [08_分层测试与验收策略.md](08_分层测试与验收策略.md) 的完整专项规则：

```text
用户 / Workflow Acceptance
→ Browser Mock Acceptance

集成 / Persistence / Runtime Dependency
→ Backend/API/PostgreSQL Integration

接口 / Contract
→ Contract / Generated Client

跨组件 Golden Path
→ Real Full-stack Golden Path

外部依赖 Probe
→ Real Provider Probe
```

原专项职责保持不变：

- Browser Mock 用于广覆盖用户可见行为、状态、请求和错误表达；它不能证明真实 API、数据库、Worker 或 Provider 链；
- Backend/API/PostgreSQL Integration 证明服务器业务规则、事务、持久化和异步运行边界；项目不是 PostgreSQL 时按实际 Persistence 映射，不机械要求 PostgreSQL；
- Contract 证明生产者/消费者的机器接口一致；
- Real Full-stack 用少量关键 Golden Path 证明真实组件接通，不负责穷举所有 UI 状态；
- Real Provider Probe 只在外部供应商当前事实需要确认时有界执行，默认不作为普通 CI 主力。

CLI、Library、Mobile、Embedded、Data、IaC 等没有这些真实边界的项目不为了填模板制造 Browser/PostgreSQL/Provider 层。

当前 `ready_check.py` 不自动判断 Matrix 的语义充分性，因此 Agent/Reviewer 必须在 Completion Audit 和 Review 中人工核对；不能因为机器 Ready Check 通过就跳过。

## Completion Audit

对持久 gated Change，进入 `ready_for_review` / 项目等价 Ready 状态前必须重新读取上游事实源，不先看当前 Change 的 checklist 来反推需求。至少完成：

```text
upstream_re_read
→ 从上游正式事实源独立重建完成定义

change_coverage
→ 比较“上游要求 vs 当前 Change”，寻找 requirement omission

reverse_audit
→ 对适用边界做反向审计，并复核 Validation Matrix 的层级选择和证据等级

unresolved_cleared
→ not_satisfied 清零；延期/不适用都有正式依据
```

轻量 L2 没有持久 Change 时，不创建形式化 Completion Audit；但前文的最小完成核对仍是强结论前的语义门禁，CI 绿色不能替代。

### 反向能力审计按真实项目边界选择

前后端 / Web：

```text
后端当前能力 → 是否应有前端入口 / 状态 / 结果？
前端 Button / Action → 后端是否真实支持且状态允许？
异步 Job → queued/running/success/failure/cancel/retry 是否正确表达？
业务动作完成 → 用户是否能找到最终结果？
错误/失败页面 → 是否只展示机器事实，不伪造不存在的历史或状态？
```

CLI：

```text
public command / flag / config
→ parser / handler
→ stdout / stderr / exit code / file side effect
→ 调用者是否能按文档完成工作流？
```

Library / SDK：

```text
public API / ABI / package export
→ consumer compile / invoke
→ 返回、异常、兼容语义
→ package artifact 是否仍能被真实 consumer 使用？
```

Schema / Migration / 数据：

```text
writer / producer
→ schema / migration
→ reader / consumer
→ 历史数据、回滚或兼容期是否满足正式策略？
```

Batch / Data / ML：

```text
input schema / artifact
→ transform / pipeline
→ output artifact / data quality
→ downstream consumer / operator
```

Mobile / Desktop / Embedded：

```text
UI / public operation
→ state / platform SDK / storage / protocol
→ simulator/device/target（实际风险需要时）
→ 用户/设备观察到的最终结果
```

Package / Release / Infra：

```text
source/config
→ build/render/plan
→ artifact/install/startup/deploy boundary
→ health/result/rollback（授权和项目策略要求时）
```

Greenfield / Bootstrap：

```text
已确认目标 / 硬约束 / 技术决定
→ 新建工程基线
→ 正式 build/test/package/startup
→ 最小真实用户或 consumer 结果
→ 文档/运行方式/后续扩展入口是否可被维护者找到
```

同时检查：

- 用户或调用者可见 Requirement 是否有适用的 Workflow Acceptance 证据；
- runtime/persistence 规则是否有适用的真实 Integration 证据；
- public 边界是否有 Contract/compatibility 证据；
- 关键跨组件链是否有足够的 Golden Path；
- 构建/打包/启动是否因“代码测试绿色”而被遗漏；
- 外部依赖只有确实需要确认当前事实时才 Probe；
- Docs/Governance 与当前实现、正式设计和当前任务契约是否一致。

没有对应边界时记录为什么不适用，不为填清单制造新架构或无价值测试。

## 两层 Review

需求符合性 Review 的深度由 Review Skill 的 Quick / Standard / Deep 规则决定。

对持久 gated L2/L3 或 Deep Review，明确分成：

```text
Review A1：上游要求 → Change / 当前持久施工范围
→ 检查是否漏需求

Review A2：Change / 当前持久施工范围 → 实现 / 测试 / 文档
→ 检查已承诺要求是否真实实现，并核对 Validation Matrix 的证据层级
```

普通 Standard Review 可以按当前最小任务契约执行等价的“目标/验收 → 实现/测试”核对，不要求为了 A1/A2 标签生成持久表格。第二阶段再做代码质量 Review。CI 绿色不能代替上游需求核对；某一测试层绿色也不能替代另一层独立风险的验证。

## 机器 Ready Check

Coding 自带 `coding-change/v1` 使用：

```bash
python .agents/skills/coding/scripts/ready_check.py --root . --require-active-ready
```

PR CI 可使用 `--changed-since <base-sha>`，只强制当前 PR 改动的 gated Active Change，避免并行 Change 互相阻塞。main push 可以要求当前 Coding carrier 中所有 gated Active Change Ready。项目使用其他正式治理载体时，使用项目自己的机器 gate；Coding 不假装解析未实现的外部 schema。

机器门禁验证：

- 当前 carrier 中的 Active Change 在需要集成时必须 `ready_for_review`；
- Archive Change 必须 `done`；
- schema 必须是当前 `coding-change/v1`，且 `completion_gate: required`；
- Traceability 至少一条，ID 唯一，状态合法；
- Ready/Archive 不允许 `not_satisfied`；
- Source 仓库路径存在，当前 Change 不能引用自身作为 Source；
- Evidence、延期/不适用依据不得为占位值；
- Completion Audit 四项全部完成。

它**只约束已经存在并由当前流程认领的 gated Coding Change**；不能反向把每个普通 L2 任务变成 Coding Change。它也不验证业务语义本身或自动证明 Validation Matrix 是否充分，因此不能用脚本通过替代 Completion Audit/最小完成核对。

## 不兼容旧 schema 的策略

当前 Coding 工具只支持 `coding-change/v1`。旧格式不是 legacy 兼容输入，也不会被 `ready_check.py` 静默忽略。

如果目标仓库仍保存旧格式：

- 先依据该项目自己的历史治理策略决定归档、转换或删除；
- 需要转换时必须是显式迁移任务，不能在普通功能开发里顺手做；
- 转换后的内容仍需保留真实需求、决策和验证证据，不能只改 `schema` 字符串制造“兼容”；
- 未完成显式处理前，不得声称 Coding CLI 已成功管理这些旧记录。

不得为了绕过 Ready Check 删除 `completion_gate`；如果发现门禁不适用于某类任务，应修改治理规则并给出证据，而不是在单个 Change 中静默关闭。
