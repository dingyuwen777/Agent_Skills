# 完成定义追溯门禁

这份规则解决：实现、测试和当前变更记录都看起来完整，但一开始漏掉上游正式要求，导致 CI 全绿仍过早宣布 Feature/Stage/Release/Architecture Change 完成。

它适用于不同项目形态、语言和研发阶段。

## 1. 核心关系

```text
用户已确认决定 / 正式 Roadmap / Spec / Feature/Release 完成定义
→ 当前变更契约
→ 实现
→ 测试与运行证据
```

当前变更不是自身需求全集。

## 2. Requirement Traceability

使用 Coding Change 时 schema 为 `coding-change/v1`，新模板固定 `completion_gate: required`。不兼容旧 schema。

每条上游要求状态只允许：

- `satisfied`；
- `explicitly_deferred`；
- `not_applicable`；
- `not_satisfied`。

`Source` 优先仓库正式事实源或 `user:/external:`；当前 Change 不得引用自身。机器检查只能验证结构/状态/占位/路径，Agent/Reviewer 仍要判断需求是否被完整提取、Evidence 是否真正证明对应语义。

项目使用非 Coding 原生治理时，保持相同语义要求，但机器校验由项目原生机制或人工 Review 承担；不要为了运行 `ready_check.py` 强行复制一套 Coding Change。

## 3. Validation Matrix

通用维度：

```text
行为 / Unit / Component
接口 / Contract
集成 / Persistence / Runtime Dependency
用户 / Workflow Acceptance
跨组件 Golden Path
外部依赖 Probe
Build / Package / Runtime
Docs / Governance / Other
```

任何层都不能冒充自己没有实际运行的边界。Web/UI/API/Persistence 等真实存在时按 [08](08_分层测试与验收策略.md) 映射专项层；CLI/Library/Mobile/Embedded/Data/IaC 不制造 Browser/数据库/Provider 层。

## 4. Completion Audit

进入 `ready_for_review` 前重新读取上游事实源，不先从当前 checklist 反推需求：

```text
upstream_re_read
→ 独立重建完成定义

change_coverage
→ 比较“上游要求 vs 当前变更”，找遗漏

reverse_audit
→ 对真实边界做反向能力审计，并复核 Validation Matrix

unresolved_cleared
→ not_satisfied 清零；延期/不适用有正式依据
```

### 反向审计例子

Web/客户端：

```text
服务能力 → 是否有应有客户端入口/状态/结果？
客户端动作 → 服务端是否真实支持？
异步过程 → queued/running/retry/success/failure/cancel 是否完整表达？
```

CLI：

```text
public command/flag/config
→ parser/handler
→ stdout/stderr/exit/副作用
```

Library/SDK：

```text
public API/ABI/export
→ consumer compile/invoke
→ 返回/异常/兼容
→ package install/smoke（有独立风险时）
```

Schema/Migration/Data：

```text
writer/producer
→ schema/migration
→ reader/consumer
→ 历史兼容/rollback
```

Data/ML：

```text
input schema/artifact
→ transform/pipeline
→ output/data quality
→ downstream consumer/operator
```

Mobile/Desktop/Embedded：

```text
公开操作
→ state/platform/runtime/protocol
→ simulator/device/target（实际需要时）
→ 最终可观察结果
```

Package/Release/IaC：

```text
source/config
→ build/render/plan
→ artifact/install/startup/deploy boundary
→ health/result/rollback（授权且项目要求时）
```

## 5. 两层需求 Review

```text
A1 上游要求 → 当前变更
→ 查 requirement omission

A2 当前变更 → 实现 / 测试 / 文档
→ 查承诺是否真实满足及证据等级
```

然后再做代码质量 Review。CI 绿色不能替代 A1；某一测试层绿色不能替代另一层独立风险。

## 6. Coding Change 的 Ready Check

默认：

```bash
python .agents/skills/coding/scripts/ready_check.py --root . --require-active-ready
```

显式 carrier：

```bash
python .agents/skills/coding/scripts/ready_check.py --root . --change-root .agents/changes --require-active-ready
```

PR 可使用 `--changed-since <base-sha>`。

机器门禁验证：

- gated Active 在需要集成时 `ready_for_review`；
- gated Archive 为 `done`；
- Traceability 表结构、ID、状态合法；
- Ready/Archive 没有 `not_satisfied`；
- Source 路径存在，当前 Change 不引用自己；
- Evidence/依据不是占位值；
- Completion Audit 四项完成；
- schema 必须是 `coding-change/v1`。

它不验证自然语言业务完整性，也不自动判断 Validation Matrix 是否充分。

## 7. 不允许绕过

- 不删除 `completion_gate` 绕过 Ready；
- 不把未满足要求静默写成“后续优化”；
- 不用旧 CI/历史测试冒充当前证据；
- 不因为项目使用非 Coding carrier 就取消 Traceability/Completion Audit 语义；
- 不为了机器脚本方便强迫项目建立平行治理。
