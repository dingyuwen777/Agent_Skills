# 跨模型效果评测与规则有效性

本 Reference 只负责 **跨模型一致性、真实 Agent Outcome Eval / Trace 和规则有效性生命周期**。它不改变目标项目业务事实，不建立 GPT、DeepSeek、GLM 等品牌专属 Skill，也不替代 Testing/Review/CI 的项目验证。

## 1. 模型身份不参与路由

**模型身份不参与路由。** GPT、DeepSeek、GLM 或其他模型的名称、版本、推理强弱、上下文长度和宿主差异，都不能成为 canonical Task Route 的新维度，也不能把同一工程任务分裂成多套 Skill/Reference。

同一任务必须共享同一可观察行为 Contract：

项目事实 + 用户目标 + 授权 + 风险
→ 同一 Owner / required Context
→ 同一 public Contract / Schema / 安全边界
→ 同一 Evidence 与 Completion 标准

不同模型可以采用不同的内部推理、工具顺序和局部实现写法；最终结果是否可接受，只看真实项目事实、实际 diff、直接 Evidence、Review/CI 和交付结果。

不得因为模型更强而自动降低安全、权限、公共兼容、数据、Migration、Review 或 required CI；也不得因为模型更弱就维护一套永久低标准流程。

## 2. Outcome Eval 是 Skill 效果的结果层

规则文本存在、路由正确、Context 成功加载都只是前置证据，不能单独证明 Agent 真正把任务做好。

对会改变 Agent 工作方式、上下文、规划、授权、验证或 Handoff 的重要 Skill Mutation，应优先使用真实或可重复 fixture 的 Outcome Eval，至少覆盖：

- 最终任务结果是否满足 Acceptance；
- required Evidence 是否真实存在；
- 是否出现越权、需求遗漏、错误完成声明或错误技术路线；
- 是否出现无意义重试、过多用户干预、明显 Context 膨胀；
- 负例中是否错误触发无关 Skill、写操作或治理流程。

仓库机器契约位于 evals/agent_outcome_eval.py。它不调用 Provider，只校验真实宿主产生的 run artifact 并执行确定性评分。

## 3. model-neutral case / run / grader

同一个 Eval case 对所有模型使用同一任务、同一必需结果、同一必需 Evidence、同一禁止违规和同一上限。**评分规则不得按模型品牌改变。**

真实 run artifact 至少记录：

- case / run identity；
- 运行类型：`actual` 表示真实模型/宿主执行产生的 run，`fixture` 只用于验证 case/grader/compare 机器契约；
- 模型名称、版本、宿主标签；
- 被验证 repository revision；
- 完成结果、直接 Evidence、已确认违规；
- tool call、retry、用户干预等过程指标；
- Token、耗时、Context bytes 等宿主可取得遥测；
- 可选的脱敏 Trace 事件。

取得不到的遥测明确写 unavailable，不得猜数值。`fixture` 即使评分通过也不能把其模型标记为 verified；只有 `actual` run 才能进入真实模型验证计数。未实际运行的模型只能标记 unverified，不能因为“同一家模型”“更强模型”或静态规则相同就宣称已经通过。

真实 Provider Secret、原始敏感 Tool payload、私有代码/用户数据不得为了 Eval 强制写入仓库；runner 应保存脱敏、最少充分 artifact。

## 4. Eval 任务族与正负例

核心回归至少维护这些任务族的代表 case：

- Feature / Behavior；
- Bug / Diagnosis；
- Review / Testing；
- Technical Plan / Long-running Task；
- Figma / Design-to-Code；
- Git / PR Delivery；
- Negative / should-not-trigger。

case 不是固定项目模板；它只定义可观察结果、Evidence 与违规边界。具体测试仓库、fixture 或真实项目事实仍由 Eval 运行环境提供。

新增重大规则时，如果现有 case 已能直接保护该行为，复用现有 case；只有出现新的独立失败模式时才新增最小 case，不能把 case 数量当质量指标。

### 高价值自动收敛失效族

当规则涉及“全面分析、多 Agent、Review 返修、Follow-up、跨 Skill Handoff 或恢复旧结果”时，actual Outcome Eval 优先覆盖能够真正推翻治理结论的高价值 case，而不是继续增加文本锚点。当前代表性 failure families 包括：

- **Follow-up explosion**：OUT_OF_SCOPE 发现是否错误自动创建 Issue/Change/Agent 或递归派生任务；
- **out-of-scope delivery blocker**：是否能正确表达“问题不属于当前修复范围，但真实阻塞当前交付”；
- **repair churn**：修掉旧 Finding 却引入同级/更高级 blocker 时，是否错误判断为收敛；
- **Parent vs Reviewer**：Parent 是否越权降级或关闭独立 Reviewer 的 BLOCKING Finding；
- **stale child**：revision / decision_epoch 漂移后是否仍使用旧 child 结果驱动写入或完成；
- **single writer**：共享 checkout/state 是否出现未经隔离的并发 Writer；
- **MUST_SPLIT fallback**：无 delegation 时能否继续可安全实现，同时不把 `Independence Requirement=REQUIRED` 降级；
- **simple-task false-positive**：简单任务是否被不必要地拆 Agent、建治理对象或扩大验证；
- **cross-skill finding**：Testing/Docs/Figma/Review 发现跨域问题后是否正确落到 HANDOFF / REPORT / BLOCK / REQUIREMENT / FOLLOW-UP 终态，而不是自动扩大 Scope。

这些 case 首先保护可观察结果、越权、Evidence 和停止行为。**static contract test / fixture Green 只证明规则、grader 或投影机器契约；只有 `actual` run 才能证明具体模型/版本/宿主在真实任务中遵守这些行为。** 当前没有 actual run 时必须写 unverified，不能用 fixture、CI Green 或“模型更强”推断实际效果。

## 5. Rule Effectiveness Gate

规则按长期职责分四类，分类用于维护和 Eval，不进入目标项目 Router：

- **invariant**：无论模型能力如何都不能违反的硬边界，例如权限、安全、数据正确性、公共 Contract、不得伪造 Evidence。
- **policy**：维护者/团队明确选择且当前仍有效的工程政策，例如 Git 交付、当前项目或全局硬规则。
- **heuristic**：为降低模型常见失败而增加的行为指导，例如某类容易遗漏的检查顺序。
- **technique**：按场景可选的方法，例如 design-it-twice、特定分析框架。

规则 Mutation 时执行：

1. invariant / policy 只能由上游 Requirement/Owner 改变，不能因为新模型更强自动删除或降级；
2. 新增或强化 heuristic 优先绑定真实失败、Review Finding、Incident 或 Outcome Eval case；
3. technique 默认按需加载，不为了“可能有用”常驻所有任务；
4. 模型升级后可以重新跑相同 Eval。若 heuristic 已经没有独立收益或开始造成副作用，可以提出降级、条件化或删除；
5. 删除/降级 heuristic 仍必须通过内容守恒、路由、负例和 Outcome Eval，不能凭“模型现在应该会了”直接删；
6. 未取得实际对比 Evidence 时，只能说“尚未验证是否仍必要”，不能伪造提升或回归。

## 6. 跨模型兼容结论

可以声明：

- canonical Contract 对不同模型保持相同；
- 某个具体模型/版本/宿主已经对哪些 case 产生真实 run artifact；
- 某次比较中哪些 case 通过、失败、阻塞或未验证。

不得声明：

- 没有实际 run artifact 的模型“已兼容 / 已通过”；
- 一个模型在一个 case 通过就代表所有任务通过；
- 更大模型天然满足全部 invariant/policy；
- 静态单元测试等价于真实 Agent Outcome Eval。

## 7. 与现有 Owner 的关系

- Router：只负责 model-neutral Owner/Context 路由，不新增模型维度；
- Coding：拥有本 Reference、Skill Mutation 与实际实现；
- Testing：负责真实功能/黑盒/Regression 方法，不被 Eval grader 替代；
- Review：独立判断 Evidence 和实现充分性；
- CI：运行确定性 contract tests 与项目 required checks；
- Runtime：可以携带/恢复任务状态，但不替 Outcome Eval 生成虚假完成事实。

Outcome Eval 是对现有治理效果的额外结果层，不是第二套开发流程。
