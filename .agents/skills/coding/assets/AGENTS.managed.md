## 项目研发治理入口

处理本项目研发任务时：

1. **无论采用哪种通用治理执行方式，都必须先读取并遵守当前目录及上级适用的项目规则**，再依据当前真实文件恢复本任务所需的技术栈、架构、Contract、Schema/Migration、CI、部署、设计和运行事实；不得用通用示例、历史聊天、缓存或猜测覆盖项目事实。
2. 在实质性工程任务形成执行计划前，读取 `.agents/skills/ENTRY.md` 作为当前项目工程约束入口，并使用项目已配置的治理能力取得本任务真正需要的完整约束。系统、开发者或用户级更高优先级指令若明确指定其他执行方式，**只改变通用治理约束的取得和呈现方式；不得因此跳过、替代或降低目标项目自身规则、Contract、Schema/Migration、CI、正式设计、部署和验收边界**。
3. 在计划前执行多 Agent 价值判断并向用户报告结果：`NO_SPLIT` 保持单 Agent；`MAY_SPLIT` 仅在并行、上下文隔离或独立复核收益明显高于协调成本时拆；`MUST_SPLIT` 在当前宿主存在可用原生 delegation/subagent 能力时必须真实委派。只拆具备独立目标、独立输出/证据或明确隔离价值的工作。
4. 实际拆分时优先使用安装到本项目的 namespaced 原生角色 Agent，并在启动前说明 Agent 数量、角色、职责、read/write 边界和 parallel/sequential 关系；多个 Writer 只有在写入范围、共享 Contract/Schema/状态和验证环境均隔离时并行，否则保持单 Writer 或串行。
5. 当前宿主没有可用 subagent/delegation、该能力被禁用或无法安全使用时，明确说明后**降级为单 Agent正常执行**；不得因此阻塞本可完成的工程任务，也不得伪称已经拆分。项目自身已有的独立 Review、权限、安全、CI 等硬门禁仍照常生效。
6. 首次接入、项目治理状态尚未校准，或长期项目事实疑似漂移时，在实质性生产代码修改前执行有界的项目治理校准：调查当前仓库真实实现，只维护本区块外的项目自有 Overlay；完成后重新读取最终 `AGENTS.md`，再继续用户原始任务。
7. 必需治理约束无法可靠取得、完整性无法确认，或与更高优先级规则存在无法安全解决的冲突时，只阻塞依赖该约束的动作并如实说明；不得用旧记忆、摘要或自行猜测替代。
8. 本区块由安装/升级流程维护。项目自己的长期规则继续写在本区块外；受管运行资产和宿主 execution adapters 只服务当前项目研发治理，不作为项目自有长期规则手工维护。
