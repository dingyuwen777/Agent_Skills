# 用户场景黑盒与探索式测试

本 Reference 负责从真实用户/调用者目标出发设计 Scenario-based Black-box Acceptance 与 Exploratory Testing。核心原则是：**测试公开行为，而不是按内部实现结构模拟“用户”。** 项目形态只决定 Testing 已命中后的入口映射，不能因为当前项目是 Web/CLI/Mobile 就机械触发独立 Testing。

## 1. 先建立 User Journey Matrix

对用户可见 L2/L3 Feature、Bug 或工作流变化，只要存在真实公开入口且没有明确不适用依据，至少建立一个关键 Journey：

```text
Persona / Caller
→ Goal
→ Preconditions
→ Entry
→ Steps
→ Expected observable result
→ Failure / recovery expectations
```

轻量表示即可，不要求项目新增固定测试文档。常用矩阵：

```text
场景
→ 用户目标
→ 初始状态
→ 操作
→ 预期结果
→ 证据层
```

Testing 不从内部函数调用顺序直接生成 Journey；先从 Requirement、正式产品行为、当前 UI/CLI/API/SDK/Data Contract 和真实入口恢复用户目标。

## 2. 黑盒不是 Browser 同义词

### Web / Full-stack

从真实页面/路由/菜单/按钮/表单/弹窗/抽屉等入口操作，验证用户看得到的状态、错误、导航、请求语义和结果。

### API

从 public HTTP/RPC boundary 输入请求，观察 response、status/error contract、最终可查询状态和业务副作用。

### CLI

从安装后或项目正式 CLI 入口运行命令，观察 stdout/stderr、exit code、文件/进程/环境副作用。

### Library / SDK

由最小外部 consumer 使用 public API，不直接调用 private helper 冒充 consumer acceptance。

### Data / ETL / ML

从代表性输入进入正式 pipeline，观察最终 artifact、数据质量、checkpoint、重跑与可复现结果。

### Mobile / Desktop

从真实 UI/navigation/permission/storage/network 用户路径验证，按项目事实选择 simulator/device。

### Infra / Release

调用者是 operator/release engineer；从正式 command/config/artifact 入口观察 plan/build/apply/deploy/result，不用内部 helper test 冒充真实工作流。

## 3. Scenario 族

优先围绕当前 Requirement 和风险选最有价值的场景，而不是固定穷举所有项。

### Happy Path

用户按正常顺序完成主要目标，最终结果可见且可继续下一步。

### Empty / Boundary / Data Variation

例如：

```text
0 条 / 1 条 / 最大页
null / empty / boundary
超长文本 / 大数据
最早 / 最晚 / 当前 / 未来时间
枚举未知值 / 兼容旧值
```

只有真实业务边界适用时才测试。

### State Variation

按实际状态选择：

```text
loading
empty
queued
running
partial success
success
failure
retrying
cancelled
expired
permission denied
```

不要为了模板发明系统不存在的状态。

### Sequence Variation

高价值探索包括：

```text
正常顺序 → 打乱顺序
点击一次 → 快速连续点击
A → B → A
Back / Forward
Refresh
Deep Link
重复提交
重复 Retry
任务进行中离开再回来
分页后再筛选 / 筛选后再翻页
```

### Failure Injection

在项目已有可控机制内稳定制造：

```text
4xx / 5xx
业务错误
Timeout
网络中断
依赖临时失败
Worker/Job 失败
部分成功
重试耗尽
```

不要为了“更真实”直接破坏生产环境。

### Time Variation

时间敏感功能要考虑当前项目真实时区和 Contract：跨天、月末、过期、未来时间、DST（项目真实涉及时）、UTC 与展示时区边界。不能把 Agent 默认时区强塞给外部 wire format。

### Permission / Identity Variation

只在功能存在权限/资格边界时覆盖未登录、无权限、权限变化、资源归属、并发身份等；不要发明项目没有的 RBAC。

## 4. Exploratory Testing 方法

探索式测试不是随便点击。先给每一轮探索一个 Charter：

```text
目标：我要证伪什么风险？
范围：哪些入口/状态？
变异：顺序、数据、错误、时间、权限中的哪些维度？
停止条件：找到确定缺陷、风险被证伪、预算耗尽或依赖阻塞。
证据：可复现步骤、输入、环境、实际结果、预期依据。
```

每次探索只扩大到与当前风险直接相关的邻近状态，避免无边界漫游。

## 5. User Journey 与测试层组合

一个 Journey 可以由多层共同证明：

```text
Browser/UI Mock
→ 广覆盖用户状态与请求语义

Backend/API/Persistence Integration
→ 服务器规则和真实持久化/Runtime

Contract
→ Producer/Consumer 字段和语义一致

Real Cross-component Golden Path
→ 少量真实链证明组件确实接通
```

不要因为 Journey 是“用户场景”就把每一个状态全部复制到真实 Full-stack。

## 6. 用户可见 Bug

对用户可见 Bug，优先从原始用户路径建立失败证据：

```text
原前置状态
→ 原操作步骤
→ 原错误可观察结果
→ 修复后同一路径通过
```

若原问题只能在更低层稳定制造，可在低层做精确回归，但仍要判断公开工作流是否存在独立接线风险。

## 7. 输出缺陷

每个确定 Defect 至少包含：

```text
Scenario / Journey
Preconditions
Steps
Expected
Actual
Evidence
Affected user/caller
Reproducibility
Likely boundary（仅有证据时）
Regression recommendation
```

没有充分依据定位根因时，不把黑盒症状伪装成确定代码根因；交给 Coding 做根因诊断。
