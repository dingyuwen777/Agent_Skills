# 测试策略与分层证据

Testing 的目标不是凑 Unit/Integration/E2E 数量，而是把 Requirement 和风险映射到**能直接证明可观察行为的最小充分测试层**。

## 1. 先建立 Risk / Evidence Matrix

对当前任务真实适用的 Requirement/Risk 建立最小映射：

```text
Requirement / Risk
→ Expected observable behavior
→ Existing evidence
→ Evidence boundary
→ Gap
→ Smallest useful next test
```

先列风险，再看现有测试，避免被“CI 全绿”诱导成确认偏差。

常见风险维度包括：

```text
成功路径
边界输入 / 空值 / 大数据
非法或不支持输入
错误与异常传播
状态转换
重试 / 取消 / 恢复
并发 / 幂等 / 事务
缓存 / 刷新 / 顺序
兼容性
权限 / 安全
用户可见反馈
构建 / 启动 / 打包
外部依赖当前事实
```

只保留当前项目真实存在的项。

## 2. 通用测试层

### Behavior / Unit / Component

适合稳定验证局部业务规则、算法、解析、validation、状态转换、组件/store/view-model 等。默认断言可观察行为，不把内部调用次数当成业务结果。

不能自动证明 public consumer、真实 persistence/runtime、package 或跨组件接线。

### Contract / Consumer

用于验证生产者和消费者对 public API/ABI/CLI/schema/format/generated artifact 的理解一致。Mock 不得手写第二套 Contract；Snapshot 失败不能默认通过覆盖 Snapshot 解决。

### Integration / Persistence / Runtime Dependency

验证只有真实依赖参与才成立的事实，例如数据库、文件系统、queue、OS process、thread/runtime、container、SDK、native dependency 等。

如果正确性依赖某个具体实现语义，不能用语义不同的替代品冒充。例如依赖 PostgreSQL transaction/lock 时 SQLite 不能证明对应事实；项目真实只使用 SQLite 时也不机械要求 PostgreSQL。

### User / Workflow Acceptance

从公开入口验证调用者能完成目标：入口、输入、操作、输出、状态、错误和必要副作用都从外部可观察。

- Web：Browser/UI workflow；
- CLI：真实命令/参数/stdin → stdout/stderr/exit code/副作用；
- Library/SDK：最小 consumer 调 public API；
- API：真实 HTTP/RPC public boundary；
- Data/ETL：代表性输入 → pipeline → output artifact/quality result；
- Mobile/Desktop：真实或批准的 simulator/device workflow；
- Infra/Release：validate/plan/build/apply/deploy 分别属于不同证据等级。

### Real Cross-component Golden Path

用于证明多个真实关键组件组装后确实接通。通常只保留少量高价值成功链；只有失败/恢复有独立高风险时再增加代表路径，不把所有 UI 状态复制成昂贵 Full-stack。

### External Dependency Probe

只有任务需要确认第三方 API、远端环境、硬件或 Provider **此刻真实事实**时才使用：字段、分页、错误、权限、限流、计费或设备行为。

固定边界：

- 默认关闭；
- 明确授权和费用/数据范围；
- 不打印 Secret；
- 不默认写生产数据；
- 区分代码缺陷、网络、权限和供应商问题；
- Probe 有时效性，不替代稳定 Fixture/Fake/Contract 回归。

### Build / Package / Runtime

任务影响 compiler/linker、package、image、install、startup、runtime config 或 release artifact 时必须单独验证；源码测试绿色不能证明正式产物可用。

## 3. 选择原则

```text
状态空间广度
→ 优先放在稳定、可控、低成本层

真实依赖语义
→ 由 Integration 证明

真实组件接线
→ 少量 Golden Path 证明

外部系统当前事实
→ 有界 Probe 证明
```

不要把“更真实”误解为“所有测试都必须 E2E”。越真实的层通常越慢、越贵、越难稳定制造边界条件。

## 4. Mock / Fake 的边界

Mock/Fake 只隔离**当前测试不负责证明的边界**。禁止：

- 用 Browser Mock 声称真实后端/数据库/Worker/Provider 已接通；
- 用 Fake/SQLite 声称任务真正依赖的 Runtime/Persistence 已验证；
- Mock 过度宽松到错误字段/请求也能通过；
- Mock 从猜测接口生成，而不是当前 Contract/生产代码事实。

## 5. 项目形态映射

项目形态只在 Testing 已经因真实测试意图命中后决定测试入口和证据层，不作为独立触发器。

### Web / Full-stack

通常组合：Browser/UI Acceptance + Backend/API/Persistence Integration + Contract；存在真实跨组件边界时补少量 Golden Path。Provider Probe 只在当前外部事实需要确认时启用。

### Backend / API

以服务器业务规则、API Contract 和真实 Runtime/Persistence 为主；没有 UI 时不制造 Browser 测试。

### CLI

重点是真 CLI invocation、exit code、stdout/stderr、filesystem/process/environment 副作用和 package/install smoke。

### Library / SDK

重点 public API/ABI、consumer compile/invoke、serialization/compatibility、package/install smoke。

### Data / ETL / ML

重点 input schema、deterministic transform、data quality、checkpoint/idempotency、batch rerun、artifact/model/version reproducibility。

### Mobile / Desktop

重点 View/State、navigation、permission/storage/network、simulator/device、build/package/signing（真实适用时）。

### Infra / IaC / Release

严格区分 lint/validate、plan/diff/dry-run、artifact/build 与真实 apply/deploy；较弱层不能冒充更强层。

## 6. 具体测试真实性与抗脆弱约束

职责从 Review 拆分到 Testing 时，以下测试工程约束必须继续保留，不能因 Owner 迁移被摘要掉。

### 6.1 Browser / UI Acceptance

如果测试使用网络 Mock，至少校验与当前场景相关的请求语义，而不是只看页面最后有没有元素：

- `method / URL / query / payload` 中与 Contract 相关的关键字段；
- enabled/disabled、eligibility、分页、排序、过滤、刷新、轮询等真实适用语义；
- 跨页面或跨状态结果是否真正由用户操作产生；
- Mock 数据必须来自当前正式 Contract、generated client 或生产代码事实，不能另写一套想象接口。

### 6.2 Backend / Integration

真实 Integration 必须按任务风险验证实际边界，例如：

- HTTP/RPC status、error Contract、serialization；
- 数据库 `事务 / 约束`、持久化和查询语义；
- `幂等 / 锁 / 并发`、重试、状态机；
- Worker/Job/Repository/queue 等真实调用链；
- pagination、eligibility、过滤、排序等会影响消费者结果的行为。

不能通过禁用真实安全检查、数据库约束、事务语义或关键 Runtime 行为来制造“稳定测试”。

### 6.3 Fixture / Test Data

测试数据不能只包含完美样例。按 Requirement/风险纳入真实适用的：

- null/empty/invalid/boundary/large 输入；
- 当前 Schema/Contract 中的时间、排序、分页、ID、enum 与兼容字段；
- 并发场景必须真的并发，而不是顺序调用后给测试起“concurrent”名字；
- Fixture/Fake/Mock 不得宽松到错误字段、错误请求或错误状态也能通过。

### 6.4 新增回归测试

新增测试优先选择最低成本、可稳定复现且直接断言可观察行为的层；测试名描述业务行为/风险，不描述偶然实现细节。Bug 回归应尽量满足修复前失败、修复后通过；不得为了一个用例无必要引入第二套测试框架。

### 6.5 抗脆弱边界

禁止用以下方式换取绿色：

- 依赖未受控外网作为普通回归前置；
- 用任意 `sleep` 掩盖同步、轮询或 race 问题；
- 只断言内部调用次数而不验证可观察结果；
- 测试失败后盲目更新 snapshot、Golden 或 Fixture，而不先确认正式行为是否改变；
- 删除断言、扩大容差、跳过失败场景或降低真实边界，只为让 CI 通过。

## 7. Evidence 表述

推荐：

```text
Browser Mock Acceptance passed for loading/empty/error/retry states.
Backend integration was not run, so persistence remains unverified.
One real cross-component golden path passed; broad error-state coverage remains at mock/integration layers.
External provider probe was not required for this change.
```

禁止笼统写“E2E 全通过”“测试充分”“系统完整验证”，除非实际证据确实覆盖对应边界。
