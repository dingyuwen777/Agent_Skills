# Figma 事实源与审查流程

这份 reference 解决两个常见误区：

1. 只看 Figma 截图就判断设计“没问题”；
2. 只看当前实现就要求设计机械迎合代码。

Figma 审查必须先识别项目形态和真实事实源，再判断设计与系统之间属于：正确映射、待实现设计、过期设计、实现缺陷还是未决产品决定。

---

# 0. 宿主 Figma 工具边界

本 Skill 定义的是审查方法、事实源和交付门禁，不替代当前宿主环境自己的 Figma MCP、插件 Skill、设计写入 API、权限和前置规则。

```text
先遵守宿主工具规则
→ 再按本 Skill 决定应该读取什么、检查什么、怎样判断 Ready
```

如果环境只能读 Figma：

- `review-only` 可以执行；
- `review-and-fix` 必须明确写入能力缺失；
- `baseline-ready` 对无法执行的必要验证如实标记，不得假装完成。

---

# 1. 开始前的最小事实恢复

先读取 [00_通用适用性与项目形态.md](00_通用适用性与项目形态.md)，确认项目属于 Web、Mobile、Desktop、Dashboard、Static Site、Design System 或其它形态。

有代码仓库时按项目规则读取最少充分事实：

```text
AGENTS / CONTRIBUTING / Project Rules
→ 当前需求 / Product Spec / Design Guide
→ 目标实现入口
→ 当前机器事实
→ 目标 Figma Page / Section / Frame / Prototype
```

“机器事实”根据项目实际选择：

```text
Route / Navigation
State / Store / ViewModel
API / RPC / SDK / Generated Client
CMS / Local Store / File System
Permission / Device Capability
Background Job / Runtime State
Database / Repository（有服务端时）
Tests / Fixtures / Config
```

没有某类边界就不要生造。

# 2. 三类事实源

## 2.1 设计事实

来源：

```text
Figma Frame
Component / Component Set
Component Property
Variable / Style
Prototype Variable / Reaction
Annotation
Flow Starting Point
```

它回答：

> 页面怎样表达、怎样交互、哪些模式复用。

它不自动证明真实系统已支持该行为。

## 2.2 系统机器事实

来源按项目实际：

```text
Public Contract / Schema
API / SDK / Generated Client
Domain / Service / ViewModel
CMS Model / Local State
Permission / Device Capability
Runtime / Job / Config
Tests
```

它回答：

> 当前系统真正支持哪些输入、输出、状态和约束。

## 2.3 当前运行事实

来源：

```text
真实 API / SDK Response
数据库 / CMS 当前数据
服务器 / 设备 / 本地运行状态
Feature Flag / Permission
有界外部 Probe
```

它回答：

> 此刻具体值是什么。

Figma 示例只能表达布局和状态，不替代当前运行事实。

# 3. Review Target

每次正式审查先写清：

```text
Project Shape:
Target User / Task:
Figma File:
Page / Section:
Frame / Node:
Prototype Starting Point:
Related Implementation Entry（适用时）:
Mode:
```

如果存在：

```text
正式开发基线
历史参考
备份
废弃归档
```

必须确定当前事实源。

---

# 4. 审查顺序

推荐：

```text
A. 项目形态与用户任务
B. 页面信息架构
C. 页面尺寸 / 布局 / 视觉 / 图片 / 标注
D. 字段与真实系统能力映射
E. 动态数据来源
F. 公共组件与业务逻辑复用
G. 状态覆盖
H. Prototype Variable / Reaction / Flow
I. 产品术语和敏感信息
J. Fresh Screenshot / Machine Audit
K. Design Context / 实现视角（适用时）
```

Design Context 是最后的实现视角复核，不是需求事实源。

# 5. 冲突分类

## `design_outdated`

当前正确产品/系统事实已稳定，Figma 仍表达旧行为。

→ 修 Figma。

## `implementation_issue_detected`

已批准需求/Contract/设计正确，但当前实现明显偏离。

→ 不让 Figma 迎合 Bug；返回项目研发工作流修实现，再 targeted re-review。

## `future_design`

设计表达已批准未来能力，当前系统尚未实现。

→ 保留 Future 标识；当前 Design-to-Code 不得假装已接通。

## `decision_required`

存在真实产品取舍，当前事实源没有决定。

→ 给证据和方案，等待 Owner 决策。

## `runtime_only`

设计结构正确，但具体值必须来自运行时。

→ 保留代表性示例，明确数据来源。

# 6. review-and-fix 的最小 Owner 原则

有修改授权时，先找问题真正属于：

```text
Design Token
Shared Component
Feature Public Component
Reusable Business Logic
Page Pattern
Single Frame
Prototype Variable / Reaction
```

优先修最小真实 Owner。

错误：

```text
多个页面同一 Select 都叠字
→ 每页分别移动 Text
```

正确：

```text
修公共 Select 的 Property/布局
→ 重新验证所有消费者
```

---

## 6.1 有界读取与可恢复写入

以下规则仅在需要工具读写 Figma 时执行；宿主规定的 Skill/API 前置步骤仍先完成。减少调用靠缩小每次读写的有效范围，不靠省略事实或验收。

- 首次建立任务内最小索引：File / Page / Section / Node ID、真实 Owner、直接消费者和对应实现入口；复用仍有效的索引，不每轮导出整份文件。节点被替换、删除、移动或宿主重连后，重新核验受影响身份和结构。
- 读取先取目标与必要父子/消费者的结构投影，只保留本轮需要的属性；按缺口下钻。独立只读请求可按宿主能力批量执行，输出过大时按 Owner/区块拆开；不以被截断输出推断未读内容。
- 写前检查目标身份、权限、字体是否已按宿主要求加载、Component Property/Variant 是否真实存在、父子布局条件是否成立。先完成一个可独立核验的 Owner 或页面区块，再扩展到同类消费者；不把大范围读取、复制、布局、删除和全量导出混成一次长调用。
- 有依赖的写入按顺序执行，避免多个调用并发修改同一 Owner、父子节点或共享消费者。批量大小由本轮成功耗时、输出与失败边界调整，不规定固定节点数或超时时长。
- 工具报超时、连接中断或服务错误时，写入结果先视为**未知**，不等于未执行或已回滚。先读回目标及相关父级/Owner，对照预期区分未应用、部分应用、已完成；只补未完成差异。无法核实时暂停依赖该结果的写入，保留准确位置和未确认项，不盲目重放创建/克隆/删除。
- 直接按 ID 读取失败时，先确认当前 File/Page 和节点是否被替换；宿主明确支持时，可从已确认父节点的 children 有界查找并复核身份。单次失败不能证明通用 API 不可用；不猜新 ID、不绕过宿主权限、不无界递归扫描。
- 每批写后读回实际 Node ID、Owner/实例关系和关键属性，并完成既有 Canvas-level Review；公共 Owner 的受影响消费者仍须覆盖。局部确认通过后才继续依赖它的修改，最后整体验收所有受影响域，不能用一个样例替代整体完成。
- 临时克隆/探索节点只在确有验证需要时创建，记录身份和用途；确认正式结果及引用关系后清除本次无用残留，不能因读取失败就扩大删除范围。

## 6.2 证据必须对应实际节点

截图/导出结果按 `File + Node ID + 本次修改后的状态 → 文件路径/链接` 对应，不能按异步任务完成顺序猜文件归属。交付前打开产物，核对页面标题、目标区块和尺寸；换名或重新导出时同步映射。

复用未受影响域仍有效的事实和证据；本次修改及共享 Owner 传播影响的区域取得新鲜结构/视觉证据。只导出验收需要的目标、受影响消费者及 Canvas 邻接范围，不每次微调重导全文件。证据等级及设计同步、人工复核要求仍按现有门禁执行。

# 7. 证据等级

## Metadata

证明节点、尺寸、父子结构、实例关系。

不能证明最终视觉没有重叠。

## Screenshot

证明当前可见视觉。

不能证明隐藏变量/Reaction/Property 正确。

## Prototype / Plugin API Audit

证明 Variable、Reaction、Flow、Overlay、Position、Scroll。

不能证明真实系统动作会成功。

## Design Context

证明实现方实际会看到的结构、组件、Annotation 和参考表达。

不能证明真实系统支持所有行为。

## Project/System Facts

证明真实系统能力和当前数据。

不能证明视觉正确。

因此 Ready 需要组合证据，而不是任一单层替代其它层。
