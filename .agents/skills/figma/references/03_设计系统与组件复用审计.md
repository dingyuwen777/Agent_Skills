# Figma 设计系统、组件与业务逻辑复用审计

判断公共组件、Feature、Page Pattern、业务规则的真实 Owner，以及 Figma 是否真复用而不是“看起来一样”。

---

# 1. 四层边界与系统化 Design Ownership Ladder

项目已有系统化设计体系时，按项目自己的命名恢复等价职责；不要求每个项目字面相同或层层齐全：

```text
Foundation / Design Token / 基础规范
→ Global Shared Component
→ Page Template / Page Pattern
→ Feature Public / Page Public Component
→ Formal Screen / State Frame（Consumer）
```

- Foundation / Token：稳定视觉语义。
- Global Shared：跨 Feature 稳定基础 UI，如 App Shell、Navigation、Page Header、Button/Input/Select、Tabs、Feedback、Modal/Drawer Shell。
- Page Template / Page Pattern：可复用页面壳或组合，如 Filter + Table + Pagination；不硬编码某个 Feature 业务事实。
- Feature/Page Public：同一业务域稳定复用的指标、详情、资格、文案映射、动态字段、表单规则；“公共”只表示真实复用范围内唯一 Owner。
- Page-private：单页特例。
- Formal Screen / State Frame：公共/稳定语义作为 Consumer，优先使用 Instance / Component Property / Variant；单页独有且无复用价值的结构可以保留 Page-private Composition，但不得升级成第二公共 Owner。

真实复用事实决定抽象层级；没有某层就按事实跳过。Figma 与代码组件不机械 1:1。公共语义改**最近且正确的真实 Owner**，局部差异留最低必要层；不得把 Feature 特例塞进 Global Shared，也不得把公共变化散落到多个 Formal Screen。

---

# 2. 真复用、假复用与 Owner-first Figma Mutation Gate

真复用至少满足：

- 页面消费 `INSTANCE`，主组件/组件集唯一；
- 可变内容走 Property / Variant，稳定语义走 Token；
- 不复制组件内部视觉层；
- 同一业务规则只有一个 Owner，多消费者共享同一状态、资格、默认值或字段来源。

假复用包括：手画相似 Frame、公共 Select 外覆独立 Text、Detach 后手改、同一规则多份 if/else。

任何创建、修复、整理或 Design-to-Code 回写前先定位 Owner：

```text
共享稳定视觉/交互 → Main Component / Component Set / Token
Feature 稳定业务组合 → Feature Public Component / Logic
局部业务变化 → Property / Variant / Page Pattern / Page-private Composition
```

已有 Owner 时**不得 Detach**、复制、重画或外覆 Text/Icon 制造**第二 Owner**。无法确认时先查 Component Set、Instance、Property、Token 和消费者；仍不明则 Finding/阻塞。

修改 Owner 后必须复核**受影响消费者**及适用的 Default/Hover/Selected/Disabled/Error、Size/Variant/Property、长文本、Auto Layout/Constraints、图标/Label/Hit Area、Prototype/Overlay；共享变化造成 Canvas 拥挤时继续执行 Canvas-level Review。

---

# 3. 视觉公共组件与业务公共逻辑分开

```text
Shared UI Component ≠ Business Rule Owner
```

Button 负责视觉/状态/交互壳；“什么时候允许提交”等资格由 Feature/Domain/Service Owner 决定。基础组件不拥有 API endpoint、业务权限、Feature 状态机、数据库查询或业务专属默认值，通过 props/events/state 与上层连接。

---

# 4. 跨页面业务逻辑复用

权限→操作、系统能力→选项、状态→文案、表单校验/格式化/默认值等同一语义，应复用已有 shared domain helper、feature public composable/view-model、state selector、backend/service capability、SDK/adapter 或 shared feature component；否则形成 Finding。

同一 Feature 多页面复用留在 Feature Public，不必升全局。相同外观不代表相同业务 Handler/资格。

---

# 5. Component Property 审计

可变内容优先用 Property：Button.Label、Input/Select.Text、Checkbox.Text、PageHeader.Title、Feedback.Message。

检查 `componentPropertyReferences`、重排后引用、Instance override、Variant 与外覆 Text；修改源组件后复核关键消费者。

---

# 6. Variant 设计

Variant 表达稳定视觉轴：State、Type、Checked、Tone。Plan=A/B 这类动态业务数据应由 Property / State / Runtime Data 驱动，不制造成 Variant。

---

# 7. Design Token 审计

稳定语义优先复用 Color / Typography / Spacing / Radius / Effect。**同值 ≠ 同语义；同语义 ≠ 多套 Raw 值。** Figma Token 映射项目现有样式系统，不因工具输出静默改代码 Token 架构。

---

# 8. 图标和资产

Unicode glyph 不自动等于生产 Icon Asset。复用项目图标体系/正式资产，并用“图标槽/刷新”这类语义命名。

---

# 9. Auto Layout 与浮层

正文优先 Auto Layout；Toast/Dropdown/Popover/Tooltip/Overlay 检查 `layoutMode`、`layoutPositioning`、`clipsContent`、scroll、z-order，必要时脱离布局流，不能只写 x/y 假设不回弹。

## 9.1 高度压缩与文字裁切

先查父级方向/宽高/padding/spacing/min/max → 子级 FIXED/HUG/FILL → axis sizing/layoutGrow/layoutAlign → 文字尺寸/换行/裁切 → override/相邻节点。合法值以当前 API/宿主为准；不机械全设 HUG，也不靠缩字号/任意固定高掩盖根因。

先在最小 Owner 验证正常与长内容，再验 Variant/实例和 Canvas。API 语义参见 [Figma layoutSizingVertical 官方说明](https://developers.figma.com/docs/plugins/api/properties/nodes-layoutsizingvertical/)。

---

# 10. 信息密度与抽象层级

视觉松散优先改现有 Feature Owner；只有真实跨 Feature 稳定复用才升级为 Global Shared。

---

# 11. 审计输出

至少说明：当前层级、建议 Owner、证据；哪些视觉组件必须复用、哪些业务逻辑必须唯一 Owner、哪些留 Feature、哪些不应全局化、修改 Owner 后需复核哪些消费者。
