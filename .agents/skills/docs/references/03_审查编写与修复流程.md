# 审查、编写与修复流程

Docs 不是固定模板工具。先确定当前任务到底是“只审查”“审查并修复”还是“新写/更新”，再选择最少充分步骤。

## 1. Review Only

用户只要求审查时，不自动修改文件。

执行顺序：

```text
明确目标读者和文档职责
→ 恢复当前事实源
→ 判断 not_applicable / targeted / full
→ 读取目标文档和必要上下游
→ 按六个维度审查
→ 区分文档问题 / 实现问题 / 未决问题
→ 给出有证据的问题和修改建议
```

Review 重点不是 Markdown 格式，而是：

- 事实错误；
- 关键遗漏；
- 因果链断裂；
- 术语没有解释；
- 历史流水账干扰当前理解；
- 复制机器事实形成第二套定义；
- 多个 Markdown 同时承担同一长期事实的完整解释 Owner，而不是最小上下文 + 导航；
- 新建文档已有合法 Owner 可以承载，却因为“内容更多/更完整/目录更顺眼”另起平行说明；
- 阶段性临时文档没有退出条件、长期知识迁移去向，或阶段结束后仍无理由滞留 live docs；
- 单个文档持续加入已经形成独立读者任务/Owner/生命周期的内容，导致局部修改必须理解大量无关章节，却没有经过 Document Growth Gate；
- 示例与当前行为不一致；
- 代码路径/命令/链接已失效；
- 真实仓库文件承担实现定位、事实验证、进一步阅读、修改入口或排障导航职责时，没有显示完整仓库相对路径、只写不可点击的 inline-code 路径、链接 target 已失效，或对 `.py`、`.json`、`.yaml`、`.toml`、`.sql` 等非 Markdown 文件漏做了应有链接；
- 误把命令、目录树、glob、占位路径、协议/流程示例、生成路径、代码字面量等非导航内容机械链接化；这类内容应按真实语义判断，不机械链接化；
- 文档声称的能力尚未实现；
- 实现偏离已批准事实，却被文档掩盖。

问题按实际严重性排序即可，不强制所有项目使用固定 P0/P1/P2 名称。

## 2. Review + Fix

只有当前任务授权修改时使用。

流程：

```text
先完成 Review
→ 对每个 finding 确定正确事实
→ 只修改受影响文档
→ 不顺手重写无关章节
→ 复核改后事实和读者理解链
→ 执行适用验证
```

如果发现实现 Bug：

```text
停止让文档追随错误实现
→ 记录 code_issue
→ 返回 Coding 修复
→ 修复后 targeted re-review
```

不要通过把“应该 A”改成“现在 B”来消除表面冲突，除非证据已经证明 B 是新的正式决定。

## 3. Write / Update

### 3.1 先过 Owner / Admission Gate

更新已有文档时先确认它仍是当前事实的合法长期 Owner；需要创建新文档时，先执行：

```text
项目本地文档规则 / Owner 导航
→ 与当前读者任务最直接相关的已有文档
→ 机器事实 Owner（适用时）
→ 现有 Owner 能否合法承载？
   ├─ 能：更新已有 Owner；新文档 not_admitted
   └─ 不能：证明独立读者任务、独立长期维护价值、清晰职责边界
            ├─ 成立：new_document_admitted
            └─ 不成立/证据不足：不新建，继续恢复事实或报告缺口
```

这里的搜索是 targeted owner search，不是全文库相似度扫描。主题词相似、都提到同一个组件或都链接同一机器事实，并不自动构成重复；只有多个位置都要独立维护同一**完整解释职责**时才需要收敛。

### 3.2 再组织内容

通过准入（或确认更新已有 Owner）后，至少回答：

```text
谁会读？
他为什么需要这篇文档？
读完要能做什么？
这篇文档完整负责什么、不负责什么？
当前正确事实源是什么？
哪些机器事实只应该链接/定位，不能复制？
哪些仓库内具体文件引用承担导航职责，需要同时保留完整路径和可点击链接？
```

然后按真实读者任务组织，而不是先套一个巨大的固定模板。

常见顺序可以是：

```text
为什么存在 / 问题
→ 责任和边界
→ 输入输出
→ 数据/调用/状态流
→ 当前实现位置
→ 必要术语
→ 最小例子
→ 验证/调试/限制
→ 精确事实源
```

不适用的部分直接省略。

### 3.3 Document Growth Gate：已有文档也要有增长边界

更新已有文档不是“只要 Owner 对就继续 append”。新增一段明显的新职责、多个 H2/H3 主题、持续扩展的专题内容，或一次修改使文件明显更难定位时，执行增长复核：

```text
新增内容
→ 仍服务同一主要读者任务？
→ 仍属于同一完整解释 Owner？
→ 生命周期一致？
→ 没有机器 inventory / 历史流水迁入？
→ 读者仍能 targeted 定位？
→ 局部变化不需要理解大量无关章节？
```

全部成立才继续在原文档扩写。任一项不成立时，先恢复项目已有 Owner/导航，再选择：

- 把内容迁到已有正确 Owner；
- 新建一个通过 New Document Admission Gate 的稳定 Owner；
- 把原文档收缩为概览/导航；
- 对阶段性内容建立退出条件，而不是继续累计。

**规模只作为风险信号。** 项目已有 quantitative budget（行数、字节、章节数等）时必须遵守；项目没有预算时，不为所有仓库发明统一硬阈值。真正的拆分依据是职责/读者任务/生命周期已经分离。

拆分禁止按长度机械切块；拆分后不得在原文档保留一份完整副本，也不得制造多层空壳索引。

### 3.4 临时文档的知识迁移与退出

如果文档只在某个 Migration、Upgrade、Roadmap 阶段、上线/回填窗口或其他可结束阶段内成立，建立或更新时同时记录：

```text
live 条件
→ 退出条件
→ 仍有效长期知识的目标 Owner
→ 历史证据的项目既有 Owner
→ 删除 / 退役 / 从 live 导航移除的时机
```

退出时按顺序执行：

1. 先把仍有效知识迁到正确长期 Owner；
2. 再把施工/验收历史保留在项目已有历史机制；
3. 验证 live 导航、链接和消费者已不再依赖临时文档；
4. 最后才删除或退役。

无法证明知识迁移完成时，宁可保留并明确待迁移，也不能为了减少文件数直接删除。

Greenfield / Bootstrap 文档还要明确“当前已建立”和“已确认但尚未实现”的边界；不能因为设计已经批准，就把尚未创建或尚未验证的工程基线写成当前事实。

## 4. 六个审查维度怎么落地

### Fact Correctness

逐条核对文档的关键断言：

- 当前支持什么；
- 当前入口是什么；
- 数据/调用经过哪里；
- 谁拥有写职责；
- 错误/限制是什么；
- 命令、路径、版本或配置从哪里得出。

不要只检查“文件存在”。

### Coverage

从读者任务反向检查：

```text
他要理解/使用/修改/排障什么？
→ 文档是否覆盖必要入口、流程、边界、限制和验证？
```

不要为了“全面”加入和目标读者无关的内部细节。

### First-principles Clarity

检查是否先说明：

```text
问题
→ 原因
→ 必要机制
→ 实际流动
→ 实现
```

如果一上来就是框架名、模式名、类名或缩写，需要调整解释顺序。

### Terminology

对第一次出现的重要术语问：

```text
基础较弱的读者能否不用再查三个新术语就理解？
```

如果解释仍然只是术语换术语，就继续改成白话。

### Source-of-truth Safety

检查是否存在：

- 手抄完整 Schema；
- 手抄完整 OpenAPI/IDL 字段；
- 手抄依赖版本表；
- 手抄 generated code；
- 大段复制生产代码；
- 两份 Markdown 同时维护同一精确规则；
- 承担导航职责的仓库内具体文件链接，其显示路径、相对 target 或最终生成位置已经与真实文件漂移；
- 为了省链接而把真实 `.py/.json/.yaml/.toml/.sql` 等事实源只写成不可点击 inline-code 路径，迫使读者手工复制查找。

如果有，优先保留解释和链接真实事实源；链接类问题按当前文档/最终输出位置恢复真实相对目标，不用不可点击路径或猜测性链接掩盖。文件类型本身不是判断依据，是否承担真实导航职责才是判断依据。

### Usability

让文档回答实际操作问题：

- 第一次接手的人从哪里开始看？
- 想改这个行为先定位哪？
- 想确认数据有没有走到下一步查什么？
- 当前失败时能区分是哪一层吗？

文档只“定义概念”但不能帮助行动时，通常仍不够实用。

## 5. targeted 的默认读取法

`targeted` 不按目录全读，而是按变化链读取；涉及新文档/Owner 判断时，只在这条链上增加最小 Owner 搜索：

```text
变化入口 / 新文档读者任务
→ 当前真实 Owner/实现
→ 项目本地文档规则 / 最直接相关已有 Owner
→ public Contract/Schema（受影响时）
→ 直接消费者
→ 承担该事实的当前文档
→ 对应测试/命令（用于验证）
```

必要时向上下游再扩一层，但每一步都要说明为什么需要。

例如只改一个导入参数，不应该因为仓库还有调度、报告、其他 Provider、移动端或独立工具模块就把这些专题文档全部读一遍。

## 6. full 也不是无限读取

`full` 先定义“完整受影响域”。

例如主数据处理链路整体重构，可以覆盖：

```text
总体架构中相关边界
输入到统一内部模型的主链
持久化/Artifact 落地
API/Worker/CLI/Consumer 边界（项目实际存在时）
模块 README
调试/运维专题
```

但与本链无关的设计工具指南、报告排版、其他独立 Provider/模块细节仍可不读。

另一个例子是 Greenfield 工程基线治理：`full` 可以覆盖根 README、架构/决策、build/test/package/run、配置/部署和模块导航，但仍不等于把所有 Markdown 逐文件机械扫描。

## 7. 例子和命令怎么验证

文档出现可执行命令或示例时，按风险决定是否实际运行：

- 当前任务声称命令可用：尽量运行；
- 示例只是概念示意：明确它是示意，不伪造执行证据；
- 付费 API / 生产写入 / 危险操作：遵守更高优先级授权与安全规则，Docs 本身不授权执行；
- 无法运行：明确“未实际验证”，不要写成已通过。

## 8. 完成输出

Review Only 通常至少给：

```text
Docs Impact 和范围
读取的关键事实源
发现的问题（按重要性）
哪些文档本身正确、不需要改
是否发现实现问题或未决事实
未验证项
```

Review + Fix / Write / Update 再补：

```text
实际修改文件
每个修改解决什么理解或同步问题
实际验证
剩余风险
```

不要只回复“文档已同步”。
