# 审查、编写与修复流程

Docs 不是固定模板工具。先确定 Review Only、Review + Fix 或 Write/Update，再选择最少充分步骤。

## 1. Review Only

```text
明确目标读者和文档职责
→ 恢复当前事实源
→ 判断 not_applicable / targeted / full
→ 读取目标文档和必要上下游
→ 审查事实、覆盖、因果、术语、source-of-truth、安全和实用性
→ 区分文档问题 / 实现问题 / 未决问题
→ 给出有证据问题和建议
```

不只检查 Markdown 格式，还检查：事实错误、关键遗漏、因果断裂、术语未解释、历史流水账、第二套事实、失效路径/命令/链接、待实现能力误写、实现 Bug 被文档掩盖。

## 2. Review + Fix

只有授权修改时：先完成 Review → 确认正确事实 → 只改受影响文档 → 不顺手重写无关章节 → 复核事实和读者理解 → 执行适用验证。

发现实现 Bug：停止让文档追随错误实现 → `code_issue_detected` → 返回 Coding → 修复后 targeted re-review。

## 3. Write / Update

先回答：谁会读、为什么需要、读完要做什么、正确事实源是什么、哪些机器事实只链接不复制。然后按实际读者任务组织：

```text
为什么存在 / 问题
→ 责任和边界
→ 输入输出
→ 数据/调用/状态流
→ 当前实现位置
→ 必要术语
→ 最小例子
→ 验证/调试/限制
→ 精确事实源
```

不适用部分省略。

## 4. 六个审查维度

- Fact Correctness：关键断言与正确事实一致；
- Coverage：读者完成任务需要的入口/流程/边界/限制/验证没有遗漏；
- First-principles Clarity：先问题/原因/机制/流动，再实现名词；
- Terminology：重要术语能用白话解释；
- Source-of-truth Safety：不手抄完整 Schema/OpenAPI/lock/generated code/生产实现；
- Usability：读者知道从哪开始、去哪定位修改、怎样验证和排障。

## 5. targeted 的默认读取法

```text
变化入口
→ 当前 Owner/实现
→ public Contract/Schema（受影响时）
→ 直接 consumer
→ 承担该事实的当前文档
→ 对应测试/命令
```

必要时再向上下游扩一层，每一步说明原因。不要因为项目还有其他独立模块就一起扫描。

## 6. full 也不是无限读取

先定义完整受影响域。例如主 ingestion/pipeline/请求链整体重构时，可以覆盖总体架构相关边界、主链、persistence、consumer、模块 README、调试/运维专题；无关 UI 设计、报告排版或其他独立 Provider 不必读取。

## 7. 示例和命令验证

- 声称命令可用：尽量实际运行；
- 只是概念示意：明确示意，不伪造执行证据；
- 付费 API/生产写入/危险操作：遵守上位授权，Docs 不自动授权；
- 无法运行：明确未验证。

## 8. 完成输出

Review Only：Docs Impact/范围、关键事实源、发现问题、哪些文档正确无需改、是否发现实现问题/未决事实、未验证项。

Review + Fix/Write：再补实际修改文件、每个修改目的、实际验证、剩余风险。
