# 事实源与同步判断

技术文档同步第一步不是“看代码然后改 Markdown”，而是先回答：**这类事实由谁负责，当前哪份证据最能证明它？**

## 1. 三类信息

### 当前已实现事实

例如当前 API/CLI/协议结构、Schema/Migration、模块入口/调用链、配置/命令/依赖版本、真实测试行为。优先由代码、Contract/Schema/Migration、generated artifact、lock、测试和实际运行等机器事实证明。文档解释目的、边界、用法和定位，不复制一套完整机器定义。

### 已批准但尚未实现设计

正式 Roadmap/Spec/ADR/Change 可以记录目标状态。不能因为代码暂时没有就自动删除，但必须明确“计划/待实现”，不能写成当前已支持。

### 历史原因

历史 Change/ADR/Release Notes/Git history 回答为什么当时改变。当前 README/Architecture/Guide 不应要求读者按时间顺序阅读全部历史才能理解现在。

## 2. 机器事实不等于代码永远正确

文档与实现冲突时按项目规则和上游事实判断：实现偏离已批准约束 → 返回 Coding；实现按新决定变化而文档落后 → 更新文档；正式设计描述未来 → 保留并标待实现；双方证据不足 → 继续调查或提请上游决定。

## 3. 避免第二套事实

已有可靠机器事实时通常不要在 Markdown 完整复制：API 字段全集、JSON Schema、数据库列/索引/约束、函数签名、精确依赖版本全集、generated client、枚举全集等。

文档更适合解释：Contract 为什么存在、最重要业务语义、调用者怎样用、失败/兼容边界、最新精确定义在哪里。

## 4. 什么时候引用代码/表/类/函数

只看两个标准：是否明显帮助理解/定位；是否不会制造需要双维护的第二套事实。

推荐写“生产入口位于某模块，该模块负责校验输入并调用领域服务，精确字段以机器 Contract 为准”；不推荐复制整段函数、枚举全部 helper、手写完整 Schema 表或只列一串类名不解释职责。

## 5. Docs Impact

- `not_applicable`：不改变人类需要理解/操作/调用/维护/排障的事实；给具体依据；
- `targeted`：默认有影响模式，从变化边界反推机器事实、直接 consumer 和承担该事实的文档；
- `full`：核心架构、主链、多模块 Contract、部署/恢复模型或文档治理结构发生系统变化；完整覆盖受影响域，不是读取所有 Markdown。

## 6. 候选文档不是必改清单

逐份判断它是否承担该事实、当前是否正确、修改是否制造重复、不改是否会让读者误解。只有证据支持时才产生 diff。

## 7. 同步完成最低证据

按实际任务验证：引用路径存在、链接无明显断裂、描述与正确事实一致、示例与当前公共行为兼容、命令是当前入口、声称执行过的命令有本轮证据、未实现能力没有写成已实现、没有把实现 Bug 写成正式设计。
