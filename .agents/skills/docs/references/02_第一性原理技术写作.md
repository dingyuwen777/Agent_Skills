# 第一性原理技术写作

技术文档的目标是让读者理解并完成真实任务，不是展示术语储备。

## 1. 先讲问题，再讲方案

优先回答：为什么需要、没有它会怎样、解决哪一段问题、不负责什么。然后再介绍架构、类、表、接口或设计模式。

不要只写“采用 Repository Pattern/DDD/Hexagonal Architecture，实现高度解耦”。先解释真实问题、依赖关系和必要机制；项目确实使用这些术语时再说明它们在当前项目中对应什么职责。

## 2. 先解释真实流动，再解释内部名字

常见顺序：

```text
输入
→ 关键处理步骤
→ 状态/数据变化
→ 输出/持久化/下游消费者
```

通用数据处理示例：

```text
外部输入
→ 入口/API/Reader
→ 校验或转换
→ 统一内部结构/领域规则（项目实际需要时）
→ 持久化或输出 Artifact
→ 下游 consumer
```

CLI：

```text
参数/stdin
→ parser
→ command handler
→ 文件/网络/进程副作用
→ stdout/stderr/exit code
```

Embedded：

```text
协议输入/传感器状态
→ parser/state machine
→ hardware abstraction
→ 设备输出/状态
```

不要为了模板硬造“数据流”。

## 3. 术语后置并用白话解释

重要术语第一次出现时说明：它在当前上下文是什么意思、为什么需要、和读者已知内容的关系。允许保留标准名/库名/协议名，但不要用缩写替代因果解释。

## 4. 最小例子只解决一个理解障碍

例如解释幂等：第一次使用同一请求身份创建任务；网络超时后重试仍返回同一任务，不生成第二个副作用。例子只解释机制，不复制完整生产 Schema/HTTP/Worker 实现；示意值要明确不是生产事实。

## 5. 是否写代码位置，看理解价值

路径/类/函数/表/接口适合帮助定位生产入口、Owner、修改点和验证点；不适合枚举全部 helper、复制生产代码、维护文件树镜像或手抄 Schema。

## 6. 不同文档的读者任务

### README

说明模块做什么、为什么存在、怎么运行/使用、输入输出、核心入口、常见修改点和限制。

### Architecture / Design

解释长期边界、模块协作、不能静默改变的决定、主要数据/调用链和机器事实位置。

### API Guide

解释业务目的、请求/响应语义、关键状态/错误/幂等/分页/兼容规则；已有机器 Contract 时不复制全部字段。

### Debug / Operations

解释现象、正常链路、从哪里查、日志/状态/命令证明哪一层、常见失败边界和安全恢复。

### Decision / RFC

解释问题/硬约束、真实方案、选择依据、代价和重新评估条件；不用“先进/企业级/高可用”等形容词代替机制。

## 7. 当前说明不要写成历史流水账

当前文档直接说明“现在为什么这样、怎么工作”。真正影响当前理解的历史原因可以简短链接 ADR/Change/Git；其余历史留在历史事实源。

## 8. 白话不等于删除技术细节

事务、锁、幂等、Migration、Contract、状态机、ABI 等如果确实影响行为必须保留，只是先解释必要性，再给术语、实现、失败边界和验证。

## 9. 文档完成后的读者测试

检查读者是否知道：为什么存在、解决/不解决什么、主要流动、真实实现/机器事实在哪里、术语能否被白话解释、怎样验证/使用/修改/排障，以及是否复制大量机器事实造成双维护。
