# 第一性原理技术写作

技术文档的目标是让读者理解并完成真实任务，不是让作者展示术语储备。

## 1. 先讲问题，再讲方案

优先回答：

```text
为什么需要它？
没有它会出现什么具体问题？
它解决哪一段问题？
它明确不负责什么？
```

然后再介绍架构、类、表、接口或设计模式。

不推荐：

> 系统采用 Repository Pattern、DDD 和 Hexagonal Architecture，实现高度解耦。

推荐先说明实际机制：

> 多个外部来源的字段和协议不一样。如果后续业务代码直接理解每个来源自己的格式，所有模块都会和外部格式耦合。因此系统先把外部输入转换成统一内部结构，后面的持久化和业务处理只依赖这一种结构。

如果项目确实使用 Repository、DDD 等术语，再在读者已经理解问题后说明这些术语在当前项目中对应什么职责。

## 2. 先解释真实流动，再解释内部名字

大多数系统文档最容易理解的顺序是：

```text
输入
→ 关键处理步骤
→ 状态/数据怎么变化
→ 输出/持久化/下游消费者
```

例如一个文件导入型系统可以写成：

```text
用户提交文件
→ 接口/命令创建处理任务
→ 后台执行器读取文件
→ 转成统一内部结构
→ 校验/去重
→ 写入项目真实持久化层
→ 调用者查询或取得结果
```

这个例子只说明写作顺序；目标项目没有 API、Worker、数据库时不要机械套用。

读者理解真实链路后，再解释项目实际使用的 Batch、Job、Mapper、Canonical、Repository 等内部名字会更容易。

如果主题不是数据处理，就用真实控制流或状态流，例如：

```text
CLI 参数
→ parser
→ command handler
→ 文件系统副作用
→ exit code
```

或：

```text
设备协议输入
→ parser
→ state machine
→ hardware abstraction
→ target output
```

不要为了符合模板硬造“数据流”。

## 3. 术语后置，术语必须用白话解释

重要术语第一次出现时至少说明：

```text
它在当前上下文是什么意思？
为什么需要这个概念？
它和读者已经知道的东西有什么关系？
```

例如：

> `Canonical` 可以理解为系统内部统一的数据格式。不同外部来源先转成它，后续代码就不用分别理解每个来源自己的字段。

这比只写“Canonical Model 是领域标准化层”更有帮助。

允许保留标准名、库名、协议名和领域术语，但不要用缩写或专业词替代解释。

## 4. 最小例子只解决一个理解障碍

能用最小例子明显降低理解成本时就给例子。

例如解释幂等：

```text
第一次提交：request_id = abc
→ 创建任务 #1

网络超时后重试：request_id 仍然是 abc
→ 返回任务 #1
→ 不再创建任务 #2
```

这个例子只解释“重复请求为什么不会产生第二个任务”，不需要把完整数据库表、HTTP Request 和 Worker 代码都复制出来。

例子必须明确是说明机制的示意时，就不要让读者误以为这些值来自生产环境。

## 5. 是否写代码位置，看它是否真的帮助理解

代码路径适合回答：

- 生产入口在哪；
- 哪个模块真正拥有这个行为；
- 想修改这个行为应该先从哪里看；
- 当前描述可以去哪里验证。

代码路径不适合用来：

- 枚举所有内部 helper；
- 代替职责解释；
- 复制整段实现；
- 制造一个和真实代码结构同步维护的“文件树镜像”。

类名、函数名、表名、接口名同理。

### 5.1 仓库内具体文档引用：路径可见且链接可点

当 Markdown 技术文档引用**当前仓库内另一个具体文档**，并且目标文件已经由当前仓库事实确认时，导航必须同时满足“人能看清目标”和“可以直接打开”：

- **link label 使用完整仓库相对路径。** 例如目标事实是 `docs/architecture.md`，显示文字就保留 `docs/architecture.md`，不要只写“架构文档”“这里”“详情”这类隐藏真实位置的标题；
- **link target 使用从当前文档位置可解析的相对路径。** 不为了方便绑定 GitHub 域名、固定 branch 或本机绝对路径；目标必须真实存在，不能为了生成链接猜一个可能的文件名；
- **不得只写不可点击的 inline-code 路径。** 如果这段文字的职责就是让读者去读另一个真实文档，应提供链接，而不是只给 `` `docs/architecture.md` `` 让读者复制查找；纯文档导航也不应仅用 fenced code block 承担；
- **模板和生成型文档按最终位置验证。** 模板源文件所在目录与最终生成文档所在目录可能不同；相对链接必须在**最终输出位置重新验证**，不能只证明模板源码位置能点；
- **目标缺失时失败关闭。** 路径不存在、文档已改名或当前事实不足时，先恢复正确目标；无法确认就明确报告断链/未确认，不创建看似可点但实际错误的链接；
- **不要机械链接化非导航内容。** 命令、目录树、glob、`<placeholder>`、协议/流程示例、生成路径、代码字面量即使看起来像文件名，也只有在语义上确实承担“打开当前仓库真实文档”的导航职责时才转成链接；
- 外部网站/外部文档不属于“仓库相对路径”规则；使用已经确认的稳定 URL 和对读者有意义的链接文字，不伪造仓库路径。

这条规则的目的不是追求 Markdown 形式统一，而是同时保证**可定位性、可点击性、可移植性和事实正确性**。

## 6. 不同文档有不同读者任务

不要把所有技术文档写成同一种结构。

### README

优先帮助读者快速回答：

```text
这个模块做什么
为什么存在
怎么运行/使用
输入输出是什么
核心代码入口在哪
常见修改点和限制是什么
```

### Architecture / Blueprint

优先解释：

```text
为什么采用这个长期边界
模块怎么协作
哪些决定不能被普通任务静默改变
主要数据/调用链
机器事实在哪
```

不要复制每个类和字段。

### API Guide

优先解释：

```text
调用者为什么用这个接口
请求/响应的业务语义
关键状态、错误、幂等、分页或兼容规则
完整机器定义在哪里
```

已有 OpenAPI/Schema/IDL 时，不再手写一份完整字段镜像。

### Debug / Operations Guide

优先解释：

```text
出现什么现象
从哪里开始查
正常链路是什么
哪些日志/状态/命令能证明哪一层
常见失败边界
如何安全恢复
```

### Design / Decision

优先解释：

```text
问题和硬约束
真实可选方案
为什么选当前方案
代价和边界
什么时候需要重新评估
```

不要用“先进、企业级、高可用、可扩展”这类无法单独证明机制的形容词替代设计依据。

### Greenfield / Bootstrap Guide

如果文档服务于新项目建立工程基线，优先解释：

```text
目标和运行环境
→ 为什么选择当前最小技术路线
→ 已确认的不变量
→ 目录 / build / test / package 如何形成最小闭环
→ 哪些能力明确延期
→ 后续修改真实事实应从哪里开始
```

不要把“目前只有一套初始实现”写成永远不可改变的架构真理；长期约束必须有正式决策依据。

## 7. 当前说明不要写成历史流水账

不推荐：

```text
Stage 3 加了 A
Stage 4 改成 B
PR #52 又补了 C
后来我们又重构成 D
```

如果读者只想知道现在怎么工作，这些历史会增加理解成本。

当前文档应该直接说明 D 现在为什么存在、怎么工作。真正影响当前理解的历史原因可以简短保留并链接 ADR/Change/Git；其余历史放到历史事实源。

## 8. 白话不等于删掉技术细节

“适合基础较差的人”不等于把重要机制全部简化掉。

正确做法是：

```text
先用白话解释目的和因果
→ 再给必要技术名词
→ 再给真实实现定位
→ 再给边界、失败和验证
```

事务、锁、幂等、Migration、Contract、状态机、ABI、设备约束等如果确实影响系统行为，必须保留，只是要先解释它们为什么必要。

## 9. 文档完成后的读者测试

针对目标读者问：

1. 他是否知道这个东西为什么存在？
2. 他是否知道它解决和不解决什么？
3. 他是否能复述主要数据/调用/状态流？
4. 他是否知道真实代码或机器事实在哪里？
5. 重要术语是否能不用更多术语解释清楚？
6. 他是否知道怎么验证、使用、修改或排障？
7. 文档有没有复制大量机器事实，让未来维护者必须同步改两处？

如果主要问题答不上来，文档即使格式漂亮也需要继续修改。
